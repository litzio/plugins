## Automotive SPICE 4.1 및 ALM 참고 조사

- VDA QMC 영문 PAM 4.1은 2026-08-24 공개판이다. §3.3.4의 생명주기 모델과 PAM의 구분을 따르고, Annex C.4를 링크·내용 검토 구분에 참고했다. 과제별 릴리즈에서 여러 프로세스를 동시에 진행하고, 반복과 재검토는 별도 이력으로 기록한다. 실행 상태, 산출물 승인, 링크 존재, 내용 정합성, 현재 검증 상태, 평가 준비, 평가자 기록은 독립된 필드다. [VDA QMC 공개 자료](https://vda-qmc.de/en/automotive-spice/automotive-spice-veroeffentlichungen/) · [PAM 4.1 영문, §§3–5 및 Annex C.4](https://vda-qmc.de/wp-content/uploads/2026/09/Automotive-SPICE-PAM-v41.pdf)
- PAM 2~3쪽의 배포·파생물·상표 조항을 확인했다. 플러그인과 홍보 자료에는 프로세스 ID, 의미가 맞는 짧은 UI 라벨, 자체 작성한 준비 점검 항목과 공식 링크를 사용한다. PAM PDF·본문·공식 체크 항목의 전문과 VDA 로고는 동봉하지 않는다. Automotive SPICE®는 VDA 등록 상표로 표기하고 제품명은 Litzio Engineering Lifecycle로 유지한다. 평가 준비 화면은 내부 점검과 증거 탐색용이다. 공식 평가, 인증, 적합성 보장 표현은 사용하지 않는다. [PAM 4.1, 2–3쪽](https://vda-qmc.de/wp-content/uploads/2026/09/Automotive-SPICE-PAM-v41.pdf#page=2)
- Polarion의 문서 단락 단위 식별과 검토에서 **원문 버전·위치를 보존하는 대조 화면**, DOORS Next의 link validity에서 **링크별 정합성 검토와 버전 의존성**을 가져왔다. [Siemens Polarion ALM](https://polarion.plm.automation.siemens.com/products/polarion-alm) · [IBM DOORS Next Link Validity](https://www.ibm.com/docs/en/SSUVLZ_7.0.2/pdf/doorsnext_master_702.pdf)
- Jama Trace View의 상하류 탐색과 관계 규칙, Codebeamer Traceability Browser의 단계별 열에서 **선택 기준 탐색, 누락 근거, 다열 Lineage**를 참고했다. 구현에서 Litzio의 테마와 공용 부품을 사용한다. [Jama Trace View](https://help.jamasoftware.com/ah/en/get-started/getting-started/exploring-the-jama-connect-workspace/trace-view.html) · [PTC Traceability Browser](https://support.ptc.com/help/codebeamer/r3.1/en/codebeamer/cbx_user_guide/cbx_traceability_browser/cbx_12450789.html)

## 공개 SDK 지원 범위와 제안

| 기능 | 근거와 적용 방향 |
| --- | --- |
| 공개 React 화면·테마 | manifest에 React JS/JSX 화면 엔트리 하나를 선언한다. Host의 React를 받아 공용 ScreenLayout, Toolbar, DataTable, Notice, Picker, Tooltip, ContextMenu, 알림과 디자인 토큰을 우선 적용한다. 도메인은 TypeScript로 엄격하게 검사하고 Host가 지원하는 아티팩트로 출력한다. |
| 리치오 탭·라우팅 | 공식 manifest에는 단일 main이 기여되고 fileActions에서 같은 화면이 재사용된다. 런타임에서 동일 플러그인의 독립 네이티브 프로젝트 탭 두 개를 만드는 계약은 확인되지 않았다. 한 네이티브 탭 안에 프로젝트 탭을 두고 projectId로 선택·필터·그래프 상태를 격리한다. 네이티브 독립 탭이 필수라면 프로젝트 키를 받는 SDK 화면 열기 계약이 필요하다. |
| 저장 및 설정 | settingsSchema는 환경 설정을 제공한다. 플러그인 작업 데이터를 위한 전용 KV/DB 계약은 확인되지 않았다. 공개 제공 pickPath로 열린 Host 작업 폴더를 선택 → 플러그인 데이터 파일 생성·열기 → Host의 Node 파일 처리로 영속 저장을 제안한다. 배포물과 브라우저 프로필에는 편집 데이터를 저장하지 않는다. 재실행 후 같은 데이터 파일을 열면 저장 팩과 연결한 자산을 복원한다. 저장 파일을 Host에서 찾아 다시 열 수 있도록 전용 확장자와 fileActions를 함께 사용한다. 제안할 SDK 개선은 플러그인별 저장소, 리비전 충돌 및 변경 알림이다. |
| 파일·문서·내보내기 | pickPath, openDocument, saveDocument, 공개 문서 작성 입력, DocumentView, LinkedDocumentView와 파일 동작을 사용한다. 리치오 문서는 공개 Node 읽기·쓰기 또는 공식 CLI 사용을 검토한다. PDF 원문 렌더링과 좌표 강조는 동봉 가능한 PDF 렌더러를 검증한다. Docx는 원문 열기와 문단 식별 또는 문서 가져오기에서 사용자가 생성한 파일 교환으로 시작하고 원본 DOCX의 정확한 페이지 하이라이트는 별도 검증 대상으로 둔다. 데이터 보고서·CSV/Markdown을 내보내고 증거와 원본 참조를 유지한다. |
| 에이전트 | assistant:true 읽기 operation과 plugin 스킬을 문서화 계약으로 제공할 수 있다. 질의는 projectId·release·baseline을 받아 ID, 문서 버전·위치, 경로, 판정 근거를 되돌린다. 공개 비서 도구는 읽기 전용이다. 제안의 반영은 화면에서 사람의 검토·승인 후 저장한다. 에이전트가 플러그인 프로젝트의 임의 노드로 포커스를 보내는 공개 브리지까지는 확인되지 않아 첫 시연은 결과 ID/리치오 원문 링크와 화면 내 검색을 사용한다. |
| 명령·단축키·메뉴·알림 | 화면의 공용 부품과 화면 단축키 계약에 맞춰 작업별 메뉴·키보드 조작·알림을 사용한다. 앱 전역 명령·단축키의 임의 manifest 등록은 확인되지 않았다. 네이티브 컨텍스트 기여는 공개 fileActions 범위다. |
| 플러그인 간 연계 | 계약 파일을 교환하고 문서·증거를 명시적으로 연결한다. 상호 소스 import 및 플러그인 작업 직접 호출에 의존하지 않는다. |
| 배치·그래프 | 깊이를 제한한 양방향 그래프를 번들 안에서 렌더한다. React Flow와 별도 자동 배치의 조합을 후보로 검토한다. MiniMap 및 viewport 지원은 문서로 확인했다. Host 제공 React, CSP, 라이선스와 오프라인 번들 런타임을 검증하고 라이브러리 조합을 확정한다. [React Flow 레이아웃 가이드](https://reactflow.dev/learn/layouting/layouting) · [MiniMap 계약](https://reactflow.dev/api-reference/components/minimap) |
| 네트워크·장기 처리 | Host Node 작업에 파일·네트워크 권한이 있지만 기본 데모는 오프라인이다. 오래 걸리는 파싱·분석은 요청을 빠르게 접수하고 작업 상태를 조회하도록 계획한다. 워크스페이스 작업의 영구 스케줄러나 플러그인 전용 백그라운드 플랫폼을 가정하지 않는다. |
| ReqIF와 Git | ReqIF 1.2는 선택 범위다. 손실 없는 round-trip(업무 ID, 타입, 형식 있는 값, 계층·다대다 관계)을 통과한 데이터만 호환 범위로 표시한다. Git 프로젝트 API는 공개 계약에서 확인되지 않았다. 파일/리치오 문서 링크와 내보내기를 먼저 사용하고 플랫폼에서 업무 Baseline을 계산한다. [OMG ReqIF 1.2](https://www.omg.org/spec/ReqIF/1.2/) |

SDK 출처는 정적 계약 및 화면 컴포넌트 표다. FileActions는 이미 열린 화면의 fileOpen 문맥을 바꾸며 두 프로젝트를 위한 신규 네이티브 탭 슬롯을 선언하지 않는다. ## 데이터 모델과 소유권

| 데이터 | 계획 |
| --- | --- |
| Project, Release, User | 각 프로젝트의 코드, 제품, 담당, 릴리즈와 사용자 역할. 모든 운영 객체는 내부 ID와 중복 없는 프로젝트 키를 갖는다. 사용자 표시 이름과 키를 구분한다. |
| ProcessDefinition, ProcessInstance | 정의는 (pamVersion, processCode) 키로 카탈로그에 등록한다. ProcessInstance가 프로젝트·릴리즈·반복 및 적용 상태, 담당자, 계획·실적을 소유한다. 프로세스 적용이나 정의 갱신은 이미 승인한 릴리즈의 규칙 판본을 바꾸지 않는다. |
| SourceDocument, DocumentRevision, SourceAnchor | 문서 정체성과 불변 버전·파일 해시를 분리한다. 원문 위치는 문서 버전·쪽·문단 키와 정규화된 바운딩 박스 및 원문 인용을 보존한다. 새 버전은 새 앵커다. 좌표를 얻지 못하면 페이지·문단과 원문을 표시하고 정확한 위치가 필요한 검토에서 별도로 확인한다. |
| Requirement, RequirementRevision, Review, Approval | 표시용 ID와 영속 내부 ID, 변경마다 본문·유형·분류·우선순위·근거·검증 기준·릴리즈를 갖는 불변 리비전. 추출·AI 제안·적용성·합의·검토·승인·구현 상태를 분리한다. 출처 유형을 구분한다. Derived 유형도 제약/안전 분석 등 명시적 근거가 필요하다. 분해·병합은 식별자와 결정 이력 및 필요한 옛 관계를 유지한다. |
| ArchitectureElement, DesignElement, SoftwareUnit | 시스템·SW·HW 구성, 인터페이스, 할당과 버전, 설계 제약과 검토. 클릭 가능한 구성 다이어그램을 TraceLink로 요구사항과 검증에 이어 준다. |
| VerificationMeasure, VerificationExecution, VerificationResult, EvidenceArtifact | 사양의 리비전·검증 방법·환경·절차·합격 기준을 실행 당시 고정한다. 실행은 릴리즈·Baseline·대상 리비전·실행 ID를 가지며 결과에는 측정값, 판정 근거, 증거 파일과 무결성 해시를 연결한다. 현재 적용 가능성은 과거 실행 판정과 별개다. |
| TraceLink, Baseline | 한 개의 방향과 관계 유형, 출발/대상 객체와 검토한 양끝 리비전, 검토 상태. 양방향 인덱스를 하나의 원장에서 생성한다. Baseline은 객체 리비전, 링크·정합성, 테일러링/정책 버전과 증거 참조를 고정한다. 승인 후 편집 불가이며 변경은 새 Baseline에 기록한다. |
| ChangeRequest, ProblemReport, Risk | ChangeRequest는 영향 후보, 경로, 직접/간접, 담당자 판단, 승인, 재검증에 연결한다. ProblemReport는 실패 실행과 원인·조치·종료 근거를 보관한다. Risk는 연결된 산출물·발생 가능성·영향·대응·잔여 위험을 기록한다. |
| AssessmentEvidence, AssessmentFinding, AuditEvent | 조사 범위와 증거 링크·검토 수준·발견 사항 및 개선 조치를 기록한다. 승인 및 도메인 변경은 행위·대상·리비전·사유·결과의 이력을 남긴다. 별도 평가자 기록은 증거 준비 상태를 갱신하지 않는다. |

### 저장 및 읽기 모델

- **Host에서 변경을 확정한다.** 화면과 에이전트 읽기는 같은 프로젝트 저장 상태에서 계산한다. 업데이트는 예상 리비전과 작업 ID를 보내고, Host는 프로젝트별 쓰기를 직렬화하여 오래된 리비전을 거절한다. 동일 파일 사용자 다중 창을 포함해 충돌을 감지한다. 같은 폴더의 임시 파일로 저장한 다음 안전하게 교체하고 실패 시 직전 저장 팩을 유지한다. 스키마 버전·마이그레이션·백업·재열기로 복구 가능성을 검증한다. 앱 업데이트나 플러그인 재설치 후에도 사용자가 선택한 폴더를 재사용한다.
- **프로젝트마다 범위를 강제한다.** 선택·필터·페이지는 project + release + baseline 기준으로 보관한다. 쓰기·탐색·캐시 모두 projectId 검증을 먼저 수행한다. 파일은 사용자가 고른 위치로 제한하고 정규 경로, 하위 경로 및 심볼릭 링크 우회를 검사한다. 데모 초기화는 사용자 확인 후 데모 팩만 복구하고 다른 파일과 프로젝트 팩을 유지한다.
- **관계 원장은 하나다.** 사실 관계(extractedFrom, derivedFrom, refinedFrom, allocatedTo, realizedBy, verifiedBy, validatedBy, resultOf)와 관리 관계(affectedBy, supersedes 등)의 유형별 허용 객체, 저장 방향, 표시 방향, 영향 전파 조건을 별도 규칙으로 둔다. Explorer, Matrix, Coverage, 영향 분석이 같은 관계와 기대 규칙을 읽는다. 개발 흐름에 따라 링크를 역방향으로 보여주더라도 역방향 행을 추가 저장하지 않는다. 허용된 순환·중복 경로는 방문 집합을 사용하여 제한한다.
- **링크 존재와 정합성을 분리한다.** 규칙 레지스트리는 출처 없음, 근거·전개·검증 방식·실행 없음, 끊어진 참조, 중복 후보, 변경으로 재검토할 링크, 다른 Baseline 실행, 객체 유형 규칙 위반을 검출한다. 중복·내용 충돌은 근거와 함께 검토 후보로 만든다. 내용 정합성은 검토자가 양쪽 리비전을 확인한 결정으로 보존한다. 화면 매트릭스는 기대 대상의 셀만 Missing으로 표시한다. 모든 불연결 셀을 결함으로 계산하지 않는다.
- **영향 분석은 판단을 지원한다.** 변경 리비전에서 프로젝트 전파 규칙으로 순회해 최소 거리(1단계 직접, 이후 간접)와 대표 경로를 기록한다. 같은 대상의 복수 경로를 묶는다. 담당자가 영향 있음·없음·보류와 사유를 선택한다. 과거 실행 결과는 고치지 않고 대상 리비전이 바뀌면 현재 적용 가능성을 다시 확인한다.
- **화면 비용에 상한을 둔다.** 그래프는 선택 항목 기준 기본 2~4단계와 60개 노드, 그룹 펼치기와 별도 목록을 사용한다. 매트릭스는 행·열 각각 가시 영역을 렌더링한다. 릴리즈/프로젝트 범위 변경에 따라 인덱스를 다시 선택하고 PDF 및 대형 증거는 요청 시 불러온다. 목표는 격리 Host에서 두 번째 과제 표시와 관계 필터 전환 p95 300 ms 이내, 1,000개 링크 그래프 최초 표시 p95 1 s 이내(기본 노드 수 제한 내), 100% 확대에서 읽기 가능 및 키보드 탐색이다. 실제 수치는 Phase 4에서 기록한다.

### 수행 상태와 계산 기준

**Not Started**는 작업 접수 전이다. **Ready**는 적용 범위·담당과 입력이 정리되어 착수 가능, **In Progress**는 실행 중, **In Review**는 지정 결과가 검토 대기 상태다. **Blocked**는 장애와 해결 책임을 기록한다. **Completed**는 해당 반복 범위의 종료 조건과 필요한 승인 충족 시 담당자가 기록한다. **Not Applicable**은 적용 제외 사유·승인·유효 릴리즈가 필요하다. 변경 시 Completed를 재검토로 돌릴 수 있으며 다른 프로세스와 과거 스냅샷은 독립적으로 보존한다.

| 화면 지표 | 분모와 판정 |
| --- | --- |
| 산출물 진행률 | 선택한 릴리즈의 계획·적용 산출물 중 현재 리비전이 승인된 수 / 적용 계획 건수. 과제별 합산시 같은 산출물은 한 번만 센다. |
| 요구사항 추적성 커버리지 | 적용된 추적 기대가 하나 이상인 요구사항 중 모든 필수 기대를 만족하는 수 / 평가 대상 요구사항. Missing, 링크 있음·검토 필요, 검토 완료를 별도로 표시한다. |
| 검증 매핑 커버리지 | 검증 대상인 적용 요구사항 중 선택한 범위에서 현재 리비전에 유효한 척도를 하나 이상 매핑한 수 / 적용 검증 대상 요구사항. 매핑과 수행 및 합격은 각각 표시한다. |
| 검증 실행률 및 합격률 | 실행률은 범위 내 동일 버전에 유효한 실행이 하나 이상 있는 고유 척도 / 계획 척도. 합격률은 해당 릴리즈·기준선 기준 별도 환경·실행 선택 규칙으로 집계한 최종 Passed / (Passed + Failed). Blocked, Not Run, Retest Required와 이전 Baseline 결과는 이 합격률의 분모에 들어가지 않는다. |
| 평가 준비 | 충족, 검토 필요, 누락, 제외를 증거 항목별로 집계한다. 0분모는 ‘해당 없음’을 표시한다. 지표가 Capability Level로 환산되는 경로는 두지 않는다. |

## 구현 순서 및 검증 게이트

1. **P0 파일·스코프·관계의 한 흐름.** 두 프로젝트/각 두 릴리즈 데이터 팩, 프로젝트 탭, 포트폴리오, 모든 적용 V-Cycle 라우트, 고객 문서 접수와 원문 앵커, 요구사항 생성·편집·리뷰·승인과 전개, 양방향 탐색, 매트릭스, 아키텍처 조회를 잇는다. Matrix에서 관계를 생성하면 Explorer와 지표가 즉시 갱신되는지 확인한다.
2. **P0 증거·변경·관리의 한 흐름.** 실행 결과와 증거 미리보기, 변경 승인 및 후보 조치, 재검증, Baseline 생성·비교, 문제·리스크·품질의 연결된 기록, 평가 준비 보고서까지 순차 검증한다. 이전 실행과 과거 기준선의 해시는 유지하며 새 리비전 실행을 별도 기록한다. 파일 재열기, 프로젝트 격리와 초기화도 확인한다.
3. **P1 공용 기능.** 공식 읽기 도구와 문서 보고, 별도의 AI 추출·초안 승인을 먼저 검증한다. ReqIF·Git 연동·교차 프로젝트 재사용은 경계와 P0 품질을 확인한 뒤 범위를 확정한다.
4. **Phase 4.** 사용자 설치본 및 자료와 격리된 공식 Host 환경에서 install/validate → 신뢰·활성 → 실제 공개 작업과 실제 화면을 확인한다. 두 테마, 키보드·Reduced Motion, 대량 범위, 원문 양방향, 다대다 링크, 지표 분모, 불변 Baseline, 오류와 취소, 재실행 및 초기화를 A~D 시나리오의 스크린샷·측정으로 남긴다. 계약 발견과 사용자가 승인한 디자인, 단위 검사와 실제 런타임 결과는 각자 증빙한다.
