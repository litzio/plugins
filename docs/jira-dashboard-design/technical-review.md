이 문서는 구현 전 조사·예산이다. 실제 구현에서는 사용자가 공식 설정창의 독립된 URL·PAT 입력을 선택했다. [현재 구현과 검증 기록](implementation.md)

## SDK 적합성

| 기능 | 확인한 공개 경로와 설계 결정 |
| --- | --- |
| React 및 테마 | manifest의 단일 화면에서 Host가 `React`, `ui`, `invoke` 등을 주입하고 글꼴·CSS 토큰을 상속한다. Overview·Issues·Board·Analytics·Saved views는 같은 화면의 내부 탭으로 두어 필터와 캐시를 공유한다. 로컬 TypeScript 소스는 공개 번들 형식과 맞춰 JS/JSX로 출력하는 후보를 두고 첫 격리 Host 검증에서 확정한다. SDK 소스 패키지의 private 표기와 Host가 배포하는 제작 경로를 구분한다. |
| 공용 부품 | `ScreenLayout`, `Button`, `Status`, `Select`, `Toolbar`, `Notice`, `EmptyState`, `ContextMenu`를 사용한다. 공개 DataTable 계약은 행 선택을 제공한다. 서버 정렬·열 너비·밀도·복수 선택이 모두 필요한 이슈 표는 토큰을 쓰는 접근 가능한 전용 표가 필요하다. 공개 Chart는 단일 시리즈 line/bar와 hover·키보드 값 표시를 제공한다. 복수 계열·현황 분포·드릴다운은 화면에서 담당한다. 50행에서 가상 스크롤 효과는 측정 후 판단한다. |
| 설정 및 비밀 저장 | Base URL은 `settingsSchema`, PAT는 `secrets`의 `scope: "connection"`, 연결 검사는 `healthCheck`로 선언한다. Windows Host의 DPAPI CurrentUser, 단일 연결이 공개 계약이다. 설정 변경 때 인스턴스를 교체한다. 연결 검사의 기본 출력은 `{ok,message}`이므로 사용자 표시 이름은 안전한 문구에 담을 수 있다. 비Windows는 보안 저장 미지원으로 표시하고 데모 사용을 제안한다. |
| 네트워크와 수명 | React 화면은 Host 작업을 `invoke`하고 인증 요청은 신뢰된 Node 플러그인 프로세스에서 보낸다. 공개 설정·secret을 activation context에서 받고 `dispose`로 진행 요청·큐·캐시를 정리한다. 일반 RPC는 10초 한계이며 `invoke`의 신호 인자는 공개 계약에서 확인되지 않았다. Jira 요청의 취소 보장은 별도의 검증 항목이다. |
| 영속 저장 | 일반 설정의 영속성은 지원한다. 작업 데이터의 플러그인 전용 저장소 및 화면별 환경설정 저장 API는 공개 계약에서 확인되지 않았다. 화면에는 최근 검색·저장 뷰 진입을 남기되, 저장 범위를 사용자에게 표시한다. 우선 세션 내 동작을 검증하고 재시작 간 보존은 공식 저장 계약이 생기거나 소유자가 파일 기반 대안을 승인하면 제공한다. |
| 명령·알림·컨텍스트 메뉴 | 공개 Host operation 및 CLI 호출, 파일 동작, 항목용 `ui.ContextMenu`가 있다. 화면 내부 키보드 조작과 `Notice`를 사용한다. 범용 Host Command Center 명령·전역 단축키 등록, 전역 Toast 발행은 공개 API에서 확인되지 않았다. |
| 에이전트 연동 | 스키마로 제한한 `assistant:true` 읽기 작업에서 자연어 요청을 프로젝트 범위·필터로 구조화해 검색한다. 결과는 필요한 필드와 건수로 제한한다. 현재 화면 상태를 에이전트에게 자동 전달하거나 에이전트 결과를 열린 탭에 푸시하는 공개 API는 확인되지 않았다. 초기에는 사용자가 선택한 조건·이슈만 명시적으로 전달한다. |
| 파일·워크스페이스·문서 | `pickPath`, `fileActions`, `openDocument`, `saveDocument` 및 `authorDocument`가 있다. 열린 폴더에 선택한 이슈의 Jira 링크와 구조화한 업무 현황을 리치오 문서로 저장하는 기능이 우선 후보다. 공개 operation의 folder scope는 실행 계약에서 아직 미지원이다. 문서·파일 계약을 사용해 다른 플러그인과 결과를 공유할 수 있다. |
| 백그라운드 작업 | 플러그인 프로세스에서 작업을 접수하고 별도 상태 읽기를 제공할 수 있다. 일반 백그라운드 스케줄러, 알림 구독, 플러그인 간 이벤트 버스는 확인되지 않았다. Jira 상태 확인을 위한 별도 주기 작업은 설계에 포함하지 않는다. |

### 인증 경계

- 입력한 Base URL은 HTTP(S) URL로 구문 검사하고 URL 사용자 정보·쿼리·fragment를 거부한다. context path를 유지한다. 실서비스는 HTTPS, 격리된 목업은 루프백 HTTP를 명시적으로 사용한다. Host가 원격이면 주소는 그 Host에서 접근 가능해야 한다.
- PAT는 요청을 보내는 Node에서만 Bearer 헤더에 넣는다. 모든 redirect를 오류로 처리하고 인증을 다른 주소로 전달하는 경로를 두지 않는다. PAT 또는 원본 오류·HTML을 로그, 응답, receipt, 화면 및 비서 문맥으로 전달하지 않는다. Jira Description은 텍스트부터 표시하고 링크를 열 경우 프로토콜과 대상 URL을 검증한다.
- 자동 조회에 앞서 변경된 주소와 이전 PAT의 조합을 차단할 방법을 격리 Host에서 확인해야 한다. 공개 설정과 secret은 각각 저장되며 Origin 결합이나 원자 교체 API는 확인되지 않았다. Base URL 변경 시 이미 저장된 PAT를 다른 origin에 보내지 않는 것이 수락 조건이다. 이 조건에 필요한 플랫폼 지원이 없다면 연결 변경을 차단하고 자격 증명에 origin을 묶는 공개 계약을 제안한다. [리치오 자격 증명 설계][adr] · [Atlassian PAT 안내][pat]

## Docker Jira 실측

기존 WireMock `3.13.2` 컨테이너에 호스트 루프백 포트 `8081`이 연결되어 있었다. 마운트된 Jira fixture가 목표로 하는 호환 기준은 Jira Software 9.12.28이다. Jira의 실제 버전·권한 동작은 실서버에서 확인해야 한다. 테스트 중 Docker Desktop과 기존 Jira 컨테이너를 기동했고 조사가 끝난 뒤 둘을 정지했다. 기존 fixture·컨테이너 설정을 유지했다.

아래는 제품 경로에 단독으로 보낸 로컬 HTTP 요청의 관측값이다. 바이트는 JSON 응답 본문 기준이며 헤더·압축 전송량을 포함하지 않는다. 시간은 단일 측정이고 Jira 운영 성능 목표 산정에는 사용하지 않는다.

| 직접 확인한 요청 | 결과 | 본문 / 경과 |
| --- | --- | ---: |
| `GET /rest/api/2/myself`, 유효한 합성 PAT | 200. 현재 사용자와 식별 키 | 190 B / 159 ms |
| PAT 누락, 또는 잘못된 토큰 | 각각 401 | 각각 55 B / 17 ms |
| `GET /rest/api/2/project` | 200. MOCK, EMPTY 두 프로젝트 | 424 B / 37 ms |
| `assignee = currentUser() ORDER BY updated DESC`, 투영 포함, offset 0, 100 요청 | 200. `total=4`, `maxResults=2`, MOCK-1/2 | 2,351 B / 187 ms |
| 같은 검색, offset 2, 2 요청 | 200. MOCK-6/8. 마지막 페이지 | 2,399 B / 164 ms |
| 고정 프로젝트 검색, 투영 없음 | 200. MOCK 8건, EMPTY 0건 | 12,510 B / 99 ms, 75 B / 70 ms |
| `GET /rest/api/2/issue/MOCK-1` | 200. 설명, 프로젝트, 상태, 유형, 담당자·보고자, 날짜 등 | 1,348 B / 55 ms |
| 없는 이슈 · fixture에 선언된 불완전 JQL | 제품형 404 · 400 | 54 B / 34 ms, 55 B / 27 ms |
| 50건과 표 필드 조합, Count 후보, POST 검색, 사용자 Picker와 Search, 프로젝트 Picker, serverInfo, 댓글, 변경 이력 확장, JQL 메타데이터 | 모두 404 `UNSUPPORTED_REQUEST` | 각각 100 B |

정적 계약은 현재 사용자용 JQL 여섯 종류와 두 고정 프로젝트 검색, 제한된 필드 투영, 합성 403·404·500·지연·빈 검색 시나리오를 제공한다. 이번 조사에서는 시나리오 전환 없이 기본 상태에서 확인했다. 403·429·5xx·`Retry-After` 및 취소는 플러그인 통합 시험 대상이다. 현재 목업으로는 일반 필터, 자동완성, Count, 댓글·첨부·이력의 통합 수락이 막힌다. 목업 확장은 Jira DC 형태의 경로·쿼리·권한 응답을 구현하는 별도 승인이 필요한 작업이다. 동명이인, 빈 값, 여러 페이지, 페이지 상한, 429, 댓글 페이징과 제한된 이력을 포함한 합성 fixture를 우선 보강한다. 플러그인에는 목업 전용 분기를 두지 않는다. ## 기능 동작과 데이터 범위

1. **연결과 검색** — `myself`로 계정과 연결을 확인한다. 프로젝트는 버전별 프로젝트 Picker부터, 사용자는 `user/picker?query=…&maxResults=15`부터 확인한다. `name`, `key`, `displayName`을 분리하며, 설치 버전에서 JQL로 실제 검색할 수 있는 식별자를 확인한다. 동명이인 이름 옆에 로그인 식별자를 노출하고 이니셜을 기본값으로 써 아바타 호출을 절약한다. 필터별 메타데이터는 열었을 때 가져온다.
2. **기본/JQL** — 기본 필터는 프로젝트, 담당자·보고자, 상태·우선순위·유형·라벨, 생성·수정·해결·기한, 키·키워드를 표현한다. 다중 선택과 기간, 정렬은 허용된 필드·연산자와 이스케이프한 값으로 JQL을 생성한다. 날짜 경계와 상대 기한은 Jira 계정의 시간대 기준을 검증한다. 고급 JQL은 사용자가 제출한 식을 서버에서 실행하고 안전한 오류를 편집기에서 보여 준다. 고급 식에 내부 JQL을 문자열로 덧붙여 대시보드 Count를 생성하지 않는다. GET과 긴 JQL의 읽기용 POST는 대상 버전 계약으로 검증한다.
3. **Overview/Analytics** — 프로젝트와 생성일 범위를 공유한다. 최근 수정순 50건을 필드 지정해 읽고 `total`을 전체 지표로 사용한다. 진행 중, 미해결, 기한 초과, 내게 할당은 각각 작은 Count 최대 4회다. 해결은 전체에서 미해결을 빼고 해결률은 해결/전체로 구한다. 0건과 Count 실패는 값 없음 또는 제한 범위로 표시한다. Count는 브라우저가 내려받은 건수를 이용하지 않으며 Data Center에서 정확한 `total`을 실측한 작은 페이지 요청을 사용한다. 서버 지원이 확인되면 무본문 Count를 사용한다. 페이지 조회와 Count 사이에 서버 데이터가 달라질 수 있으므로 단일 시점 값을 보장한다고 표시하지 않는다.
4. **차트와 드릴다운** — 상태·우선순위·유형·담당자·생성/해결 추이는 동일한 최근 수정순 조회분에서 계산한다. 기본 50건, 사용자가 범위를 확장할 때 최대 200건(50건 기준 4페이지)이다. 서버가 더 작게 제한하면 최대 4페이지까지만 읽고 실제 범위를 표시한다. 시안의 200건은 확장된 합성 표본이다. 추이는 해당 생성 코호트에서 표시 기간에 속하는 생성일과 해결일을 각각 센다. 차트 선택 후 서버에서 다시 검색할 때는 전체 조건의 결과임을 표시한다. 임박 목록은 기한순의 작은 별도 쿼리 한 번, 최근 업데이트는 공통 결과로 표시한다. Overdue는 미해결·기한 있음·오늘 이전이다. 진행 중은 Jira 상태 범주, 해결은 resolution 기준이므로 두 지표는 독립적이다.
5. **Issues/Board** — 화면 간 필터와 정렬을 공유한다. 목록은 페이지당 요청 50건에 실제 표시하거나 보드에 필요한 필드만 지정하고, 사용자가 새 열을 켜면 필요한 필드만 현재 페이지에서 갱신한다. 서버 응답의 실제 반환 건수로 다음 offset을 계산하고, 빈 페이지나 `total` 도달 시 중지한다. 보드는 해당 검색 페이지의 필드를 재사용해 상태별로 그룹화한다. 열의 수는 읽은 범위의 건수다. 열에서 캐시된 카드를 먼저 펼치고 추가 Jira 전송은 사용자가 다음 검색 페이지를 요청할 때 한 번 발생한다. 전체 상태 집계나 Jira Agile Board 이름으로 표시하지 않는다. 상태 변경은 읽기 중심 첫 구현의 범위 밖이다.
6. **상세** — 선택 건의 Description·관계·날짜 등만 한 요청으로 가져온다. 댓글 탭은 20건씩, 첨부는 목록만 요청한다. 바이너리는 자동 요청하지 않는다. 이력은 버전별로 응답 크기 상한과 페이지 기능을 확인한다. 상한을 보장할 수 없는 버전에서는 원본 Jira로 연결한다. 하위·연결 이슈는 상세에서 받은 요약을 표시하고 클릭한 대상만 읽는다.

## 호출 예산

정상 무재시도 기준의 Jira REST 전송 횟수다. 화면→Host 호출은 따로 계측한다. 최초 연결 시험에서 받은 계정 응답은 세션에서 재사용한다. 기준 범위는 프로젝트 한 개와 생성일 30일이며, 프로젝트 범위가 아직 없으면 작업 화면에서 고를 때까지 이슈 요청은 0회다.

| 사용자 행동 | Jira 목표 | 구성 |
| --- | ---: | --- |
| 플러그인 최초 실행 | 0–1 | 미설정/데모 0. 기존 연결 확인이 필요하면 `myself` 1. 프로젝트 검색은 선택기 열고 검색할 때 1. |
| Overview 최초 로드 | ≤6 | 공통 50건 1 + Count ≤4 + 임박 목록 1. 최근 업데이트 추가 0. |
| 사용자 자동완성 | 0–1 | 한 번의 안정된 입력당. 2글자, 350ms, 15건. 캐시 적중·동일 진행 요청 0. |
| 검색 조건 변경 | 0–1 | 필터 편집 중 0, 검색 확정 시 현재 페이지 1. 열린 결과 외 위젯 갱신 0. |
| 동일 조건 재실행 | 0 | 1분 TTL 내. TTL 만료 또는 명시적 강제 갱신이면 1. |
| 페이지 이동·서버 정렬 | 0–1 | 캐시 적중 0, 새 페이지/정렬 1. |
| 이슈 상세 열기 | 0–1 | 선택한 이슈 1, 상세 캐시 적중 0. 댓글·첨부·이력 탭은 열 때 각각 ≤1, 이후 페이지는 직접 요청한다. |
| Overview ↔ Issues ↔ Board | 0–1 | 정렬·필드·조건이 같고 데이터가 캐시에 있으면 0. 최초 다른 범위/필드의 결과 1. Overview 자체 최초 집계는 위 최초 로드 예산 적용. |
| Analytics 표본 확장 | ≤3 추가 | 명시적 확장 후에만. 최대 200건, 공통 첫 페이지 포함 최대 4회. |
| 수동 새로 고침 | Overview ≤6 / Issues·Board ≤1 | 현재 화면에서 사용 중인 범위만 갱신. 상세 탭 재요청은 명시적으로 수행한다. |
| 자동 폴링 · 데모 모드 | 0 | 기본 폴링 없음, 데모는 합성 데이터 사용. |

설계 검증 목표는 연결된 정상 50건 테스트에서 목록의 압축 해제 JSON 본문 ≤150 KiB, Count 응답 ≤4 KiB/회, 15건 Picker ≤16 KiB이다. Jira는 필드 내용과 압축을 서버가 제어하므로 초과 시 payload 원인을 기록하고 목록에는 Description·댓글·이력을 제외한다. 수락에서는 시나리오마다 호출·캐시 적중·취소·바이트·응답 시간(p50/p95)을 기록한다. 자동완성 350ms 대기·Host 왕복·Jira 응답과 화면 표시 시간은 따로 기록한다. 50건 이상을 제공할 수 있는 합성 자료를 사용하며 이번 로컬 탐침의 응답 시간을 운영 서버 성능으로 사용하지 않는다.

## 요청 제어와 장애

- Host 메모리에서 연결 세대 + 승인된 origin/context + 계정 + 정규화한 작업 입력으로 키를 구성한다. 자동완성 5분, 메타데이터 30분, 이슈 검색 1분. 개수와 전체 크기가 제한된 캐시와 동일 요청 합치기를 적용한다. 저장된 PAT는 키에 넣지 않고 설정·토큰 변경 및 폐기 때 이전 세대의 큐·캐시·진행 요청을 정리한다.
- 연결당 최대 동시 전송은 3개다. 상세·새 검색을 오래된 집계보다 먼저 처리한다. 화면은 바뀐 요청 ID의 응답을 폐기한다. Host는 `AbortController`로 타임아웃·dispose를 처리하고, 같은 화면의 요청 키를 이용한 별도 취소 작업이 실제로 진행 RPC와 병행되는지 검증한다. 공유 요청은 기다리는 소비자가 없을 때만 끊는다. bridge에서 실행 중 취소를 보장할 수 없으면 새 요청을 대체하고 옛 결과를 버리는 동작과 SDK 개선을 문서화한다.
- Jira per-attempt 타임아웃 기본 4초, 전체 읽기 예산은 8초 이내로 두어 Host RPC의 10초 한계에 여유를 둔다. 일시 연결 실패나 일부 5xx만 최대 1회 backoff+jitter로 재시도한다. 429는 `Retry-After`(초 또는 HTTP 날짜)을 반영해 해당 연결의 다음 전송을 제한한다. 남은 예산과 사용자 동작이 허용할 때만 재시도한다. 400은 JQL 및 입력, 401은 인증 재확인, 403은 권한, 404는 대상·주소·지원 API를 구분해 안내한다. 네트워크 단절 때는 조회 시각과 함께 이전 결과를 표시한다. 인증 실패 뒤에는 민감한 캐시를 숨기고 지운다.
- 진단에는 작업 종류, 상태 코드 그룹, 전송 횟수, 응답 본문 바이트, 대기·응답 시간과 캐시 적중을 담는다. URL, JQL, 사용자 이름, 이슈 제목, 인증 헤더는 진단 데이터에 남기지 않는다.

## 구현 승인 후 수락 기준

사용자는 리치오에서 자신의 Jira를 연결하고, 프로젝트와 기간을 선택해 지표의 범위를 읽고, 기한 초과 이슈를 표로 좁힌다. 같은 필터로 보드를 보고, 동명이인 중 정확한 담당자를 고른 뒤 상세의 댓글과 이력을 필요한 때만 확인한다. 페이지를 새로 열지 않고 작업 맥락을 유지하며, 인증 만료나 일시 장애에서 다음 행동을 알 수 있다.

검증은 공개 SDK 설치·화면·DPAPI 경계, 지원되는 목업 HTTP 통합, 실제 Jira DC 호환성, 승인된 화면의 시각 품질, 성능 실측을 각각 기록한다. 부족한 목업 계약을 먼저 해결하며, 안전한 자격 증명·데이터 저장이 필요한 SDK 개선은 소유자 판단을 받는다. 우선 개선 후보는 origin에 결합된 secret, 플러그인 전용 영속 데이터, `invoke` 취소, 다중 계열·서버 모드 표 부품이다. 현재 시안은 독립 렌더링 결과다.
