# 첫 시도의 교훈 (2026-11-13 ~ 11-16)

이 저장소의 첫 시도는 2026-11-16에 지웠다. 남긴 것은 이 문서뿐이다. 지운 코드, 계약, 표본, 시험 기록은 태그 `archive/2026-11-16-first-attempt`에 그대로 있다.

다시 만들 때 이 문서를 먼저 읽는다. 지운 코드를 되살려 고쳐 쓰지 않는다.

## 무엇이 있었나

세 플러그인이 파일로 이어지는 하나의 흐름이었다.

| 플러그인 | 하는 일 | 규모 |
| --- | --- | --- |
| docling-convert | PDF를 변환 서버로 보내 결과를 받는다 | 화면 14줄, 처리 코드 하나 |
| docling-to-litzio | 변환 결과를 리치오 문서로 만들고 검수한다 | 소스 약 9,000줄, 검사 약 6,400줄, 화면 1,296줄 |
| requirements-extract | 리치오 문서에서 요구사항을 뽑아 연결하고 ReqIF로 내보낸다 | 소스 약 3,300줄, 검사 약 2,000줄 |

사흘 동안 PR 31개가 병합됐다. 변환 결과에서 ReqIF까지 형식상 이어지는 것은 확인했다. 확인한 것은 길이 있다는 사실이고 결과의 품질이 아니다.

## 왜 지웠나: 소유자의 평가

소유자가 직접 써 보고 세 플러그인 모두 받아들이지 않았다. 아래는 소유자의 말을 옮긴 것이다.

**PDF 변환 화면**

- 화면이 복잡하고 난잡하다. 선택지는 많은데 각각이 무엇을 뜻하는지 알 수 없고 내부 값이 그대로 드러나 있다. 버튼이 여기저기 흩어져 있다.
- 경로를 직접 입력하게 한다. 절대 경로와 쪽 수를 사용자가 손으로 넣어야 한다. 사용자가 고르게 하지 않고 입력하게 만드는 것은 받아들일 수 없다.
- 변환이 어떻게 되고 있는지, 서버가 살아 있는지 알 수 없다.
- 플러그인 설정에서 서버 주소를 넣고 연결을 시험해 볼 방법이 없다.

**문서 만들기 화면**

- 무엇을 입력해야 하는지 알 수 없다.
- 여기서도 절대 경로를 입력하게 한다.
- 작업 폴더를 설정 창에서 고르게 한다.

## 다시 만들 때 지킬 것

소유자의 평가에서 나온 요구다. 기능보다 먼저 지킨다.

1. **입력하게 하지 말고 고르게 한다.** 파일과 폴더는 리치오의 고르는 창으로 고른다. 쪽 수처럼 파일에서 알아낼 수 있는 값은 사용자에게 묻지 않는다.
2. **내부 값을 화면에 그대로 내놓지 않는다.** 선택지는 사용자의 말로 쓰고, 대부분의 사용자에게 필요 없는 조정 값은 기본값으로 둔다. 선택지가 많다는 것은 설계가 덜 됐다는 신호다.
3. **지금 무슨 일이 일어나고 있는지 항상 보인다.** 서버가 연결돼 있는지, 작업이 어느 단계인지, 끝났는지 실패했는지가 화면에 있다.
4. **연결 설정은 설정 창에서 하고 그 자리에서 시험할 수 있다.** 주소를 넣고 연결을 확인하는 것까지가 설정이다.
5. **작업할 대상은 설정이 아니라 작업 화면에서 고른다.** 설정에는 환경(서버 주소 같은 것)만 둔다. 이번에 무엇을 처리할지는 설정이 아니다.
6. **화면을 열면 무엇을 해야 하는지 보인다.** 첫 화면에 다음에 할 한 가지가 있다. 안내 문서를 읽어야 쓸 수 있는 화면은 실패다.
7. **화면의 규칙은 리치오의 `DESIGN.md`와 플러그인 화면 계약을 따른다.** 주 버튼은 하나, 조작은 한곳에 모은다.

## 측정으로 확인한 것

- **사람의 부담이 줄지 않았다.** 공개 표본(13쪽) 하나로 실제 비서에게 전 범위 검수를 시켰다. 주입한 오류 6개는 모두 맞게 고쳤고 정상 값은 건드리지 않았다. 그러나 6턴 안에 검수를 끝내지 못했고, 사람이 봐야 할 쪽은 8쪽으로 비서 없이 할 때의 7쪽보다 줄지 않았다. 한 건 한 번의 실행이다.
- **글자 대조의 한계.** 글자를 맞춰 보는 것으로는 제목의 계층, 읽는 순서, 의미를 검사하지 못한다. 그림, 스캔, 도형(표의 테두리 포함)이 있는 쪽은 사람 몫으로 남았다.
- **절차가 비서를 막았다.** 묶음 단위로 짠 검수 절차에는 쪽 전체를 검사하는 방법이 없었고, 비서가 스스로 멈추는 것과 중단 뒤 다시 시작하는 규칙이 충돌했다.
- **큰 문서에서 느렸다.** 13쪽 표본으로만 재면서 만들어서 130쪽 규모에서 쓸 수 없는 구조가 됐다. 고친 뒤에도 화면의 작업 하나가 1초를 넘었고, 그 비용의 절반 이상이 리치오 CLI 호출이었다.
- **사용 절차가 8단계였다.** 쪽별 대조, 표현 규칙의 대표 대조, 상위 연결 분류 같은 단계를 사람이 순서대로 밟아야 했다. 화면 하나에 버튼이 50개였다.

## 만드는 방식에서 틀린 것

- **세 개를 한꺼번에 만들었다.** 뒤의 플러그인이 앞의 플러그인의 출력 형식에 묶여서, 하나를 단순하게 바꾸면 나머지가 깨졌다.
- **써 보지 않고 쌓았다.** 소유자가 자리에 없는 동안 에이전트가 자율로 진행했다. 써 보고 고치는 순환이 없었다.
- **리뷰의 지적을 고칠 때마다 단계와 상태가 늘었다.** 결함 하나를 막으려고 확인 단계 하나를 더하는 식이었다. 그 결과가 8단계 절차다.
- **끝났다는 기준이 형식이었다.** "ReqIF까지 이어진다"를 완료로 삼았고 "소유자가 자기 문서로 써서 일이 줄었다"를 기준으로 삼지 않았다.
- **처음의 교훈을 되풀이했다.** 이 일의 출발점은 수백 쪽을 사람이 하나씩 보는 방식이 피로해서 실패했다는 경험이었다. 그런데 다시 사람이 여러 단계를 확인하는 구조를 만들었다.

## 다시 만들 때의 진행 방식

- 한 번에 플러그인 하나만 만든다. 소유자가 실제 문서로 써 본 뒤에 다음으로 간다.
- 시작하기 전에 그 플러그인이 끝났다고 할 기준을 소유자와 정한다. 기준은 사람이 하는 일로 쓴다.
- 화면부터 정한다. 소유자가 화면에서 무엇을 고르고 무엇을 보는지 먼저 합의하고 그 뒤에 처리 코드를 쓴다.
- 결함을 막으려고 사용자가 밟을 단계를 늘리지 않는다. 단계를 늘려야 한다면 멈추고 소유자에게 묻는다.

## 그동안 리치오에 생긴 것

첫 시도의 화면은 아래가 없을 때 쓰였다. 다시 만들 때는 처음부터 쓴다.

- 화면의 바탕, 여백, 제목은 리치오의 화면 틀이 그린다. 플러그인이 넣지 않는다.
- 파일 고르기: 열린 폴더 안의 모든 종류의 파일과 폴더를 리치오의 창으로 고른다. 확장자로 거를 수 있다.
- 선택 상자, 위험한 동작의 확인 대화상자, 표에서 행 고르기.
- 버튼은 변형을 생략하면 테두리 버튼이다. 채운 버튼은 그 화면의 주된 동작 하나에만 쓴다.
- 표는 내용 폭과 기본 밀도를 쓰고 숫자 열은 오른쪽으로 정렬된다.
- 플러그인 설정 창의 연결 확인.

## 태그에서 꺼내 쓸 수 있는 것

코드는 되살리지 않는다. 아래는 다시 만드는 비용이 커서 필요하면 태그에서 꺼낸다.

- `fixtures/`: 공개 표본과 고정해 둔 변환 결과. 변환 서버의 버전이나 옵션을 바꾸지 않는 한 다시 변환하지 않아도 된다.
- `docling-server/`: 변환 서버의 실행 설정과 준비 안내.
- `plugins/docling-to-litzio/docs/`의 시험 결과 기록.
- `docs/progress.md`의 "플랫폼에 모자란 것" 표. 리치오에 반영되지 않은 항목은 큰 문서에서 읽기와 편집을 여러 번 호출하는 비용 하나다.
