아래는 초기 정책의 실행 기록이다. 손실 정책과 LSR 완료 발급의 최신 결과는 [추가 검증](results-human-policy.md)을 따른다.

2026-11-14. 공개 master `7aa12173d2e4d976e7990d3300aae9bab0609920`을 새 격리 checkout에서 frozen install·production CLI/Editor build했다. 공개 제작 안내(plugin-stage1-v1), DocumentView 공개 SDK 계약, CLI help/scaffold/install/operation만 사용했다. 저장소도 시작 전에 fetch해 HEAD와 origin/master 차이가 0임을 확인했다.

## 실제 확인

- 세 격리 환경 변수(data, assistant cwd, assistant settings)를 모두 지정한 임시 Host. 수동 CLI 설정 없이 context.cli로 LSR 생성 성공: 113블록, 그림 2개, 검수 15묶음. fixtures는 읽기만 했고 변환 서버를 쓰지 않았다.
- 같은 Host의 열린 폴더에서 bundled PDF.js가 실제 PDF 한 쪽만 canvas에 그리고 해당 source의 근거 상자를 표시한다. DocumentView는 현재 공식 inspect/인계의 revision과 경로를 받는다. 위치 변경 시 해당 source 쪽도 변경한다. 셀 선택은 표 전체 강조임을 표시한다.
- LSR 표 4, 수식 52, 문단 40, 미주 113의 현재 경로를 선택했다. 문단 40을 선택하면 PDF가 6쪽으로 바뀌는 것을 확인했다. 미주 113은 5쪽의 원문 정의와 연결되지만 자동 스크롤 한계가 있었다(아래).
- 별도 변환 사본의 두 셀에 999/888 오류를 주입한 뒤 공개 correction-submit으로 원본의 0.12 s/0.22 s를 복원했다. 두 응답은 applied이고 현재 인계/실제 inspect가 검증됐다. 적용 교정 선택은 각각 NodePath 39.1.2 / PDF 6쪽과 45.1.2 / PDF 7쪽을 반환했다. UI의 첫 교정 대조에서도 39.1.2 / 6쪽을 확인했다. 원본 fixture와 PDF는 변경하지 않았다.
- 화면에서 식 (1)의 PDF와 현재 표시의 합 범위·분자·분모를 확인하고 사람 확인을 기록했다. 미주 범위는 보류를 기록했다. 판단은 note/revision과 함께 남고 보류는 완료를 차단한다. 이 기록은 제품의 사람 역할을 검사한 것이며 비서 전수 검수가 아니다.
- NIST도 생성 성공: 407블록, 그림 8개, 검수 9묶음. 첫 묶음 선택부터 실제 DocumentView 강조 표시까지 약 2936ms(한 번 측정, CLI/material 전달과 렌더링 포함). 큰 문서에서도 실제 렌더러가 반응했지만 반복 성능·메모리 수락은 아니다.
- 1440/640 폭을 실제 브라우저로 확인했다. 640에서는 세로 배치이고 body.scrollWidth=innerWidth=640이었다. 각 영역은 480px 내부 스크롤을 가지며 확대 시 PDF 영역 안에서 스크롤한다. 기존 부품과 공개 색/간격 토큰을 사용했다. 캡처는 개인 정보가 있는 앱 탐색기를 제외한 대조 영역이다.

## 검사

격리 CLI 지정 전체 검사: 71개 중 66 통과, 실패 0, corpus 환경 변수가 필요한 기존 탐지 검사 5개 skip. 새 최종 gate/교정 변화 이후 실제 CLI 교정 검사와 완료 검사 14개를 다시 실행해 모두 통과했다. 별도로 최신 완료 검사 2개를 실제 source-built CLI로 실행해 통과했다. 마지막 완료 검사는 작은 합성 Docling/LSR PDF 입력에서 공식 생성→교정→checkpoint/사람 결정→완료 발급→require-reviewed 읽기→재검사/손 편집 무효화를 확인한다. 합성 checkpoint는 실제 전수 검수나 원문 전체 의미 보존의 증거가 아니다.

설치 검증은 최종 작업 선언과 화면 번들에 대해 성공했다. PDF.js의 선택적 Node canvas 경고는 텍스트 추출 검사에서 발생했고 브라우저의 PDF canvas 렌더는 별도로 확인했다. 기존 수식의 KaTeX strict 경고도 관찰했다.

## 끝내지 못한 수락과 플랫폼에 모자란 것

- LSR 차단 손실 29건은 그대로다. 현재 공개 교정은 평문/셀/수식 값 교정만 가능하며 구조 손실을 해소하는 작업이 없다. 사람의 확인으로 면제하지 않았다. 따라서 LSR 전체 완료/완료 인계와 실제 비서 검사 범위 충족은 **미수락**이다. AI는 호출하지 않았다. 200쪽 이상 실사용 수락도 하지 않았다.
- DocumentView의 표 셀 경로는 표 전체 강조라 셀 귀속 대조에는 충분하지 않다. 화면은 이 한계를 표시하며 자체 셀 DOM 강조를 추가하지 않았다.
- 첫 두 수식은 실제 수식이 강조되어 읽혔다. 복합 식 95와 재배치 미주 113은 초기 읽기에서 강조의 세로 위치가 480px 스크롤 영역 아래에 남았다. 미주 사례에서 영역 위쪽부터 강조까지 약 550px 떨어져 있어 바로 보이지 않았다. 위치는 유효하지만 대조용 자동 이동은 충분하지 않다. 수동 스크롤은 가능하다. 내부 선택자/레이아웃에 기대는 제품 우회는 하지 않았다.
- 640으로 폭을 바꾼 뒤에도 이미 읽은 문서의 자동 이동을 다시 보장하지 않는다. 높이 480은 본문과 표 일부를 읽기에 적당하지만 큰 표/수식에는 수동 스크롤이 필요하다. 전체 문서를 실제 렌더링하므로 더 큰 입력의 반응은 별도 측정이 필요하다.
- reloadKey로 새 파일을 읽는 경로는 사용했다. 플러그인은 저장된 문서 bytes의 revision을 주기적으로 확인하고 바뀌면 기존 대조를 제거한 뒤 현재 대응을 다시 검증한다. 수동 편집의 digest 불일치와 완료 무효화는 처리 검사에서 확인했다. 일반 탭의 미저장 변경 감지는 공개 CLI/DocumentView 계약에 없다. 실제 동시 편집 UI 수락은 남았다.
- 확인한 공개 master에는 기존 문서 openDocument/pickPath가 아직 없다. openDocument가 제공되면 사용하도록 연결했고 현재는 비활성/일반 문서 탭 안내다. API를 추측해 호출하지 않았다.
- requirements-extract는 읽기만 했다. 현재 1.2를 거부하며 정식 내보내기 지원은 계약의 소비자 변경이 필요하다.
