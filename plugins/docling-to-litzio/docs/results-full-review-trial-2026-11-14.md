# LSR 전 범위 비서 검수 시험 — 공급자 기억 접근으로 중단

2026-11-14. **전 범위 검수의 유효한 결과를 얻지 못했다.** 실제 비서 1턴을 시작했으나 공급자의 전역 기억 파일을 검색·열람하는 셸 호출을 관찰하고 운영자가 중단했다. 재시도하지 않았고 플러그인·스킬을 고치지 않았다. 이 시험의 결과를 **교정 품질의 보증으로 쓰지 않는다.**

## 절차와 고정 조건

- 시작 전 `git fetch origin master` 후 HEAD와 origin/master가 모두 `34ced140c90be9610b20da796bd4352bb9e387c5`임을 확인했다.
- 공개 리치오 master를 새 임시 하위 checkout에 clone했다. commit은 `ca9675ecf40e0c12c61255d3139f69ac4159a941`. Node 24.22.2 / pnpm 12.5.1, frozen install과 production CLI·Editor build 성공. 빌드의 chunk 크기 경고는 있었다. 공개 안내·CLI만 사용했고 플랫폼 내부 구현을 읽어 우회하지 않았다.
- 플러그인 0.9.0의 변경 없는 사본을 Host 허용 시험 폴더에 설치했다. 첫 설치는 허용 폴더 밖이라는 `outside_plugin_scope`로 거부돼 사본을 허용 폴더 안에 두었다. 제품 결함 수정은 아니다. 설치 running 및 작업 폴더 available=true를 확인했다.
- `LITZIO_DATA_DIR`, `LITZIO_ASSISTANT_CWD`, `LITZIO_ASSISTANT_SETTINGS_FILE`을 모두 자체 임시 하위 폴더로 지정했다. 실제 AI 전 설정 화면에서 비서 작업 폴더가 자체 임시 하위 폴더이고 설치 검수 스킬이 목록에 있음을 확인했다. 대화 UI에서도 Codex gpt-6.1-terra / high / 전체 접근을 확인했다.
- 표본은 저장소 `fixtures/lsr-1.1` 북마크 판의 고정 변환 결과 사본. PDF와 원래 fixture는 변경하지 않았다. 사본 document.json의 셀 text만 바꾸고 사본 변환 기록의 document digest를 갱신했다. 재변환·Docling 서버 호출 없음. 공개 preflight/start/job으로 생성했다.
- 주입 정답표와 준비 스크립트는 비서 작업 폴더와 Host 문서 root 밖에 두었다. 주입판·시험 산출물·원시 대화·캡처는 저장소에 넣지 않는다.

## 비서 진행과 중단

지시는 작업 ID와 함께 “문서의 검수를 끝까지 해 줘. 판단할 수 없는 부분은 남겨 두고 사람이 확인할 것을 알려 줘.”라고 보냈다. 절차와 정답은 지시에 넣지 않았다.

1. 비서가 검수 스킬을 적용하겠다고 말하고 설치된 SKILL.md를 읽었다(셸 1회).
2. 공급자의 전역 기억 파일을 검색했다(셸 1회).
3. 같은 종류의 기억 파일 일부를 열람하면서 Host 환경 확인·플러그인 목록 호출을 시도했다(셸 1회). 비공개 파일의 이름·내용·출력은 여기 옮기지 않는다.
4. 운영자가 전역 기억 접근을 관찰하고 UI 응답 중단을 눌렀다. 중단 직전까지 입력 JSON을 쓰고 review-progress/groups를 조회한 셸 1회도 표시됐다. UI의 ‘중단됨’을 확인했다.

이후 운영자가 공개 review-progress/groups를 읽고 생성 원장·문서 hash를 확인했다. changes와 submissions는 빈 배열이고 pending/completion은 없다. 문서 digest는 생성 revision과 같았다. 사람 근거 경로 사용·문서 직접 수정·근거 없는 채우기의 실행 흔적은 이 짧은 구간에서 없었다. uncertain의 타당성은 제출 자체가 없어 평가하지 못했다. 공급자가 자동으로 만드는 전역 세션·로그까지 무변경인지 전수 확인하지 않았으므로 ‘전역에 아무 변화도 없음’이라고 주장하지 않는다.

## 사람에게 남는 양 — 중단 상태의 계수

실제로 사람 검수를 하거나 사람 판단·표현 확인을 제출하지 않았다. 다음은 중단 후 원장과 report를 읽어 센 양이며, **비서가 검수를 끝낸 후의 잔여량이 아니다.**

| 종류 | 항목 / 묶음 | 원문 쪽 | 해석 |
| --- | --- | --- | --- |
| 판단 불가 | 0 제출 | — | 읽고 판단한 결과 0이 아니라 아직 미처리 |
| 표현 손실 | 29항목 / 10묶음 | 1, 3, 4, 5, 6, 8, 11 | 항목마다 뜻 보존 확인 필요. 10회 대표 확인으로 대체할 수 없음 |
| 수식 | 3개 / 3묶음 | 8, 11 | formula-review-required. 그중 복합식 1개에 suspicion/prose 후보 중복 |
| 병합 표 | 2개 / 2묶음 | 4, 5 | 표현 확인 묶음과 중복 |
| 원본 셀 기록 부재 | 7칸 / 표 2묶음 | 5, 11 | 빈칸·추출 누락·벡터 수식 여부 미판정. 7칸 모두 내용 누락이라고 단정하지 않음 |
| text-layer-unavailable | 9후보 / 1묶음 | 9 | 글자 층 부족 후보이며 내용 누락 확정 아님 |
| 필수 사람 큐 합집합 | 13묶음 | 1, 3, 4, 5, 6, 8, 11 (7쪽) | 위 종류를 단순 합산하지 않음. 큐 밖 셀 부재 등도 따로 남음 |
| 전체 미검사 | 17묶음 + 13쪽 범위 | 전체 13쪽 | 페이지 검사를 완료한 근거 없음 |

화면의 반복 패턴 자료는 3계열(5·2·2묶음)이다. 하지만 현재 화면 코드는 필수 사람 큐를 접기로 숨기지 않는다. 반환된 groups/series와 humanQueue에 그 규칙을 적용하면 기본 접힘 상태에도 **17개 묶음 행**이 남는다. 이는 화면 코드와 실제 반환 자료로 계산한 탐색 수이며 실제 클릭 횟수 실측은 아니다. 필수 사람 큐만 방문해도 최소 13묶음 확인 위치이고, 표현 확인은 별도 29항목 제출이 필요하다. ‘접으면 3번만 확인’으로 줄여 세지 않는다. 사람의 최종 결정·교정·재확인·완료 클릭까지 포함한 총 조작 수는 미측정이다.

필수 큐의 쪽만 보면 7/13쪽(53.8%)이지만 남은 6쪽을 생략해도 된다는 증거가 아니다. 13/13쪽 미검사 상태이므로 전부 보는 것에 비해 실제 사람 부담이 줄었다고 말할 수 없다. 원래 빈 수식 셀의 사람 교정 여부와 내용 누락 확정 수는 이번에 대조하지 않았다.

중단 후 gate는 ready=false, uncovered=30(17묶음+13쪽), human=13, blocking=0, expressionUnconfirmed=29, failures=0, tokenDifferences=6이었다. blocking=0도 표현 보존 확인이나 내용 완전성을 뜻하지 않는다.

## 막힌 곳과 원인 분류

**관측:** 세 리치오 격리 변수를 설정하고 화면 확인까지 했지만 비서가 공급자의 전역 기억을 검색·열람하는 셸 호출 2회를 실행했다. 운영자는 공급자 홈·인증·설정을 변경하지 않았다. 중단 후 오케스트레이터도 재시도하지 말고 중단 결과를 기록하도록 확인했다.

**공개 계약:** [ADR-0014 결정 2](https://github.com/litzio/litzio/blob/ca9675ecf40e0c12c61255d3139f69ac4159a941/docs/adr/0014-main-agent-app-server.md)는 기존 Codex 로그인·설정·지시문·세션 재사용과 별도 CODEX_HOME을 만들지 않는다고 명시한다. [HTTP 실행 안내](https://github.com/litzio/litzio/blob/ca9675ecf40e0c12c61255d3139f69ac4159a941/docs/design/http-host-v1.md)는 빌드 CLI가 설치본과 같은 사용자 기본값을 쓰며 명시적 override가 우선함을 설명한다. [앱 초기화 계약](https://github.com/litzio/litzio/blob/ca9675ecf40e0c12c61255d3139f69ac4159a941/docs/design/app-reset-v1.md)은 리치오 AI 설정·비서 cwd와 공급자 전역 계정을 구분한다. LITZIO_DATA_DIR의 Host 데이터 격리는 같은 HTTP 계약에 명시돼 있다.

**판정:** 세 변수는 리치오 데이터·비서 작업 폴더·비서 설정 격리이며 공급자 홈 격리의 증거가 아니다. 전역 설정·기억이 세션에 적용될 수 있다는 설명은 공개 계약과 이번 관측에 부합한다. 어떤 공급자 설정 또는 지시문이 실제 기억 호출을 유도했는지, 자동 주입된 기억의 전체 범위는 확인하지 않았다. 이를 플러그인 결함이나 모델 판단 품질 실패로 단정하지 않는다.

| 분류 | 이번 결론 |
| --- | --- |
| 플러그인 | 설치·생성·공개 읽기 성공. 전 범위 교정 절차는 미평가 |
| 스킬 | 자발적 읽기 확인. 묶음·쪽 순회 및 재검사 완주 능력은 미평가 |
| 리치오 / 시험 환경 | 공급자 환경 재사용 경계가 공개 fixture 전용 시험 조건과 충돌. 기존 환경 재사용 자체를 플랫폼 구현 결함이라고 단정하지 않음 |
| 모델의 한계 | 판단 품질은 평가 대상 아님. 짧은 실행으로 품질·완주 능력 결론 불가 |

이전 [6묶음 결과 문서](results-assistant-skill.md)와 [측정 JSON](assistant-skill-results.json)에는 공급자 전역 기억 검색·열람 여부가 기록돼 있지 않다. 기존 로그인 환경을 사용한 조건만으로 그때도 읽었다고 추정하지 않는다. **이전 시험에서 같은 일이 있었는지는 확인하지 못함.** 이번 결과로 이전 두 교정의 정오를 뒤집거나 전체 격리 성공을 인정하지 않는다.

## 다음 추천과 재시험 선택지

작은 순서로: 먼저 시험의 공급자 환경 허용 범위를 소유자가 고른다. 다음으로 재시험 기록에 리치오 세 변수 확인과 공급자 홈·기억 정책 확인을 별도 항목으로 둔다. 그 조건이 정해진 뒤에만 같은 고정 표본으로 전 범위 검수를 다시 측정하고, 순회·재검사·사람 큐의 실제 병목을 근거로 수정 범위를 정한다. 이번 PR에는 어떤 수정도 넣지 않는다.

| 선택지 | 조건과 한계 |
| --- | --- |
| 가. 전역 기억 접근을 받아들이고 진행 | 공개 fixture 전용 입력이라는 기존 시험 조건을 소유자가 명시적으로 바꿔야 함. 기존 기억의 영향이 있는 시험임을 기록 |
| 나. 공급자 홈까지 격리 | 별도 환경 구성과 소유자의 로그인 필요. 세 리치오 변수만으로 달성됐다고 간주하지 않음 |
| 다. 공급자 기억 기능을 끈 설정 | 해당 공급자의 지원 방법과 실제 비활성화를 먼저 확인해야 함. 기억 해제만으로 모든 전역 지시문·설정까지 격리된다고 가정하지 않음 |

어느 선택지도 이번에 시도하지 않았다. 공급자의 홈·인증·설정을 건드리지 않았고 소유자 선택은 오케스트레이터에게 넘겼다.

## 정리와 검증 경계

실제 비서 응답의 중단됨을 확인하고 시험 브라우저를 닫았다. 명령줄과 생성한 Host를 대조한 뒤 그 Host 프로세스 트리만 종료했다. 종료 출력에서 공급자 하위 프로세스 종료를 확인했고, 시험 Host와 브라우저 프로세스 없음·시험 포트 listener 0개를 확인했다. 재귀 삭제 명령은 쓰지 않았으며 임시 자료는 보존했다.

저장소 변경은 이 결과 문서 하나다. 다른 플러그인·docs/progress.md·fixtures는 변경하지 않았다. 사용자의 설치된 리치오와 기존 daemon을 조작하지 않았다. 공급자의 전역 기억 접근은 위와 같이 발생했으므로 사용자 환경 완전 격리·공개 자료만 사용한 성공 시험이라고 보고하지 않는다. 제품 코드 변경과 새 단위 검사는 없고, 전체 회귀·소유자 시각 수락도 수행했다고 주장하지 않는다.
