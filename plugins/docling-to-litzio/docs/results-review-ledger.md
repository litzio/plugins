# 검수 계약 명문화와 생산자 원장 성능

2026-11-14. 기준은 plugins master `d52c451`이다. 공개 플랫폼 master `26c902d3c7d329603d31ea02e3af40e891785b9f`를 별도 checkout에서 frozen install 후 CLI·Editor로 빌드했다. 빌드는 성공했으며 Editor chunk 크기 경고가 있었다. 플랫폼 내부 구현에 의존하지 않는다.

## 범위와 원인

계약의 lossId 직렬화·분류 정책·basis 문자열과 scopes/humanDecisions 필드를 [계산 규칙](../../../contracts/docling-to-litzio/review-values.md) 및 정본 schema에 명시했다. 기존 생산자의 의미를 고정했으므로 v1.2를 유지한다. 소비자 변경은 없다. 다른 플러그인의 파일도 변경하지 않았다.

보고된 8.6MB checkpoint의 원인과 생산자 비용은 구분해야 한다. 읽기 조사에서 requirements-extract의 loadLedger가 번호 checkpoint 파일 전부를 읽고 매번 canonical state 전체의 hash 사슬을 재검증하며, publish가 checkpoint마다 state 전체를 저장하는 것을 확인했다. 이는 이번에 수정할 수 없는 소비자 코드다. 해당 증상 전체를 해결했다고 주장하지 않는다.

원래 보고의 8.6MB 파일은 제공받지 않아 직접 계수하지 않았다. 위 소비자 구현이 보고된 동작과 일치한다는 정적 근거이며 동일한 원본 실행의 파일을 재현했다고 주장하지 않는다.

docling-to-litzio는 가변 correction-ledger와 correction-history를 사용하며 각 고리마다 PDF 증거나 snapshot 전문을 저장하지 않는다. 이 파일들은 인계 계약 대상이므로 참조 파일로 치환하지 않았다. 다음 중복을 줄였다.

- readReview가 이미 검증한 현재 인계를 같은 작업의 material·진행·표현 확인·완료 판정에서 다시 loadHandoff하지 않는다. 표현 확인은 같은 작업의 material에도 그 검증 결과를 전달한다.
- loadHandoff는 이번 호출에서 digest를 확인한 bytes를 완료 검증에도 쓴다. 마지막 원장·완료 표지 bytes 재읽기는 그대로다.
- 모든 고리를 여전히 검증하되, 사슬 재생은 처음 복사한 전용 snapshot 하나에 순서대로 투영한다. 고리마다 전체 snapshot을 다시 복사하지 않는다. 외부 projectEdit의 불변 입력 규칙은 유지한다.

지속 캐시는 없다. 재사용 수명은 함수 호출 하나이며 다음 작업은 전체 인계를 새로 읽는다. 쓰기 이후 publish/finalize의 인계 검증도 새로 실행한다. C0–C9·교정 근거·receipt·역연산·전체 snapshot 비교와 무효화 규칙은 유지한다. 과거 파일 전체를 일관되게 위조하는 공격까지 막는 서명은 이번에도 추가하지 않는다.

## 측정 절차

[재현 스크립트](../test/measure-ledger.js)의 prepare → measure를 사용한다. 고정 LSR JSON/PDF 사본과 이를 10회 연결한 130쪽 합성본을 새 폴더에서 생성한다. PDF 페이지 복사와 Docling 참조/쪽 번호 이동만 하며 fixtures는 읽기만 한다. PDF 복사에는 pypdf 6.14.2를 썼다. 복사 PDF에는 북마크가 없으므로 과거 원본 PDF 시험의 묶음 수와 직접 비교하지 않는다.

문서 생성은 새로 빌드한 공식 CLI다. 측정 구간의 편집/inspect/check는 결정적인 메모리 편집기로 대체해 CLI 프로세스 시작 비용과 분리한다. 첫 교정은 실제 생산자 submit으로 실행한다. 130쪽에서는 나머지 아홉 고리를 동일한 전후/근거/receipt 구조로 합성하고, 나머지 범위·사람·표현 기록도 명시적인 시험 선언으로 준비한다. 이어 모든 고리를 생산 reader로 재검증한다. 각 작업 표본은 교정 제출 1회, 사람/표현 결정·checkpoint 각각 2회, 진행/인계 조회 각각 3회, 완료 발급 1회다. 제출 측정은 사슬 누적 전 첫 교정이며 나머지는 1/10고리가 누적된 상태다. 전체 검수 시간이나 실제 사람·AI 품질의 측정이 아니다.

동일 준비본 두 사본에 변경 전/후 코드를 순서대로 실행한다. 시간은 벽시계 ms이며 적은 표본의 산술 평균이다. I/O는 프로세스 내 readFile/writeFile의 호출 수와 bytes를 계수한다. lstat·rename·잠금 handle 쓰기·외부 프로세스 I/O는 계수하지 않는다. OS 파일 캐시는 비우지 않았다. 원시 계수에는 파일별 읽기/쓰기 횟수와 bytes를 함께 남긴다.

재현에는 빈 작업 하위 폴더와 DOCLING_TEST_CLI가 필요하다. CLI 실행 환경의 LITZIO_DATA_DIR, LITZIO_ASSISTANT_CWD, LITZIO_ASSISTANT_SETTINGS_FILE, LITZIO_DAEMON_DIR, LITZIO_PLUGINS_SETTINGS_FILE을 모두 자기 시험 하위 폴더로 지정한다. prepare의 생성 CLI는 앞 세 값을 출력 하위 폴더로 덮어쓴다. 임시 최상위에서 npm init/install하지 않는다.

모든 측정 작업은 오류 없이 끝났고 두 크기 모두 완료 발급에 성공했다. 파일 크기는 같으며 저장 형식과 중복 인계 기록을 바꾸지 않았다. 현재 원장의 작은 checkpoint 쓰기는 전체 인계 검증을 하지 않지만, 재개 상태일 때의 관련 무효화와 완료 시 전체 재검증은 유지한다.

130쪽에서도 개선 뒤 수 초의 지연과 비선형 증가가 남는다. 전체 source/native 및 검수 대상 대조의 반복 선형 탐색, 큰 schema 검증 등은 여전히 비용이다. 따라서 수백 쪽 사용성 합격이나 보고된 소비자 checkpoint 문제의 해결로 판정하지 않는다. 다음 범위 결정에는 소비자 원장 자체의 별도 성능 작업과 생산자 전체 대조의 추가 프로파일링이 필요하다.

130쪽의 human-decision과 handoff 시간은 오히려 늘었다. 변경하지 않은 경로도 변동했고, 같은 머신의 다른 Node 프로세스 부하를 통제하지 않았으므로 시간 차이를 전부 코드 효과로 귀속하지 않는다. 작업별 읽기 횟수/bytes 감소는 계수로 직접 확인했지만 균일한 속도 개선이나 응답 시간 보장은 입증하지 못했다.

## 검증과 한계

최신 source-built CLI를 지정한 전체 검사: 136개 중 131 통과, 5 corpus 환경 skip, 실패 0. 기존 C0–C9 변형·무효화 회귀를 유지했고, 계약 bytes 예시·닫힌 정책/필드·100고리 replay의 중간/마지막 손상 및 입력 불변 검사를 추가했다. 변경 전 코드가 발급한 v1.2 완료 묶음도 새 reader의 requireReviewed에서 수락했다.

최종 schema의 basis enum을 닫은 뒤 완료/사람 검수 관련 63개도 전부 통과했다. 13/130쪽 모두 변경 전·후 묶음을 새 reader의 requireReviewed로 재검증하고 현재 snapshot 및 provenance 전체가 서로 같음을 확인했다.

설치·Host 화면·실제 AI·Docling 서버·재변환은 실행하지 않았다. 수백 쪽 실사용 수락이나 의미 품질 보증이 아니다. 직접 시작한 빌드·검사·측정·재검증 프로세스의 종료를 확인했다. docs/progress.md는 수정하지 않으며 전달안은 PR 본문에 둔다.
