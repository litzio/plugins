# PDF 가져오기

글자 층이 있는 PDF를 리치오 문서로 만들고, 원본 쪽과 저장된 문서를 나란히 봅니다. 변환 서버와 AI 모델은 쓰지 않습니다.

## 설치와 사용

**필요한 Host는 SDK 0.12.0과 [litzio#1901](https://github.com/litzio/litzio/pull/1901)을 포함한 리치오(17b8ee03 이후)입니다.** 변환한 문서는 공개 `ui.ItemList`로 표시합니다. 대조 화면에는 공개 ContextMenu·Select hideLabel과 DocumentView의 스크롤·클릭·배치 보고·scale·`target.top`을 사용합니다. 플러그인 선언에는 최소 SDK 버전 필드가 없습니다.

**GitHub에서 설치(리치오 litzio#1770 이후):** 설정 → 플러그인 → **GitHub에서 추가…**에 `https://github.com/litzio/plugins`를 넣고 PDF 가져오기를 고릅니다. 정식 Release가 있으면 Release를, 없으면 브랜치를 따라갑니다. CLI는 `litzio plugins install https://github.com/litzio/plugins/tree/master/plugins/pdf-import --host <Host 주소> --json`입니다. 리치오가 받은 폴더에서 `npm ci --ignore-scripts --omit=optional`을 실행하므로 PC에 npm이 없어도 됩니다. 버전은 `litzio-plugin.json`의 `version`이고, `repository`가 있어 로컬 폴더로 설치해도 업데이트 확인은 이 저장소 기준입니다.

**로컬 폴더에서 설치:** Node 24 환경에서 이 폴더의 `npm ci --omit=optional`를 실행합니다. `node prepare.mjs`는 고정된 pdf.js worker 문자열을 다시 만듭니다. 공식 CLI에서 대상 Host를 명시하여 `litzio plugins install <이 폴더> --host <Host 주소> --json`으로 설치합니다.

PDF가 든 폴더를 리치오에서 열고 **PDF 가져오기 → PDF 고르기**로 파일을 고릅니다. 다음은 전체 폭의 **뺄 쪽 고르기** 격자입니다. 격자는 제외 제안을 기다리지 않고 열립니다. 제안이 도착하면 직접 바꾸지 않은 쪽에만 적용합니다. 누르거나 Shift 범위로 바꾼 쪽은 사용자의 선택을 유지합니다. 제안 확인 중에도 변환을 누르면 그때 고른 대로 진행합니다. 이전 파일의 저장된 제외 선택은 바로 적용합니다. 128px 미리 보기를 누르면 포함·제외가 바뀌고 Shift로 범위를 고릅니다. 키보드 Enter·Space와 Shift도 같습니다. 쪽 번호 아래에는 그 쪽의 첫 책갈피 제목을 한 줄로 표시하며 hover·focus로 전체 제목을 확인합니다. 책갈피가 없으면 번호만 표시합니다. **취소**는 파일을 고르기 전으로 돌아갑니다.

미리 보기에 hover·focus하면 **크게 보기** 아이콘이 보입니다. 크게 보는 동안 이전·다음 쪽 버튼이나 좌우 화살표로 넘기고 포함·제외를 바꿀 수 있습니다. Esc나 닫기로 원래 격자 위치와 focus에 돌아옵니다. 범위 조작 설명은 격자 상태 글의 hover·focus에, 큰 쪽의 단축키는 해당 버튼의 hover·focus에 표시합니다. 공개 화면 부품에 일반 Dialog·Popover가 없어 격자 자리를 큰 쪽으로 바꾸는 방식을 씁니다.

**변환**을 누르면 PDF 폴더 아래 PDF 이름의 폴더를 만들고 그 안에 같은 이름의 `.md`와 `.pdf-source.json` 대응 자료, `assets/`의 그림을 만들고 원본과 저장본을 나란히 보는 **대조 화면**으로 갑니다. 대조 화면에는 쪽 고르기 조작이 없습니다. 머리 줄은 변환 경고가 붙은 블록 수를 표시합니다. 도구 줄의 **변환 경고** 옆 이전·다음은 같은 블록을 순회하며 현재 번호와 이유는 그 아래 한 줄에 표시합니다. 머리 줄에는 PDF 고르기·다시 변환·문서 열기와 검토 상태 버튼을 둡니다. 원본 상자를 누르면 문서 블록을 강조하고 누른 상자와 같은 높이에 둡니다(아래 "누른 블록의 짝 맞추기"). 함께 스크롤은 기본으로 켜져 있으며 양방향으로 동작합니다. 원본 스크롤이 멈추면 강조 없이 문서가 따라오고, 문서를 스크롤하면 맨 위에 보이는 블록의 원본 상자가 왼쪽 높이의 1/3 지점에 옵니다. 최근 휠·스크롤바·스크롤 키 입력을 받은 칸이 주인이며 반대쪽의 늦은 보고는 무시합니다. 함께 스크롤을 끄면 양쪽 모두 따라가지 않습니다. 오른쪽 블록을 누르면 원본의 같은 블록이 선택되어 그 블록과 같은 높이로 오고 해당 동작 줄과 강조가 표시됩니다. 이 누르기는 함께 스크롤을 꺼도 동작하며 문서를 다시 읽지 않아 더블클릭한 글자 선택을 유지합니다. 원본 대응이 없는 블록은 스크롤 때 가장 가까운 앞 대응을 쓰고 누르기는 무시합니다. 문서가 바뀌었거나 고치는 중이면 보고를 무시합니다. 따라가는 블록은 왼쪽 분류 막대의 색으로 표시합니다. 선택과 올림에는 리치오 편집기의 블록 윤곽을 씁니다. 제목은 H1~H6, 목록은 변환 결과에 2 이상 단계가 있을 때 여백에 단계를 표시합니다. 문서 열기는 일반 탭을 엽니다.

PDF 읽기, 구조 분석, 그림 만들기, 문서 저장, 원본 연결 만들기 중 실패한 단계가 상태 줄에 표시되며 자세한 원인은 오류 영역에 나옵니다. 문서 저장 뒤 원본 연결 만들기에 실패하거나, PDF를 고를 때 결과 폴더에 문서만 있고 대응 자료가 없으면 **문서 열기**와 **다시 변환**을 사용할 수 있습니다. 다시 변환을 확인하고 쪽을 고르면 이전 문서를 복구용으로 옮긴 뒤 새 문서와 대응 자료를 만듭니다. 이전 그림은 소유 기록이 없으면 보존합니다.

첫 화면에서 **PDF 고르기**로 변환을 시작하거나 **변환한 문서** 목록의 줄을 골라 저장본을 엽니다. 대조 화면 머리 왼쪽의 **변환한 문서**를 누르면 같은 탭에서 방금 갱신된 목록으로 돌아갑니다. 대조 화면에서도 **PDF 고르기**를 사용할 수 있습니다. 목록에 여러 검토 상태가 있으면 검토 중, 초안, 검토 완료 순서로 묶이며 각 묶음을 접고 펼 수 있습니다. 묶음 안에서는 최근에 변환한 결과가 위에 오고, 검토 완료 문서의 변환 경고 수는 숨깁니다. 변환한 때는 다시 열기, 교정, 검토 상태 변경 뒤에도 유지되며 다시 변환하면 갱신됩니다. 변환 시각을 기록하기 전에 저장한 결과는 대응 자료 파일의 수정 시각을 표시합니다. 목록은 이 브라우저가 Host별로 기억한 최근 10개 PDF 폴더의 바로 아래 PDF별 폴더의 대응 자료를 읽습니다. 폴더 하나가 목록 한 항목이며 더 깊은 폴더는 찾지 않습니다. 원본이 없거나 바뀌면 상태를 표시하고 자동 변환하지 않습니다. 같은 이름은 폴더 이름 하나로 구분합니다. 새 PC나 브라우저 자료를 지운 뒤에는 그 폴더에서 PDF를 한 번 고르기 전까지 목록이 비어 있습니다. 공개 계약에 현재 열린 폴더를 조회하는 기능이 없어 최근 폴더 방식을 사용합니다.

[변환 경고를 표시한 대조 화면](test/captures/first-use/after-warning-1440-light.png)과 [변환한 때를 표시한 목록](test/captures/converted-time/list-1440-light.png)을 볼 수 있습니다.

제외한 쪽은 흐린 원본 위에 반투명 대각선 **제외** 글자와 위험색 테두리로 표시합니다. 대상 정보에는 떨어진 제외 범위도 표시하며 다섯 구간을 넘으면 개수만 표시합니다. 제외 목록은 대응 자료에 보관합니다.

변환한 문서 목록에서 저장본을 열면 바로 대조 화면으로 갑니다. PDF 고르기로 이전 파일을 고르면 그때 저장한 제외 선택이 적용된 격자로 갑니다. 대조 화면의 다시 변환은 확인 후 같은 선택의 격자로 돌아갑니다. 변환을 실행할 때 기존 문서와 대응 자료를 같은 결과 폴더의 `previous` 복구용 사본으로 옮기고 새 문서를 만듭니다. 새 저장과 대응 검증이 끝나면 복구 사본과 쓰이지 않는 이전 그림을 정리합니다. 실패하면 복구 사본을 남기며 자동 복구는 하지 않습니다. 격자를 취소하면 기존 저장본은 바뀌지 않습니다. 그림은 생성 당시 기록한 이름·SHA-256이 일치하는 파일만 지웁니다. 사용자가 수정한 그림과 다른 파일은 보존하며, 결과 폴더에 다른 문서가 있으면 공유 가능성이 있어 이전 그림도 보존합니다. 문서를 고쳤으면 대응 이동을 막습니다. 대응 자료를 잃은 기존 문서는 자동 덮어쓰지 않습니다.

짝이 맞는 각주는 공식 미주로 저장합니다. 동일 번호의 정의가 여러 개면 모호한 호출과 모든 정의를 글자로 보존하고 각주 짝 경고를 붙입니다. 정의 없는 표시는 `[n]` 글자로, 표시 없는 정의는 해당 쪽의 문단으로 보존하고 경고합니다. 괘선 표는 글자 표로, 믿을 수 없는 표와 그림은 원본 영역 PNG로 저장합니다. 캡션은 각 작성 블록의 공식 캡션을 사용합니다. 같은 종류의 번호 캡션이 붙은 그림·표는 원문 번호를 고정 번호로 가지며 본문의 같은 번호 참조가 리치오 참조가 됩니다(아래 "그림·표 참조"). 인식할 영역이 없는 독립 캡션은 문단으로 남습니다. 캡션은 Table/Figure 번호 뒤의 줄표·하이픈·마침표·쌍점을 인식하며, 보통 글자는 같은 쪽의 인접 영역이 있어야 합니다. Figure 아래 작은 글자의 축 줄만 사이에 있으면 영역을 아래로 넓혀 PNG에 포함합니다. 본문 크기의 줄을 넘어서 연결하지 않습니다.

글자 표의 주석은 표 바로 뒤에 설명마다 한 문단으로 둡니다. 한 글자 표시는 위첨자로 보존하며, 같은 표시가 표 칸이나 캡션에서 작은 글자로 올라가 있으면 그곳도 위첨자로 둡니다. 표 밖 문단은 표와 가까이 이어지고 표시의 순서·작은 글자·표의 위첨자 중 하나가 확인될 때만 주석으로 인식합니다. 다른 표의 주석이 섞인 경우는 남아 있습니다.

쓰는 pdf.js 기능과 쓰지 않는 기능의 판단은 [pdf.js 기능 장부](docs/pdfjs-features.md)에 있다. `node pdfjs-probe.mjs <PDF>`는 PDF에 어떤 신호(태그 구조, 링크, 쪽 표시 번호, 레이어 등)가 있는지 개수만 출력한다.

수식 그림을 LaTeX로 바꾸는 로컬 모델 조사(판단 보류)는 [수식 OCR 조사](docs/formula-ocr-research.md)에 있다.

변환 중에는 구조 분석·그림 만들기·문서 저장·원본 연결 단계를 표시합니다. 뺀 쪽이 있으면 머리에서 전체 쪽 수와 포함한 쪽 수를 보여 줍니다. 다시 변환할 때는 이전 문서 정리 단계가 앞에 추가됩니다. 실패하면 해당 단계와 오류를 표시하고 기존 복구 동작을 제공합니다.

## 확인 범위

표 주석은 격리 HTTP Host에서 공개 표본을 변환해 표시와 문단 분리를 확인하고, 인접 설명의 합치기·나누기·되돌리기를 실행했습니다. [변경 전](test/captures/table-notes/before-1440.png)과 [변경 후](test/captures/table-notes/after-1440.png)는 같은 공개 표본입니다. 별도 큰 디지털 PDF에서 주석 표시 20곳을 원본과 대조하고 저장본을 공식 CLI로 다시 읽었습니다.

변환 단계 화면은 격리 HTTP Host에서 공개 표본의 첫 변환과 다시 변환, 그림 진행, 완료 후 대조 화면을 확인했습니다. 640px 어두운 화면의 구조 분석 실패 안내도 확인했습니다. 그림 저장 위치를 파일로 막은 시험에서 실패했으나 실패 원인은 확정하지 못했습니다. 공개 캡처는 `test/captures/conversion-steps/`에 있습니다.

`npm test`는 리치오 없이 공개 LSR 표본의 제목·글자 분류·제외·쪽 간 문단·결과 형태, 쪽 제외 제안과 선택한 쪽의 글자·그림 제외, 짝 없는 표시, 영역 합치기와 각주 공백 보존, 캡션과 축 포함, 같은 크기 각주 번호·쪽 간 짝 맞추기, 최근 폴더 목록의 원본 변경·삭제를 검사합니다. 실제 격리 HTTP Host에서 공개 표본과 별도 큰 디지털 PDF의 선택·변환·저장·강조·전체 스크롤을 확인했습니다. 저장본 재사용, 확인 후 이전 사본 보관, revision 변경 시 이동 차단, 640px 안내와 밝고 어두운 테마를 확인했습니다. 공개 표본 캡처는 `test/captures/`에 있습니다.

OCR, 스캔 PDF, 글자 교정, 옵션과 설정 화면은 없습니다. 패키징된 Desktop, 다른 OS·폰트·회전/세로쓰기 PDF, 변환 중 종료 뒤 복구는 검증하지 않았습니다. 같은 쪽에서 크게 겹치는 영역은 읽기 순서와 무관하게 하나로 합치고, 그 밖의 연속 도형은 본문·제목·캡션·각주가 경계가 됩니다. 공개 표본에는 영역 밖 축 글자의 본문 혼입, 옆에 놓인 표의 합침, 수식 도형과 본문의 분리, 작은 글자 본문의 각주 포함은 큰 줄 간격을 경계로 고쳤습니다. 여러 단 이름 목록과 나란한 표의 주석 합침은 남아 있습니다. 원문 각주 번호와 리치오가 표시하는 미주 번호는 다를 수 있습니다. 저장본을 불러올 때 revision을 확인하고 이후 stale-target 알림이 오면 이동을 막습니다.

직접 의존성은 Apache-2.0의 `pdfjs-dist` 6.5.438 하나입니다. pdf.js worker와 `PDFJS-LICENSE`는 같은 배포물에서 가져옵니다. 스크립팅은 계속 끕니다. `npm audit`에서 취약점 0건을 확인했습니다.

`npm ci --omit=optional` 설치 상태에서 추출과 검사를 실행했습니다. 선택적 canvas와 그리기 전역에 관한 pdf.js 경고는 나지만 글자·도형 추출에 사용되지 않아 전역 대체는 추가하지 않았습니다.

`node measure.mjs <PDF>`는 문서를 저장하지 않고 추출·규칙을 실행해 제목·각주·캡션 등의 검증 통계를 JSON으로 출력합니다. 저작권 입력의 통계와 내용은 저장소 밖에서만 보관합니다.

이번 화면 변경은 격리 HTTP Host에서 공개 표본의 쪽 선택·Shift 범위·키보드 선택·재변환 확인·목록 재열기와 경고 필터를 확인했습니다. 각주 정의가 든 쪽을 제외한 경우도 통합된 각주 짝 판정을 사용합니다. DocumentView의 공개 경로 보고와 target을 사용하며 내부 에디터나 스크롤 DOM에 접근하지 않습니다.

## 문단과 목록 판정

본문 크기(±0.6pt) 글자들의 기준선으로 줄 간격을 잽니다. 쪽마다 긴 본문 줄의 오른쪽 끝 90백분위수를 구하고 1.25em 이내를 가득 찬 줄로 봅니다. 그 비율이 45% 이상이면 양끝 맞춤으로 판정합니다. 평소 기준선 간격의 1.45배를 넘는 간격, 0.7em을 넘는 들여쓰기 변화는 문단을 나눕니다. 양끝 맞춤에서 짧은 줄은 문단을 끝내며 줄 끝 하이픈은 이어짐의 보조 신호입니다. 겹치는 문자 조각의 기존 조립은 유지합니다. 쪽 끝의 가득 찬 줄은 다음 쪽 본문과 잇고, 신호가 어긋날 때만 `paragraph-boundary` 경고와 이유를 남깁니다. 소문자 시작 자체는 경고가 아니며 `용어: 설명`도 정상입니다.

목록은 기호·순서 표시와 내어쓰기 위치를 보존하며, 같은 높이에 떨어진 표시와 본문을 합칩니다. 변환 블록의 `marker`, `level`, `contentX`에 표시와 단계를 담습니다. 공식 작성 입력의 순서 목록(style/start/delimiter)과 중첩 목록을 사용합니다. `(a)`처럼 지원하지 않는 표시는 글머리 목록 항목 글자에 그대로 둡니다. 연속 목록을 묶은 경우 각 원본 항목은 저장된 최상위 목록 경로에 대응합니다. 단독 `i)`는 뒤의 `ii)`가 없으면 영문자로 해석하는 모호성이 남습니다.

`node compare-paragraphs.mjs <PDF 또는 변환 결과 JSON> <비교 자료 JSON> [첫 쪽]`은 개발용 경계 비교입니다. 비교 자료는 Docling의 texts 또는 공개 표본의 elements를 받습니다. 영문자·숫자로 정규화한 25자 이상 문단·목록의 앞뒤 22자를 같은 쪽 ±1에서 비교합니다. 목록 표시는 새 변환 블록의 marker로 본문에서 분리하며, 비교 자료에서 여러 쪽에 반복되는 머리글을 제외합니다. 원문과 비교 자료는 포함하지 않습니다.

공개 LSR 정답의 문단·목록 부분을 CC0 표본으로 두고 경계를 검사합니다. 이 표본은 가득 찬 줄 약 33%의 오른쪽이 들쭉날쭉한 문서입니다. 경계 비교는 각주 뒤 본문 두 개를 분리하여 33/46에서 35/48이 되었으며, 기존의 영역·수식·쪽을 넘는 정답 단위 차이도 분모에 남습니다. 이름만 배치한 명부를 표시가 있는 목록으로 추정하지 않습니다. 큰 PDF와 공개 표본은 격리 HTTP Host에서 목록을 포함한 문서 저장 및 대응 자료 생성을 확인했습니다. 다단 본문과 임의 순서 표시를 폭넓게 검증한 것은 아닙니다.

각주 짝은 블록 조립 뒤 실제 저장 대상의 문단·목록·제목·번호 없는 제목 후보·캡션 전체에서 다시 셉니다. 작성 계획도 전달받은 블록 목록으로 재판정하므로, 정의가 제거된 표시는 `[n]` 글자와 각주 짝 불일치 경고로 남습니다. 참조가 없어진 정의는 원래 위치의 문단으로 남습니다. 완성된 작성 입력의 중첩 목록·그림 캡션까지 순회해 같은 입력 안에 정의가 없는 미주 호출이 있으면 번호를 담은 오류로 저장 전에 중단합니다. 공개 표본에서 정의 블록을 제거한 경우와 입력 간에만 정의가 존재하는 경우를 검사합니다. 통합한 쪽 제외 화면에서 각주 정의가 든 쪽을 제외한 뒤 저장하고, 남은 호출이 글자와 경고로 보존되는 것도 확인했습니다.

## 대조 화면에서 고치기

원본 상자를 누르고 Shift로 범위를 고릅니다. 고칠 수 있는 원본 상자의 우클릭·Shift+F10·메뉴 키는 공통 ContextMenu를 엽니다. 선택 안에서 열면 여러 선택을 유지하고, 선택 밖에서 열면 그 블록 하나로 바뀝니다. 메뉴와 도구 줄은 같은 조건·이유·동작을 쓰며 쓸 수 없는 항목의 이유는 hover·focus로 보입니다. 메뉴의 종류는 본문으로·제목 1~6으로·문서 제목으로 나열하고 같은 종류는 비활성입니다. 표·그림·제외 상자에는 메뉴가 없고 고치는 중이나 대응이 바뀌면 열리지 않습니다. 메뉴를 닫거나 실행하면 원본 상자로 focus가 돌아오며, 뺀 상자는 다음 대응 상자로 옮깁니다. 동작 줄의 **합치기**는 이웃한 본문, 또는 같은 종류(번호 목록끼리, 기호 목록끼리)의 이웃한 목록 둘 이상을 하나로 합치고, **나누기**는 본문 하나의 둘째 원본 줄부터 처리합니다. **종류**에서 본문·제목 1~6·문서 제목을 고르고 **문서에서 빼기**로 본문·제목·목록을 제외합니다. 표·그림 영역, 목록 항목·캡션으로의 변환은 지원하지 않습니다. 목록을 합치면 뒤 목록의 항목이 첫 목록 뒤에 붙고 번호 모양과 시작 번호는 첫 목록을 따릅니다. 합친 목록이 100항목을 넘으면 합치지 않습니다. 알림 상자(참고)는 고칠 수 없습니다. 공개 SDK에 알림 상자를 본문으로 바꾸거나 다시 넣는 연산이 없어 본문으로 되돌리기·빼기의 되돌리기를 만들 수 없기 때문이며 문서 탭에서 고칩니다. 목록 여러 항목이 같은 문서 블록에 묶였으면 개별 항목을 빼지 않습니다. Esc는 줄 선택을 취소합니다. **되돌리기**는 이 화면의 직전 동작부터 복원합니다. 각주 호출이 든 블록을 빼면 정의가 사라질 수 있고 공식 SDK에 원래 표지를 지정한 정의 복원 연산이 없어 확인 후 처리하며 되돌리기 기록을 비웁니다.

대응 자료의 줄 자료·문서 종류·고친 표시와 이력은 저장됩니다. 옛 위치와 옛 형식의 결과는 지원하지 않습니다. 같은 프로세스의 공식 SDK `readDocument`로 문서와 revision을 읽고, Core 연산을 적용한 뒤 `writeDocument`로 한 번 저장합니다. 사전 revision·블록 수·종류 검사와 쓰기의 revision 충돌 거부를 유지합니다. 저장 직후 SDK로 저장본을 다시 읽어 반환 revision·블록 수·종류를 검사하고 실제 인라인 스냅샷을 대응 자료에 보관한 뒤 화면에 반환합니다. 이 사후 검사는 쓰기용 읽기와 별도이며, 화면 뒤로 미루지 않습니다. 원본 상자와 오른쪽 문서는 확인 결과를 받은 뒤 함께 갱신합니다. 어긋나면 대응 이동을 멈추고 되돌리기는 남깁니다. 화면을 닫으면 되돌리기 기록은 없어집니다. 문서를 탭에서 고치는 중인지 SDK가 알 수 없어 저장본 수정은 허용됩니다. 미저장 탭에서 나중에 저장하면 충돌로 거부되므로 먼저 저장하거나 닫은 뒤 대조 화면에서 고치세요.

단위 검사는 `npm test`로 실행하며 SDK 없는 환경에서는 통합 검사 하나를 건너뜁니다. SDK 통합 검사는 공개 SDK를 해석할 수 있는 환경에서 필요한 TypeScript loader를 사용하고, `PDF_IMPORT_TEST_CLI_ARGS`에 공식 CLI 실행 인자 배열(JSON)을 지정하여 `node --test test/corrections-host.test.mjs`를 실행합니다. CLI는 검사 문서 생성과 최종 유효성 검사, 아래 문서 제목 고치기에만 쓰며 나머지 교정·조회는 SDK로 실행합니다. 줄 글자와 문서의 글자·미주 호출을 공백 차이만 허용하여 전체 대조하며 위치를 확정하지 못하면 나누지 않습니다.

격리 HTTP Host에서 공개 표본의 합치기·되돌리기·다시 합치기·나누기·종류 변경과 되돌리기·빼기와 되돌리기를 확인했습니다. 오른쪽 문서 ready까지 0.54~0.64초였습니다. 큰 문서의 같은 흐름은 2.07~3.10초여서 1.5초 목표를 충족하지 못했습니다. 큰 문서에서 26회 연속 교정 중 plugin process failure는 재현되지 않았습니다. 공개 표본의 7가지 교정과 각각의 되돌리기는 master의 CLI 경로와 문서 바이트 및 사후 검사가 끝난 대응 자료 전체가 같았습니다. 각주 호출 삭제는 기존과 같이 확인 후 되돌리기 기록을 비우며, 원래 표지를 지정한 정의 복원 기능은 여전히 제공하지 않습니다. 처리 코드에 남은 CLI 호출은 없습니다. 설치형 Desktop은 검사하지 않았습니다.

## 문서 제목

첫 번호 조항 위의 대제목은 제목 단계가 아니라 리치오의 문서 제목(머리말 `title`)으로 보냅니다. 조항 제목의 단계는 번호 깊이 그대로 둡니다(`1. Overview`는 제목 1). 변환은 문서 제목을 스스로 정하지 않습니다. 번호 없는 큰 글자는 지금처럼 제목 후보 경고(사례집 H-01)로 남고, 사람이 **종류 → 문서 제목**(메뉴는 **문서 제목으로**)을 고릅니다.

- 본문이나 제목 블록 하나를 골랐을 때만 쓸 수 있습니다. 여러 개, 목록·표·그림·각주, 미주 호출이 든 블록, 수식·인용이 든 블록은 비활성이고 이유를 메뉴와 **종류** hover에 보입니다(**종류**의 다른 항목은 쓸 수 있을 때 `문서 제목: …`으로 표시).
- 블록의 글자에서 서식을 떼고 줄바꿈과 연속 빈칸을 빈칸 하나로, 앞뒤 빈칸을 다듬어 제목으로 씁니다. 그림·표 참조는 원문 글자(`Figure 3`)로 씁니다.
- 그 블록은 본문에서 빠집니다. 원본 상자는 제목 색으로 표시하고 상자 옆에 **제목**을 적습니다. 상자를 고를 수 있으며 hover·focus 설명은 **문서 제목으로 쓰임**입니다. 이 상자에서 종류 바꾸기·합치기·나누기·빼기는 사용할 수 없고 **되돌리기**로 복원합니다. 새 색 범례는 더하지 않았습니다. 제목 후보 경고는 블록과 함께 사라집니다.
- 이미 제목이 있으면 **문서 제목 바꾸기** 확인 창에서 묻습니다. 이전 제목 블록은 본문으로 되살리지 않습니다.
- **되돌리기**는 블록을 원래 종류와 자리로, 문서 제목을 이전 값(없었으면 없음)으로 함께 돌립니다. 기존 되돌리기 기록과 대응 자료를 그대로 씁니다.
- 공개 SDK에 문서 제목을 바꾸는 연산이 없어 이 동작과 그 되돌리기만 공식 CLI `apply-batch` 하나(블록 빼기·넣기와 `update-title`, `--if-revision`)로 저장합니다. 본문과 제목이 한 revision 검사·한 번의 쓰기로 바뀌며, 저장 뒤 검사는 다른 고치기와 같습니다. Host가 CLI 실행 정보를 주지 않으면 실패를 알립니다.

제목 상자를 고르면 연결 띠를 그리지 않고 오른쪽 문서를 움직이지 않습니다. 첫 본문을 대상으로 이동하는 실험에서는 제목이 보이는 영역 밖으로 밀렸습니다.

격리 HTTP Host에서 공개 LSR의 표지를 포함해 변환하고, 제목으로 보내기·선택·되돌리기·다시 보내기·문서 목록에서 다시 열기와 실제로 뺀 블록의 빗금을 확인했습니다. [이전](test/captures/title-box/before-1440.png), [변경 후](test/captures/title-box/after-1440.png), [어두운 화면](test/captures/title-box/dark-1440.png)을 확인했습니다.

## 원본의 영역 표시

일반 블록은 종류별 옅은 면과 왼쪽 띠로 표시합니다. 마우스를 올리거나 키보드로 초점을 주면 블록 윤곽과 설명이 보입니다. 스크롤 추적은 띠 색만 바꿉니다. 경고·단계·고침은 왼쪽 여백에 나란히 둡니다. 줄 선택선은 나누기 중에만 표시합니다. 제외 영역은 빗금으로 구별하고 hover와 focus에서 제외 이유를 표시합니다. 설명은 조작 줄 아래의 예약된 공간에 있어 원문을 덮지 않습니다. 종류별 색과 조작 방법은 같습니다.

격리 HTTP Host의 공개 표본에서 7쪽 각주 선택 전후, 다중 선택, 나누기, 머리글·바닥글과 사용자가 뺀 영역, 단계·경고·고침의 동시 표시, 표와 그림, 밝고 어두운 테마를 확인했습니다. 종류별 면은 토큰 색 12%, hover/focus 18%, 선택 22%를 곱하기 혼합으로 표시합니다. 혼합은 쪽 단위로 묶습니다. 제외는 text-muted 70%와 surface 30%를 섞은 회색에서 80% 빗금 선(2px, 주기 7px)과 35% 면을 만듭니다. 제외 영역만 사방 3px 넓혀 작은 머리글·바닥글에서도 무늬가 보이게 합니다. 범례도 같은 무늬입니다. 임의 PDF의 극히 좁은 왼쪽 여백과 본문까지 겹친 원본 상자는 확인하지 않았습니다. 설치형 Desktop은 이번 변경에서 검사하지 않았습니다.

## 쪽 고르기의 검증과 비용

격리 HTTP Host에서 공개 표본(책갈피 있음/제거한 사본)과 별도 138쪽 PDF로 선택 → 격자 → 변환·대조, 누르기·Shift 범위·크게 보기·키보드 조작, 취소·다시 변환·저장본 바로 열기를 확인했습니다. 공개 표본 캡처는 `test/captures/page-picker/`입니다. 범위 선택과 공개 PDF의 첫 책갈피 대응은 리치오 없이 검사합니다.

미리 보기는 화면과 300px 주변만 그리며 동시에 두 장까지 그립니다. 지나간 쪽은 대기·진행 중 그리기를 취소합니다. 완성된 캔버스는 격자를 닫을 때까지 재사용합니다. 138장을 그린 뒤 왕복 스크롤에서 크기 재설정 0건을 확인했습니다. 크게 보기는 해당 쪽만 큰 배율로 그립니다.

SDK 0.6.0 Host의 1440×1000 창에서 128px·8열로 24장이 완전히 보이고 일부가 보이는 것까지 32장입니다. 첫 화면 완료는 5.52초에서 1.75초로 줄었습니다. 파일 전달 0.56초, PDF 준비 0.12초, 책갈피 대응 0.01초였고 제안은 별도로 진행합니다. 완성된 138장으로 왕복했을 때 재그리기 0건, 전체 격자 스크롤의 50ms 초과 long task는 17회·최대 71ms였습니다. 캔버스 픽셀 저장량은 약 11.2MiB이며 GPU·프로세스 전체 메모리 값은 아닙니다.

처리 코드는 같은 sha256의 추출 Promise와 결과를 한 파일분만 메모리에 보관합니다. 제안 완료 뒤에는 기존에도 추출을 다시 하지 않았습니다. 이제 제안 추출 도중 변환을 시작해도 같은 작업을 기다리며 중복 추출하지 않습니다. 같은 선택의 변환은 변경 전 14.48초, 변경 후 13.30초였으며 둘 다 추출 대기는 약 0ms였습니다. 이 차이를 추출 재사용에 의한 개선으로 해석하지 않습니다. 제안 응답을 끝까지 보류하고 그 전에 시작한 변환은 남은 추출 대기 2.11초를 포함해 14.96초였습니다. 저장된 제외 선택이 사용자 선택 그대로이고, 늦은 응답이 대조 화면을 바꾸지 않는 것을 확인했습니다.

제안 응답을 늦춰 직접 포함·제외와 Shift 범위를 먼저 바꾼 경우도 확인했습니다. 앞 부속을 포함한 변환에서 발견한 중복 각주 정의는 F-07로 기록했고, 모호한 짝을 글자로 보존하여 공식 저장과 CLI 검사를 통과했습니다. 설치형 Desktop, 다른 OS, 회전·세로쓰기·가로세로가 혼재한 대형 PDF는 검증하지 않았습니다.

## 양방향 대조 검증

PR litzio#1716을 포함한 격리 HTTP Host에서 공개 표본과 별도 큰 PDF의 양쪽 휠·스크롤바·키보드 이동, 번갈아 조작하기, 함께 스크롤 끄기, 오른쪽 제목·문단·목록·표·그림 누르기와 고친 뒤 새 대응을 확인했습니다. 오른쪽 누르기로 선택한 문단을 합치고 되돌린 뒤에도 이동했습니다. 더블클릭한 단어 선택이 유지됐습니다. 공개 표본의 일부 대응을 비운 시험 자료에서 누르기는 기존 선택을 유지하고 스크롤은 바로 앞 블록의 원본을 사용했습니다.

큰 PDF에서 1800px 휠 이동마다 120ms와 두 animation frame을 기다리며 처음부터 끝까지 측정했습니다. 50ms 초과 long task는 왼쪽 15회·최대 107ms, 오른쪽은 새로 연 PDF에서 25회·최대 109ms였습니다. 앞선 순회로 그림이 준비된 상태의 오른쪽은 0회였습니다. 이전 왼쪽 기록 33~34회·최대 99~108ms와 비교해 최댓값은 비슷하지만 조작·캐시 조건이 같지 않아 횟수 차이를 성능 개선으로 해석하지 않습니다. 빠르게 끝까지 옮긴 뒤 약 120ms 간격으로 2.3초 동안 두 칸 위치를 기록했고, 왼쪽 주도는 263ms 이후, 오른쪽 주도는 137ms 이후 안정적이었습니다. 소유권 해제를 위한 고정 대기는 없으며 기존 왼쪽 스크롤의 150ms 모음만 유지합니다. packaged Desktop과 다른 OS는 검증하지 않았습니다. 터치패드·터치는 지원 대상이 아닙니다.

## 가벼운 위쪽 줄과 블록 메뉴

도구 줄 왼쪽은 범례와 선택 동작을 바꿔 보이고, 오른쪽은 경고 이동·함께 스크롤·되돌리기를 한 묶음으로 둡니다. 되돌리기는 기록이 있을 때만 한 자리에 나타납니다. 종류 선택은 공개 Select의 hideLabel을 쓰며 접근성 이름은 유지합니다. 도구 줄은 32px 버튼 한 줄이고, 그 아래 안내는 24px 한 줄을 늘 차지합니다. 나누기 안내가 경고 이유보다 우선합니다. 내부 폭이 940px 이하면 오른쪽 묶음을 다음 줄로 보내 범례와 선택 동작 사이의 높이 차이를 막습니다.

## 연결 띠와 훑어보기 배율

대조 화면은 리치오의 `LinkedDocumentView`를 사용합니다. 원본과 문서가 도구 줄 아래 남은 높이를 채우고 각 칸에서 따로 스크롤합니다. 종류별 색의 연결 띠는 채움으로 표시되며, 창 높이와 스크롤 위치에 맞춰 다시 그려집니다. 띠를 누르면 대응 블록을 고릅니다. 쪽을 넘는 블록은 상자마다 이어집니다. 저장본이 바뀌어 대응을 표시할 수 없으면 띠를 숨깁니다.

Shift로 여러 블록을 고르면 마지막 블록에 리치오 윤곽과 활성 띠가 보입니다. 나머지 선택은 원본의 옅은 면과 가는 선으로 표시하며, 도구 줄에 전체 선택 개수가 나옵니다.

도구 줄 오른쪽 배율과 양쪽 칸 안의 Ctrl+휠은 100·75·50·40%를 함께 바꿉니다. 기본은 75%이며 브라우저의 기존 localStorage 방식으로 기억합니다. 칸 밖의 Ctrl+휠은 가로채지 않습니다. 원본은 기준 위치의 블록을 같은 높이에 두고 새 크기의 canvas를 다시 그립니다. 문서는 공개 scale의 재배치와 위치 유지를 사용합니다. 작은 배율에서 보이는 쪽과 앞뒤 두 쪽을 그리고, 40%에서는 단계와 고침의 여백 글자를 점으로 줄입니다. 우클릭·선택·나누기 좌표는 같은 축소 비율을 사용합니다.

격리 HTTP Host의 합성 표본에서 두 스크롤 영역은 1440×1000에서 664px, 1440×700에서 364px였고 탭 하단까지 채웠습니다. [밝음](test/captures/linked-document-view/light-selected.png), [어두움](test/captures/linked-document-view/dark-selected.png), [1440×700](test/captures/linked-document-view/short-selected.png), [여러 블록 선택](test/captures/linked-document-view/multiple-selected.png)에서 확인할 수 있습니다.

아래 수치와 이전 캡처는 화면 자체 연결 띠를 쓰던 버전의 기록입니다. 격리 HTTP Host(SDK 0.9.0)에서 공개 표본과 큰 PDF로 네 배율, 양방향 스크롤, 양쪽 hover, 띠 클릭, 한쪽 화면 밖으로 빠지는 띠, 표·그림·쪽을 넘는 문단과 제외된 쪽 구간을 확인했습니다. 50%에서 합치기·나누기와 각각의 되돌리기 뒤 새 대응이 그려졌습니다. 40%의 우클릭 메뉴와 작은 여백 점도 확인했습니다. stale에서는 띠가 없습니다. 공개 표본의 스크롤 직후 다음 frame에서 측정한 양 끝 위치 오차는 0.01px 이내였고, 네 배율을 왕복했을 때 원본 기준 블록의 높이 변화는 0.3px 미만이었습니다. Ctrl+휠은 양쪽 안에서만 브라우저 확대를 막았고 재진입 시 배율이 복원됐습니다. 1000·900px에서도 가로 넘침이 없으며 800px에서는 기존 세로 배치와 함께 띠를 숨깁니다.

## 누른 블록의 짝 맞추기

원본 상자를 누르면 오른쪽 문서의 짝이 그 상자의 보이는 윗선과 같은 높이에 옵니다. 누른 상자의 블록에서 화면에 걸친 첫 상자의 윗선(원본 칸 위 가장자리 기준 px)을 공개 `document.target.top`으로 넘기고, 누를 때마다 `target.request`를 바꿉니다. 그래서 문서만 스크롤한 뒤 같은 블록을 다시 눌러도 다시 맞춥니다. 위 가장자리에 걸려 잘린 상자는 음수 높이를 넘겨 문서 블록도 같은 만큼 잘립니다. 문서 블록을 누르면 반대로 문서는 그대로 두고, `onVisibleBlockLayoutChange`가 알린 그 블록의 윗선에 원본 블록의 첫 상자 윗선이 오도록 원본 칸을 직접 스크롤합니다. 양쪽 모두 처음·끝 스크롤 한도에서는 갈 수 있는 데까지만 가고, 차이가 8px 이하면 움직이지 않습니다(리치오 `target.top`과 같은 기준). 원본이 한도에 막혀 맞추지 못하면 문서는 움직이지 않습니다. 경고 이전·다음은 지금처럼 원본 블록을 원본 칸 높이의 1/3 지점에 두고, 문서 짝을 그 높이에 맞춥니다. 고치기 뒤 다시 읽을 때도 결과 블록의 원본 상자가 보이면 같은 높이에 맞춥니다. 이 기능은 이전의 "이미 보이면 그대로 둔다" 동작을 대신합니다.

**함께 스크롤과의 우선.** 누른 직후에는 누른 정렬이 이깁니다. 누르기는 그 짝을 보겠다는 분명한 요청이고, 함께 스크롤은 훑어보는 동안의 대략적인 대응이기 때문입니다. 누를 때 원본에서 기다리던 따라가기를 취소하고, 정렬로 생긴 원본 스크롤은 사용자 입력이 아니므로 따라가기를 일으키지 않으며, 문서 쪽 `target` 이동은 리치오가 보이는 블록 알림을 보내지 않습니다. 다음 휠·스크롤바·스크롤 키 입력부터 그 칸이 다시 주인이 되어 함께 스크롤이 따라옵니다. 누른 뒤 아무 칸도 스크롤하지 않았으면 배율을 바꿔도 누른 짝을 기준으로 원본을 다시 놓고 문서 짝을 같은 높이에 다시 맞춥니다.

격리 HTTP Host(리치오 07cdfe31)에서 공개 LSR 표본으로 확인했습니다. 두 윗선의 차이는 원본 클릭(문서 짝이 위·아래·안, 위 가장자리에 잘린 상자, 75%·100%) 0.22~0.36px, 문서 클릭(원본 짝이 위·아래·안) 0.06~0.47px, 문서만 스크롤한 뒤 같은 블록 다시 클릭 0.31~0.36px였습니다. 함께 스크롤을 켜고 원본 휠 뒤 원본 클릭, 문서 휠 뒤 문서 클릭, 경고 다음·이전, 배율 75%↔100%, 본문을 제목으로 고친 뒤와 되돌린 뒤 모두 0.22~0.33px였고, 매번 정렬 뒤 40 animation frame 동안 두 칸의 스크롤 위치가 바뀌지 않았습니다(흔들림 없음). 한도에서는 문서 처음(문서 0px에서 34.8px 차이로 멈춤)·문서 끝(끝에서 64.0px 차이)·원본 처음(원본 0px에서 31.8px 차이, 문서는 그대로)을 확인했습니다. 이 표본에서는 원본 끝 한도에 막히는 문서 블록이 없어 원본 끝은 단위 검사로만 확인했습니다. 앞의 두 경고는 문서 처음에 있어 같은 이유로 3.4~26.1px 차이에서 멈춥니다(75%). ## PDF별 저장

`X.pdf`는 원래 위치에 두고 `X/X.md`, `X/X.pdf-source.json`, `X/assets/`에 저장합니다. 그림 key는 그림으로 저장되는 표·그림 순서로 `table-001`, `figure-002`처럼 정합니다. 실제 파일은 같은 이름의 `.png`이고, 기존 이름에 다른 내용이 있으면 Host 계약에 따라 내용 해시 8자리가 붙습니다. 원본 위치는 대응 자료의 PDF 이름과 결과 폴더의 부모로 찾습니다. 이전 평면 저장 위치를 찾거나 변환하는 코드는 없습니다.

고친 이력은 PC 시간대에 관계없이 한국 시간 `YYYY-MM-DD HH:mm:ss`를 사용합니다. 목록은 대응 자료의 수정 시각을 한국 시간 기준의 ‘오늘 14:20’, ‘어제’, ‘11월 17일’ 등으로 보여 줍니다. 대응 자료에는 최초 변환 시각이 없으며, 저장본을 다시 열거나 교정하면 수정 시각이 바뀔 수 있습니다.

이번 변경은 격리 HTTP Host에서 공개 LSR와 책갈피를 제거한 LSR 사본을 같은 입력 폴더에서 변환했습니다. 각각 그림 10개가 별도 assets에 저장되고 대조 화면·일반 문서 탭에서 표시됐으며 합치기·되돌리기와 목록 재열기를 확인했습니다. 재변환 전후 모두 문서 1개·대응 자료 1개·그림 10개였고 복구 사본은 남지 않았습니다. 큰 디지털 PDF에서도 저장과 그림 정리를 확인했습니다. 실패 후 수동 복구, 다른 OS와 packaged Desktop은 확인하지 않았습니다. 터치패드·터치 입력은 검사 범위가 아닙니다.

## 문서 검토 상태

새 변환과 다시 변환은 항상 초안으로 저장합니다. 머리 줄과 목록의 검토 상태는 문서에서 읽습니다. 검토 완료 버튼은 approved로, 초안으로 되돌리기는 draft로 바꿉니다. 검토 중과 상태 없음에서는 검토 완료를 제공합니다. 변환 경고가 남아 있어도 완료할 수 있고 hover·focus에 남은 개수를 알립니다. 문서가 바뀌거나 고치는 중에는 이유와 함께 버튼을 비활성화합니다. 상태만 바꿀 때 대응 자료의 revision과 기존 되돌리기의 revision을 맞추며 고치기 이력에는 추가하지 않습니다.

이번 상태 변경은 격리 HTTP Host에서 공개 표본의 변환 → 초안 → 검토 완료 → 합치기·되돌리기 → 초안 복귀, 공식 CLI의 검토 중 변경 후 재열기, 재변환 뒤 초안과 check 유효성을 확인했습니다. 외부 상태 변경도 revision을 바꾸므로 대응 이동과 상태 버튼은 기존 보호에 따라 멈춥니다. 새 배율 기억을 지운 뒤 75%, 50%를 선택한 뒤 화면 재열기에서 50% 유지와 경고 개수 설명의 keyboard focus를 확인했습니다. 1440px의 초안·검토 완료·목록·다크 캡처는 test/captures/draft-status-*.png입니다. 머리 줄 control의 높이·중심과 줄 넘침을 직접 확인했습니다. 설치형 Desktop·다른 OS·터치 입력과 저장 도중 강제 종료는 확인하지 않았습니다.

## 괘선 표를 글자로 옮기기

가는 채움(1.5pt 미만)과 stroke 경로에서만 괘선을 얻습니다. 넓은 채움 사각형의 배경은 경계로 쓰지 않으며, 열 경계는 전체 높이의 15% 이상을 덮는 선분으로 정합니다. 2pt 이내 선 위치를 모으고 이웃 칸의 경계가 절반 이상 없으면 병합 칸으로 복원합니다. 짧은 내부 분수선은 격자 경계로 쓰지 않습니다.

머리글은 경계를 가로지르는 병합을 따라 늘립니다. 마지막 머리글 행에서 시작하고 끝나는 가로 병합(전체 폭 제외)은 바로 아래 행이 그 열 범위를 둘 이상의 칸으로 나눌 때만 한 줄 늘립니다. 끝까지 늘어나면 한 줄로 되돌립니다. 열별 머리글은 같은 칸을 한 번씩 ` / `로 잇고, 본문 병합 값은 덮는 칸마다 반복합니다. 전체 폭 제목은 첫 칸에만 두며, 아래에 이어진 전체 폭 주석 행은 자기 원본 상자를 가진 본문으로 뺍니다. 테두리 아래에서 왼쪽 정렬로 시작한 글자도 주석 문단 하나로 보존합니다. 문장별로 다시 나누지는 않습니다. 칸 안의 줄은 문단과 같은 하이픈 잇기 함수를 씁니다. 같은 보이는 칸 줄에서 바로 앞 낱말보다 크기가 0.8배 미만이고 기준선이 1pt 넘게 올라간 낱말도 위첨자로 판정합니다. 정의가 유일한 숫자 위첨자는 공식 미주 호출로, 그 밖의 위첨자는 공식 서식으로 옮깁니다. 글자가 아닌 내용이 의심되는 칸은 위첨자·미주로 해석하지 않고 보통 글자로 둡니다. 본문 위첨자 판정은 바꾸지 않습니다. 번호 캡션이 붙은 표·그림은 원문 번호를 고정 번호로 넣고 캡션 앞의 번호를 뗍니다(아래 "그림·표 참조"). 그 밖의 표·그림은 원본 캡션을 그대로 두고 공식 enumerated:false로 자동 번호를 숨깁니다. 캡션이 없어도 번호는 붙지 않습니다.

세로로 쌓인 영역은 모두 각각 변환할 수 있을 때만 분리합니다. 하나라도 실패하면 전체를 그림으로 남깁니다. 가로로 나란한 격자는 나누지 않습니다. 격자 없음, 칸 밖 글자, 떨어진 두 격자, 직사각형이 아닌 병합, 100행·32열 초과는 이유를 붙인 그림입니다. 글자 표의 PNG는 만들지 않습니다. 원래 격자·병합 범위·머리글 줄 수·내보낸 주석 수는 대응 자료에만 남깁니다.

병합을 푼 표는 `table-unmerged`, 칸 안의 짧은 분수선·이미지·사각형이 아닌 작은 채움 도형은 `table-cell-graphic` 경고를 붙입니다. 배경 사각형과 격자 행 경계는 의심 신호에서 뺍니다. 글자 겹침/기준선 차이 신호는 위첨자와 혼동하므로 쓰지 않습니다. 수식을 복원하지 않아 빈칸이나 조각난 글자가 남을 수 있습니다. 의심 칸은 비서나 사람이 원본으로 확인해야 합니다. 글자 표 자체를 대조 화면에서 빼거나 그림으로 바꾸지는 못하며 문서 탭에서 고칩니다. 쪽을 넘는 표도 잇지 않습니다.

정답 채점은 원래 격자의 행·열과 병합 범위를 비교합니다. 칸 값은 NFKC와 빈칸 정리만 하며 부호·단위·소수점·대소문자를 보존합니다. LaTeX 수식 칸은 일치/불일치에서 제외합니다. 수치는 이 합성 표본의 진단이며 대표 정확도가 아닙니다.

| --- | ---: | ---: |
| 글자 표 / 정답 표 8개 | 0 | 5 |
| 행·열 수가 같은 글자 표 | 0 | 5 |

나머지 정답 표 세 개는 칸 밖 글자 또는 나란한 두 격자 때문에 그림으로 남습니다. 표 밖 기존 정답 채점의 모든 맞음 수는 유지합니다. `answer-key-baseline.json`은 종류별 맞음 수와 위 표 지표의 하락을 막습니다. `compare-tables.mjs <PDF 또는 변환 JSON> <Docling JSON>`은 개발용 일치율 측정이며 정확도가 아닙니다. 같은 모양의 표에서 같은 범위를 가진 칸을 엄격 비교합니다. 원문과 비교 자료는 커밋하지 않습니다.

넓은 7열 표는 대조 화면의 문서 칸에서 오른쪽 열이 한 번에 보이지 않습니다. 75%·100%에서 가로 휠로 마지막 열까지 읽을 수 있고 일반 문서 탭에서도 가로 휠로 닿습니다. 화면을 고치지 않고 제약으로 남겼습니다. 설치형 Desktop·터치 입력·임의 스캔/회전 PDF와 모든 수식의 의미는 검증 범위가 아닙니다.


격리된 최신 Host에서 공개 표본의 변환·저장·표 선택·경고 hover·밝음/어두움, 표 뒤 문단의 합치기·나누기·빼기와 되돌리기를 확인했습니다. 큰 문서에서는 전체 변환·저장·공식 check, 분리한 표와 원본의 대응, 표 밖으로 내보낸 주석의 대응과 교정을 확인했습니다. 공개 표본에는 이번 규칙으로 새로 분리되는 주석 행이 없어 그 형태는 합성 단위 검사로 고정하고 실제 주석 교정은 큰 문서에서 확인했습니다. 새 표 자체의 고치기는 기존 그림처럼 비활성입니다.

공개 SDK는 격리 Host가 공급하며 플러그인 작업 폴더의 node_modules에는 pdf.js만 있습니다. Host 패키지로 가는 junction/symlink를 만들지 않았습니다. 첫 격리 checkout은 기존 추적 패키지 삭제와 손상된 의존성 설치가 있었고 `--force` 재설치가 다른 플랫폼용 선택 의존성까지 설치해 고지 검사가 실패했습니다. 그 checkout은 보존하고 새 격리 checkout에서 일반 설치와 편집기·CLI 전체 빌드를 통과한 Host로 검증했습니다. 원인 추정은 확인된 삭제 원인으로 단정하지 않습니다.

검토 수정 뒤 단위 검사 42개와 별도 SDK 통합 검사 1개가 통과했습니다. 격리 Host에서 두 PDF의 재변환·공식 저장·check를 다시 확인했으며 합성 표본의 캡션 번호는 한 번만 보입니다(`test/captures/table-text/caption.png`).

## 번호 있는 독립 수식

줄 전체가 `(1)` 또는 `(A.1)` 꼴이고, 제외되지 않은 본문 폭의 오른쪽 20%에 있으며, 같은 높이의 오른쪽에 글자가 없고 왼쪽에 글자나 영역이 있는 번호를 닻으로 씁니다. 왼쪽 목록 표시는 닻으로 잡지 않습니다. 번호 없는 수식은 찾지 않습니다.

옆 그림이 없으면 번호와 세로로 겹치는 글자 상자부터 겹치거나 거의 닿은 상자(번호 높이의 10% 이내)를 연결합니다. 본문 폭의 80% 이상을 채우는 줄은 연결하지 않습니다. 수식 근호·분수의 가로 괘선은 글자 경계에서 번호 높이 이내인 것까지 그림에 포함합니다. 보통 문단 간격과 `where` 설명은 연결하지 않습니다. 뜻·폰트 이름·특정 쪽 번호는 신호로 쓰지 않습니다.

한 그림에 번호가 여럿이면 번호 띠 사이의 빈 곳에서 세로로 나눕니다. 괘선 격자 아래 번호가 있으면 격자 아래 끝을 표의 끝으로 남겨 엄격한 기존 표 판정에 맡깁니다. 분리된 수식은 이후 영역 병합에서 보호합니다. `figure`와 `formula:true`, 경고 `formula-as-image`(수식을 그림으로 둠)로 내고 대체 글자는 `수식 영역`입니다. 캡션·자동 번호는 붙이지 않습니다. 화면 코드는 바꾸지 않습니다.

채점은 정답 수식마다 `own_image`(다른 정답 표·수식과 겹치지 않는 자기 그림 하나), `merged`, `fragmented_text`, `missing`을 별도로 냅니다. 수식의 의미 일치를 검사하지 않습니다.

| 합성 표본 지표 | 전 | 후 |
| --- | ---: | ---: |
| 자기 그림 하나 / 수식 3개 | 0 | 3 |
| 다른 것과 합쳐진 수식 | 3 | 0 |
| 글자 표 / 정답 표 8개 | 5 | 6 |
| 격자 일치 | 5 | 6 |
| 병합 범위 일치 | 122 | 131 |
| 수식 제외 값 일치 | 120 / 120 | 127 / 127 |

11쪽의 표가 수식과 분리되어 글자 표가 됩니다. 표 칸의 수식 두 개는 기존 의심 칸 경고로 남습니다. 표 밖 채점의 모든 칸과 관계(맞음 18·틀림 1·확인 안 함 3)는 그대로입니다. 이 수치는 합성 표본의 진단이며 대표 정확도가 아닙니다. 기준선은 글자 표 지표와 자기 그림 수의 하락을 막습니다.
격리 HTTP Host에서 두 표본 모두 공식 저장과 공식 `check`의 valid=true를 확인했습니다. 합성 표본은 8쪽의 두 수식을 각각 선택하고 경고 다음·이전으로 이동하여 오른쪽의 해당 수식 그림이 강조됨을 확인했습니다. 공개 캡처는 `test/captures/formula-regions/`에 있습니다. 원본 영역 다섯 개와 사라진 본문 블록은 원본 쪽 그림으로 직접 대조했습니다. 합성 표본에서는 사라진 본문이 없고, 큰 문서에서 사라진 여섯 블록은 수식 본체·한계·분모·번호였습니다. 두 표본 모두 글자 표의 누락·중복 낱말은 0입니다.

번호 없는 독립 수식·본문 안 수식·표 칸의 수식 복원과 `where` 기호 설명 정리는 범위 밖입니다. 수식의 의미 정확도, 다른 문서의 다단 배치·폰트·회전·스캔, 설치형 Desktop과 다른 OS는 검증하지 않았습니다. 공유 그림과 표의 복합 영역 분리는 작은 합성 줄 자료로도 검사했으며, 실제 표본에서는 추출기가 남긴 별도 도형 영역을 이후 병합에서 보호하는 경로로 분리됐습니다. 새 플랫폼 우회는 없습니다.

## 엔진과 문서 형식 프로필

변환 규칙은 공통 엔진(`rules.mjs`, `extract.mjs`, `table-grid.mjs`, `formula-regions.mjs`)과 문서 형식 프로필(`profiles/`)로 나뉩니다. 엔진은 어느 PDF에나 통하는 모양·배치 신호를 읽고, 프로필은 한 문서군의 글자 약속만 담습니다. 프로필은 번호 제목 해석 함수 `heading`, 캡션 패턴 `caption`과 캡션이 가리키는 종류 `captionKind`, 본문의 그림·표 참조 글자 `reference`와 링크 없는 문서에서 다른 규격의 번호를 거르는 `foreignReference`, NOTE 문단 `note`, NOTE 문단을 알아보고 알림 상자 본문을 정하는 함수 `noteBody`, 표 아래 NOTE 줄 `tableNote`, 본문 시작 제목 `bodyStart`만 가집니다. `null`은 그 약속을 쓰지 않는다는 뜻입니다.

- `ieee`: IEEE 표준의 약속.
- `generic`: 문서군을 모를 때의 기본값. NOTE 문단, NOTE 알림 상자와 표 아래 NOTE 줄은 끕니다. 부록 제목, 캡션 모양, 그림·표 참조 글자, 본문 시작 제목은 공개 표본이 기대고 있어 켜 두었습니다(재검토 대상).

**선택.** `profiles/index.mjs`의 `selectProfile`은 첫 두 쪽에 `IEEE Std <번호>`로 시작하는 줄이 있거나 PDF 제목이 그렇게 시작하면 `ieee`, 아니면 `generic`을 고릅니다. 문장 속 인용이나 PDF의 다른 정보 칸에 IEEE가 나오는 것은 신호가 아닙니다(공개 표본의 주제 칸이 그렇습니다). 고른 이름은 변환 결과·대응 자료·`measure.mjs` 출력의 `profile`에 남습니다. 화면은 아직 이 값을 쓰지 않으며, 이 칸이 없는 이전 대응 자료도 그대로 읽힙니다.

**새 프로필.** 그 문서군의 공개 표본과 정답 기준이 있을 때만 더합니다. `profiles/`에 같은 칸을 가진 파일을 두고 `profiles/index.mjs`의 목록과 선택 신호에 더합니다. 프로필 이름에 회사·고객 이름을 쓰지 않습니다. 엔진에 걸림 자리가 없는 약속이 필요하면 엔진에 자리를 하나 열고, 기존 프로필에서는 이전 동작이 유지되는지 확인합니다.

**분류.** 규칙마다 쓰는 신호로 나눈 결과입니다. 근거의 사례 번호는 `cases.md`를 봅니다.

## NOTE 알림 상자와 쪽을 넘는 목록

**NOTE(IEEE 프로필).** `NOTE—`, `NOTE 1—`처럼 시작하는 본문 문단은 리치오 알림 상자 `note`(화면 이름 "참고")로 저장합니다. 상자 본문은 원문 글자 그대로입니다(소유자 결정, 2026-11-18). `NOTE` 낱말, 번호, 구분 기호와 빈칸을 바꾸지 않으므로 상자의 종류 이름표("참고")와 `NOTE`가 겹쳐 보이는 것은 받아들입니다. 구분 기호는 줄표(—, –, ―)와 하이픈을 받습니다.

| 원문 | 알림 상자 본문 |
| --- | --- |
| `NOTE—text` | `NOTE—text` |
| `NOTE 2—text` | `NOTE 2—text` |
| `NOTE 3 – text` | `NOTE 3 – text` |

쪽을 넘는 NOTE는 쪽을 넘는 문단 잇기(P-02)가 먼저 한 문단으로 이은 뒤 상자로 바뀌므로 상자 하나에 원본 상자 둘이 대응합니다. NOTE 뒤에 NOTE 표시 없이 이어지는 문단은 상자에 넣지 않습니다. **목록 항목 안의 NOTE(L-07, 소유자 결정 2026-11-18)**는 상자로 빼지 않습니다. 바로 앞 블록(사이의 각주는 건너뜀)이 같은 쪽의 목록 항목이고 NOTE의 왼쪽 끝이 그 항목의 표시보다 0.7em 넘게 들어가 있으면(항목 글 열) 그 항목 안의 NOTE로 봅니다. 리치오 목록 항목은 문단 하나(인라인 내용 하나와 중첩 목록)만 담으므로, 원문 글자 그대로 항목 글 뒤에 빈칸 하나를 두고 이어 붙이고 원본 상자도 그 항목에 합칩니다. 그래서 목록이 NOTE에서 끊기지 않습니다. 목록 여백에 놓인 NOTE는 전처럼 목록 뒤의 상자입니다. 큰 표준 문서에서는 106쪽의 NOTE 하나가 해당하며, 원본에서 그 NOTE는 항목 글 열에 맞춰 들어가 있습니다(PDF 구조 태그는 이 NOTE를 목록 밖 문단으로 태그하지만, 이 문서의 목록 태그는 표 캡션에도 붙어 있어 배치를 따랐습니다). 알림 상자는 37개, 목록은 51개(이 NOTE 뒤에서 이어지던 목록이 없어 그대로)입니다. 리치오 알림 상자는 문단 하나만 담고, 큰 표준 문서에는 여러 문단으로 된 NOTE가 없었으며(NOTE 뒤에 NOTE 표시 없이 NOTE 크기로 이어지는 문단이 없음), 글자 크기만으로 뒤 문단을 NOTE에 붙이면 잘못 붙일 위험이 있기 때문입니다. 글자 표에서 주석으로 빼낸 표 아래 NOTE는 그대로 문단입니다. 범용 프로필은 바뀌지 않습니다.

**쪽을 넘는 목록(엔진).** 쪽을 넘는 문단 잇기와 같은 단계에서, 쪽의 첫 본문 블록이 목록 항목이고 앞 쪽이 목록으로 끝났으면 앞 쪽 끝의 목록 항목 가운데 들여쓰기가 같은(0.7em 이내) 항목을 찾습니다. 그 항목과 표시 모양이 같고 번호가 바로 다음이면(`a)`→`b)`, `1)`→`2)`, `(i)`→`(ii)`, 같은 기호) 이어진 목록으로 표시합니다. 사이에 든 각주는 건너뜁니다. 번호가 끊기거나(`a)`→`c)`), 모양이 다르거나(`a)`→`(b)`, `a)`→`B)`, 다른 기호), 들여쓰기가 다르면 잇지 않습니다. 작성 계획은 이 표시가 있을 때만 쪽 경계에서 목록을 잇습니다. 다음 쪽이 더 깊은 단계의 새 하위 목록으로 시작하는 경우는 잇지 않습니다. 표시 없이 다음 쪽으로 넘어간 항목의 글(L-06)도 잇지 않습니다. 변환 결과의 `continuesList`가 이 표시이고 `stats.lists.cross_page_joined`가 그 수, `stats.notes`가 알림 상자 수입니다.

**큰 표준 문서(IEEE) 결과.** NOTE로 시작하는 문단은 40개이고 그중 38개가 알림 상자가 됐습니다. 나머지 둘은 글자 표에서 빼낸 표 아래 NOTE입니다. 원본 쪽과 PDF 구조 태그(검증용으로만 대조)를 보고 놓친 것과 잘못 바꾼 것이 없음을 확인했습니다. 표 바로 아래 왼쪽 끝에서 시작해 표 영역에 들지 않은 NOTE 하나는 알림 상자가 됐고, 목록 항목 안에 든 NOTE 하나는 처음에 목록 뒤의 상자가 됐고, 지금은 그 항목의 글로 둡니다(L-07, 아래). 알림 상자는 38개에서 37개가 됐습니다. 쪽을 넘는 목록은 7곳을 이었고(그중 5곳은 사이에 각주가 있어 이전에는 두 목록이었음) 원본에서 잘못 이은 것은 0입니다. 저장 목록은 56개에서 51개가 됐습니다. 제목 240(1~5단계 19·77·92·35·17), 책갈피 일치 188, 각주 정의 141, 표 캡션 48, 그림 캡션 26, 글자 표 62, 쪽을 넘는 문단 11, 경고 75, 분류되지 않은 글자 0은 그대로입니다. 작성 입력은 공식 CLI `create`와 `check`를 통과했습니다(그림은 문단으로 바꿔 검사).

**공개 표본과 채점.** 공개 LSR 표본은 범용 프로필이고 쪽을 넘는 목록이 없어 변환 결과·작성 입력이 새 통계 칸을 빼고 바이트 단위로 같습니다. 정답 자료에도 NOTE 상자와 쪽을 넘는 목록이 없어 채점과 `answer-key-baseline.json`은 바뀌지 않습니다(정답의 NOTE 세 개는 범용 프로필에서 문단이 맞는 답입니다). 새 동작은 손으로 만든 줄 자료와 합성 표본 `test/fixtures/notes-lists.pdf`로 검사합니다.

**대조 화면.** 알림 상자 블록은 "참고"로 표시하고 본문과 같은 색을 씁니다. 격리 HTTP Host에서 합성 표본으로 알림 상자 선택과 띠, 두 쪽에 걸친 목록이 오른쪽의 한 목록에 대응하는 것, 이웃한 번호 목록 둘의 합치기와 되돌리기, 목록과 본문을 섞어 고르면 합치기가 막히는 것을 확인했습니다. SDK 통합 검사는 각주 호출이 든 목록의 합치기·되돌리기가 문서 바이트를 원래대로 돌리는 것을 확인합니다. 캡처는 [알림 상자 선택](test/captures/notes-lists/note-selected.png), [쪽을 넘는 목록](test/captures/notes-lists/list-continued.png), [목록 합치기](test/captures/notes-lists/lists-merged.png)입니다. 큰 표준 문서는 Host에서 다시 변환하지 않았고 설치형 Desktop·다른 OS·어두운 테마는 이번에 확인하지 않았습니다.

## 그림·표 참조

원문과 번호가 같은 그림·표 참조만 리치오 참조로 바꿉니다(S-02의 일부). 조항·부록·수식·참고문헌·각주·표 주석 참조는 지금처럼 글자로 둡니다.

**대상(그림·표).** 같은 종류의 번호 캡션(`Figure 3—…`, `Table B.2—…`)이 붙은 그림 영역과 글자 표는 이름표(`fig-3`, `tab-B.2`)와 원문 번호를 고정 번호로 받습니다. 리치오가 캡션 앞에 `Figure 3`을 그리므로 캡션 글자에서 `Figure 3—`를 뗍니다. 원문의 줄표 구분자는 리치오의 `. `가 됩니다. 그림으로 들어간 표는 리치오에서 `Figure n`으로 보이므로 번호를 넣지 않고 원래 캡션 글자를 그대로 둡니다. 이어지는 표처럼 같은 번호 캡션이 다시 나오면 첫째만 대상이고 둘째는 원래 캡션 글자를 둡니다. 나머지 그림·표는 전처럼 `enumerated:false`이므로 문서의 번호 방식은 고정 번호이고 번호 경고가 나지 않습니다.

**참조 찾기.** 층을 나눕니다.

- 공통 엔진: PDF의 문서 안 링크 주석(`getAnnotations`)의 목적지 쪽·높이에서 대상 블록을 찾습니다. 목적지는 대개 대상보다 약 20pt 위(앞 블록의 끝)를 가리키므로 목적지를 덮는 블록, 없으면 그 아래에서 시작하는 첫 블록입니다. 대상이 캡션이면 캡션이 붙은 그림·표입니다. 링크 상자가 놓인 원본 줄에서 상자에 가장 가까운 참조 글자를 고릅니다. 줄을 넘어 두 상자로 나뉜 링크도 한 참조입니다. 글자 표 칸 안의 링크는 그 칸의 같은 참조 글자를 모두 바꿉니다(병합 값은 덮는 칸마다 반복되므로).
- IEEE 프로필: 참조 글자 `Figure n`·`Table n`(`B.2` 같은 부록 번호 포함)을 읽습니다. 링크가 가리키는 대상의 종류와 번호가 글자와 같을 때만 바꿉니다. 대상이 그림으로 들어간 표처럼 종류가 다르거나 번호가 다르면 글자로 둡니다.
- 글자 규칙: 문서에 문서 안 링크가 하나도 없을 때만 씁니다. 같은 번호의 대상 그림·표가 문서에 있어야 하고, 바로 앞에 다른 규격 이름(`ANSI C84.1 Table 1`)이 오면 버립니다. 제목과 캡션 자기 번호는 찾지 않습니다. 링크 있는 문서에서 글자 규칙 후보는 잘못 찾음이 많아 쓰지 않습니다.

참조는 Core 작성 입력의 `{kind:"reference", role:"numref", label}`로 넣습니다. 작성 계획은 실제로 넣는 블록에 대상이 있는 참조만 넣으므로 대상이 빠지면 그 참조는 글자로 남습니다. 변환 결과의 블록 `refs`(`at`, `length`, `label`)와 글자 표 칸의 `refs`가 찾은 참조이고 `stats.references`가 방식(`links`/`text`), 링크 수, 바꾼 수, 대상 수입니다.

**대조 화면과 고치기.** 대응 자료와 대조 화면은 바뀌지 않습니다. 참조는 블록 하나 안의 글자이므로 합치기·나누기·종류 바꾸기·빼기와 되돌리기가 참조를 그대로 옮깁니다. 나누기는 참조를 원문 글자(`Figure 3`) 한 자리로 셉니다. 그림·표 블록은 대조 화면에서 빼거나 종류를 바꿀 수 없어 이 화면에서는 대상이 사라지지 않습니다. 문서 탭에서 대상을 지우면 리치오가 그 참조를 "해결되지 않은 참조"로 표시합니다. 리치오 계약은 이것을 저장을 막지 않는 작성 상태로 허용합니다(완성 문서 작성 입력만 없는 대상을 거부합니다).

**IEEE 1547 결과.** 원문 문서 안 링크 1,373개 중 그림·표 참조 183개를 대상 73개(그림 25, 표 48)로 바꿨습니다. 측정 보고의 179개보다 많은 4개는 측정이 글자 모양으로 분류하지 못한 진짜 참조입니다(줄을 넘어 링크 상자 둘로 나뉜 `Table n` 둘과 `Figure X.n` 하나, 링크 상자가 글자 일부만 덮은 `Figure n` 하나). 그래서 대상도 하나 많습니다. 원본 쪽과 대조해 리치오 표시가 원문 글자와 다른 것 0, 잘못 바꾼 것 0입니다(번호 앞 빈칸이 U+00A0인 것만 다름). 바꾸지 못한 그림 참조 링크 3개는 모두 같은 그림을 가리키며, 그 그림은 영역을 찾지 못해 캡션이 그림에 붙지 않았거나 링크 목적지가 쪽 끝·제목을 가리킵니다. 캡션 번호를 뗀 그림·표 73개 모두 원문 번호와 리치오 번호가 같고 공식 `check`는 유효·해결되지 않은 참조 0·번호 방식 고정·번호 경고 0입니다. 제목 240, 책갈피 일치 188, 각주 정의 141, 표 캡션 48, 그림 캡션 26, 경고 75 등 다른 통계는 바뀌지 않았습니다.

**공개 표본(LSR).** 링크가 없어 글자 규칙으로 후보 5개(`Table 1`, `Table 3` 두 번, `Figure K.1`, `Figure K.2`)가 모두 같은 번호의 대상으로 바뀝니다. 그림으로 들어간 `Table L.2`와 이어지는 표의 둘째 `Table 3` 캡션은 원래 글자를 둡니다. 격리 HTTP Host에서 변환한 문서를 열어 다섯 참조가 모두 해결되어 링크로 보이고, 누르면 `Figure K.1` 그림과 `Table 3` 표가 선택되는 것을 확인했습니다. 캡처는 [문서의 참조와 대상](test/captures/figure-table-refs/document-reference.png), [그림 블록을 고른 대조 화면](test/captures/figure-table-refs/figure-selected.png)입니다. 정답 채점과 `answer-key-baseline.json`은 바뀌지 않습니다.

단위 검사는 링크 목적지 → 대상 블록, 번호·종류 일치, 같은 블록의 같은 번호 중 링크가 덮은 것 고르기, 캡션 번호 떼기, 글자 규칙의 캡션 존재·링크 없음 조건, 대상이 빠진 참조, 나누기 위치를 손 입력으로 검사합니다. SDK 통합 검사는 참조가 든 문단의 나누기·합치기·종류 바꾸기·빼기와 되돌리기가 문서 바이트를 되돌리고 `check`에 해결되지 않은 참조가 없음을 확인합니다. IEEE는 Host에서 다시 변환하지 않았고 어두운 테마·설치형 Desktop은 이번에 확인하지 않았습니다.

## 원본 쪽 그리기 실패

원본 칸과 쪽 고르기 화면의 쪽 그림이 실패하면 그 쪽 자리에만 "이 쪽을 그리지 못했습니다."와 **다시 그리기**를 보입니다(쪽 고르기 미리 보기는 "그리지 못했습니다"를 보이고 다시 보일 때 그립니다). 다시 그리기에 성공하면 안내가 사라집니다. 배율 변경·스크롤로 취소된 그리기와 화면에서 내려간 쪽은 실패로 보지 않습니다. 같은 canvas에는 이전 그리기를 취소하고 끝나기를 기다린 뒤 다시 그립니다(`page-render.mjs`, V-03). 화면 위의 오류 상자에는 닫기가 없으므로 다음에 성공한 동작(블록 고르기, 경고 이전·다음, 배율 바꾸기, 문서 열기)에서 사라집니다.

격리 HTTP Host에서 공개 표본의 한 쪽만 그리기에 실패하게 만들어, 수정 전에는 화면 전체 오류 상자가 뜨고 남는 것을, 수정 후에는 그 쪽 자리 안내만 뜨고 다시 그리기로 사라지는 것을 확인했습니다([캡처](test/captures/page-render-error/page-failed.png)). 소유자가 본 오류의 실제 종류는 재현하지 못했습니다. 큰 표준 문서에서 배율 연속 변경, 빠른 스크롤, 고친 뒤 다시 읽기, 쪽이 들어오자마자 내려가는 경합을 섞어도 나온 것은 내려간 쪽의 취소뿐이었습니다. 설치형 Desktop은 확인하지 않았습니다.

## 글자 서식과 인라인 수식

문단·목록 항목·알림 상자·각주 정의·글자 표의 칸에서 일부만 굵거나 기울어진 글자를 옮긴다. 정의 항목의 굵은 머리말도 여기에 포함된다. 경계의 빈칸과 문장부호, 낱말 중간에서 끊긴 강조, 제목과 캡션의 서식은 생략한다. 원본 글자 조각을 작성할 문장의 끝과 공백을 제외하고 맞출 수 있어야 한다. PDF 글꼴 이름에 굵기나 기울임 정보가 없으면 해당 서식을 추정하지 않는다.

첨자는 앞 글자 크기의 45% 이상 80% 미만이고 두 조각의 수평 간격이 앞 글자 크기의 −16% 이상 12% 이하일 때 검사한다. 기준선이 아래로 3.5% 이상 또는 위로 12% 이상 움직이고 그 차이가 65% 이하인 수평 글자가 대상이다. 로마자·그리스 글자 하나에 영숫자 첨자가 붙으면 인라인 수식으로 옮긴다. 위첨자 변수는 기울임 글꼴을 요구한다. 여러 글자의 곧은 첨자 낱말은 LaTeX의 `\mathrm{}`로 표시한다. 단위의 제곱·세제곱과 서수는 위첨자로, 화학식처럼 변수로 확정하기 어려운 작은 글자는 아래첨자로 남긴다. 연결할 정의가 있는 숫자 호출은 각주를 유지한다.

대조 화면에서 서식이 있는 문단도 원본 줄의 첫 글자를 찾아 나눈다. 인라인 수식은 문서 위치 한 칸을 차지한다. 줄 경계가 수식 안에 있거나 전체 글자가 대응하지 않으면 나누기를 거절한다. 분수·근호·여러 줄 식과 그림으로 들어간 기호는 기존 그림과 경고를 보고 검수한다.

격리 HTTP Host의 1440px 창에서 LSR 정의 항목의 [변환 전](test/captures/inline-styles/lsr-before.png)과 [변환 후](test/captures/inline-styles/lsr-after.png)를 대조했다. 별도의 합성 PDF로 문단과 표 칸의 수식 표시 및 합치기·나누기·되돌리기도 확인했다. SDK 통합 검사는 굵은 범위 안에서 나눈 뒤 되돌리면 저장한 문서의 바이트까지 복원되는지 검사한다.
