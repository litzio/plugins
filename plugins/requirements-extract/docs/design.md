## 1. 목표와 끝난 기준

검수된 리치오 입력 문서와 상위 요구사항 문서 묶음을 읽어, 출처와 상위 연결을 갖춘 **사람 소유의 요구사항 문서**를 만들고, 거기서 OMG ReqIF 1.2 파일을 내보낸다. ReqIF는 파생물이다. 요구사항 문서를 자동 재생성하거나 ALM에서 역수입하지 않는다. 이력·백업은 문서를 둔 저장 수단이 맡는다.

줄일 일은 후보 문장을 빠짐없이 훑는 일, 수십 개 상위 요구사항을 매번 찾아 대조하는 일, 수치·단위·관계·출처를 내보내기 때마다 재입력하는 일이다. 사람의 해석 책임을 없앤다는 목표는 두지 않는다. 비서가 먼저 전체 대상과 예외를 검토하고, 사람은 문제 묶음과 채택안을 확인한다.

첫 실사용 버전의 수락 기준은 다음과 같다. 수치는 **설계상 목표**이며 측정 결과가 아니다.

| 관점 | 통과 기준 |
| --- | --- |
| 문서 | 작은 합성 표본에서 생성 → 사람의 본문 수정·이동 → 다시 읽기 후 모든 ID·속성·관계가 보존되고 공식 `check`·canonical 왕복이 성공한다. |
| 출처 | 내보낸 모든 요구사항에 유효한 원문 요소 출처가 하나 이상 있다. 표본의 모든 출처를 입력 리치오 위치와 PDF 쪽·좌표까지 찾는다. 실패는 0건이어야 한다. |
| 처리 범위 | 후보별 채택·제외·보류와 이유가 남는다. 미탐지 확인을 위해 비서가 후보가 없는 구획도 검토한다. 미처리 구획·보류가 남으면 완료가 아니다. |
| 값 보존 | 확정 요구사항에서 보호 대상 숫자·단위·부등호의 미설명 차이 0건. 기계 검사는 의미 동등성을 보증하지 않으며 조건 범위는 비서와 사람이 확인한다. |
| 연결 | 정답 연결을 미리 만든 상위 30개·하위 60개 합성 표본에서 기대 연결이 후보 집합에 모두 포함된다. 고아·깨진 대상·순환·상위의 미연결이 전부 분류된다. |
| 재실행 | 같은 입력·정책·확정 문서로 재실행하면 확정 ID가 바뀌지 않고 이미 판단한 후보를 다시 묻지 않는다. 변경 표본은 영향을 받은 항목만 재검토한다. |
| 표준 | XSD·참조 무결성·독립 파서 왕복 통과. 두 번 내보낸 모든 Identifiable ID가 같다. StrictDoc 가져오기에서 본문·수·관계를 대조한다. |
| 도구 | 첫 검증 도구 Polarion에서 최초 가져오기 → 본문·관계 수정 → 같은 대상에 재가져오기 후 기존 항목 ID 유지, 중복 0건. 도구 없이 표준 단계만 완료했다고 보고한다. |
| 사람의 일 | 표본에서 전체 원문 순회·상위 검색 횟수와 확인 시간을 수동 기준과 비교해 기록한다. 상위 검색 시간을 절반 이하로 줄이는 것을 목표로 한다. 미달이면 검색 개선 후 실사용 수락을 재판정한다. |
| 규모 | 합성 200쪽에서 구획 단위 중단·재개, 변경 감지, 진행 수 집계가 동작한다. 전체를 한 AI 요청에 넣지 않는다. |

TestCase 작성·시험 자동화, ALM 직접 등록, 새 개정 PDF의 자동 병합은 첫 버전에 넣지 않는다. Requirement↔Requirement 연결과 누락 조회는 첫 버전의 필수 범위다.

## 2. 근거와 과거 결정의 적용

근거 링크와 읽은 범위를 [근거 목록](sources.md)에 모았다. 구현자는 공개 계약이 바뀌었는지 먼저 재확인한다.

- `docs/purpose.md`의 “근거와 결과의 연결”, “플러그인은 열린 문제를 좁힌다”를 따른다. 반복 절차는 코드, 해석은 비서, 확정은 사람이다.
- [#347](https://github.com/litzio/litzio/issues/347)의 2026-11-02 **소유자 결정**: 자동 고정 ID 하나로 시작, 사람용 관리 번호는 후속, Requirement 우선·TestCase 후속, 역할 있는 참조, 누락을 ALM 삭제로 간주하지 않음. 요구사항 문서가 기준 자료이고 변환 문서·ReqIF는 파생물이다. 출처는 NodePath가 아닌 원본 Docling 요소 참조로 남긴다. 표준 목표는 ReqIF 1.2, Polarion은 첫 검증 도구다.
- 같은 이슈의 `{requirement}` 지시문·Core 요구사항 기능은 **당시 조사안**이다. 현재 공개 네이티브 문법에 없고 이번 저장소는 플러그인이므로 채택하지 않는다. 위 소유자 결정의 의미를 일반 문서 요소로 표현한다.
- `spike/requirements-traceability` 및 태그 `spike/2026-11-11-requirements-traceability`의 `24e7e95b` 보고서를 읽었다. XSD·StrictDoc 성공은 과거 실험 기록이다. 문장 해시 기반 동일성, 최상위 단락만 탐색, 일반 텍스트 본문의 한계를 답습하지 않는다. 코드를 가져오지 않는다.
- AI 제안 스파이크(2026-11-01)의 교훈은 제안·확정 분리와 입력 변경 시 적용 거부다. 스파이크 API를 사용 가능하다고 가정하지 않는다.
- Discussion #766의 원문 보존·대응표·교정과 #739의 공통 문서 계약 방향은 역사적 맥락이다. 과거 DB·내장 모듈·전용 화면 계획을 현행 SDK 계약으로 취급하지 않는다.

앞 단계 계획 브랜치 `docs/docling-to-litzio-plan`은 확인 시 원격 ref와 파일이 아직 없었다. 변환 계약과 계획은 병렬 작성 중이다. 아래 5절은 **소비자가 요구하는 정보**이지 합의된 파일 스키마가 아니다. `contracts/`와 진행 기록은 이 PR에서 수정하지 않는다. 계약 합의 전 출처 어댑터 구현은 막히지만 작은 합성 문서의 모델·내보내기는 시작할 수 있다.

## 3. 요구사항 모델과 식별

### 최소 항목

| 항목 | 규칙 |
| --- | --- |
| id | `req-` + 소문자 UUID v4. 첫 채택 때 코드가 발급해 기준 문서에 저장. AI가 만들거나 hash에서 계산하지 않는다. |
| title / body | 제목 한 줄, 본문은 아래 문서 프로파일의 블록. 고객 문장의 인용과 도출 본문을 구별한다. |
| kind | functional / performance / interface / constraint / safety. 모르면 unknown이며 확정 불가. 정보·배경은 후보 제외 사유로 분류한다. |
| level | stakeholder / system. 첫 기본값 system, 상위 묶음은 stakeholder. 이름과 허용 조합은 설정 표에 둔다(가정). |
| origin | quoted / derived. quoted는 원문 그대로, derived는 주체 변경·분해·통합 등의 도출 근거가 필수다. |
| strength | mandatory / recommended / permitted. shall·해야 한다 등의 원문 강도와 대응. 번역 표는 설정으로 둔다. |
| sources | 1개 이상의 출처 레코드. 원문 문장·표 셀 범위와 검토 당시 해시를 포함한다. |
| relations | `refines`(하위 → 상위), `relatesTo`(대칭 관련) 역할별 ID 참조. `verifies`는 예약만 하고 첫 버전은 거부. |
| status | draft / reviewed / confirmed / obsolete. 비서 검토가 reviewed, 사람이 확정한 경우만 confirmed. |
| verification | test / analysis / inspection / demonstration / undecided. undecided는 검토 문제로 남긴다. 시험 사례 자체는 만들지 않는다. |
| rationale | 도출·연결·수치 변경 예외의 이유. 출처를 대체할 수 없다. |
| confirmedDigest | 사람이 확정한 의미 모델의 SHA-256(키를 사전순 정렬한 UTF-8 JSON, 본문은 공식 read model의 의미 값). id·본문·속성·출처·관계를 포함하고 status·이 값 자체·표시 위치는 제외한다. |

확정 해시가 현재 내용과 다르면 표에 confirmed가 남아 있어도 유효 상태는 reviewed다. 사람의 일반 편집을 감지하며 자동 재확정하지 않는다. 해시는 무결성·변경 감지용이며 서명이나 감사 증명은 아니다. 정식 내보내기에는 유효한 확정 해시가 있는 confirmed와 obsolete만 허용한다. 전체 대상에 draft·보류·verification=undecided가 있으면 정식 내보내기를 막는다. 시험용 내보내기는 별도 표시와 진단을 붙이고 실사용 파일로 오인시키지 않는다.

문서별로 `set-<uuid>`를 본문 속성 표에 둔다. 문서 집합 안에서 요구사항 ID는 전역 유일하다. 문서 집합은 사용자가 선택한 상대 경로 목록이며 매번 같은 집합 전체를 검사한다. 다른 파일의 역방향·하위 목록은 계산하고 저장하지 않는다. refines의 순환·자기 참조는 오류, level 역전은 검토 경고다. relatesTo는 양쪽 UUID를 사전순으로 정렬해 한 관계로 저장한다.

### ID 수명과 재처리

- 제목·본문 수정, 파일 이름·위치 변경, 같은 항목을 다른 기준 문서로 이동해도 id는 유지한다. set ID와 요구사항 ID를 파일 경로에서 만들지 않는다.
- 복제는 새 ID다. 손 복사로 생긴 중복은 진단하고 내보내기를 막는다. 전체 문서를 다른 논리 세트로 복제할 때도 새 set ID와 항목 ID가 필요하다.
- 재실행은 **기준 문서에서 읽은 ID**를 재사용한다. 원문 문자열 유사도만으로 새 요구사항을 기존 항목에 덮어쓰지 않는다.
- 처음 채택할 때 후보 키와 발급 ID의 대응을 작업 원장에 남긴다. 원장은 확정 문서에서 복구할 수 있는 대응을 우선한다. 문서·원장 간 불일치는 자동 생성 중단·복구 검토로 보낸다.
- 1→N 분해: 기존 항목을 obsolete로 유지하고 새 항목들에 새 ID를 발급한다. N→1 통합도 새 ID와 대체 관계의 설명을 남긴다. 첫 버전의 관계 역할을 늘리지 않고 rationale에 대체 전 ID를 기록한다. 단순 문장 손질은 분해로 보지 않는다.
- 삭제는 물리 제거보다 obsolete를 기본으로 한다. 내보내기에 남겨 상태를 알리며 삭제 요청을 보내지 않는다. 물리 제거는 끊어진 참조 진단, 내보내기 차이 보고에 나타난다.
- 새 PDF 개정은 별 입력으로 취급한다. self_ref가 같아도 같은 원문 요소라고 판단하지 않는다. 개정 간 대응은 후속 사람이 검토한다.

원문 한 요소가 여러 요구사항의 출처가 되거나 여러 요소가 한 요구사항의 출처가 될 수 있다. 출처 중복은 허용한다. derived 본문은 여러 원문을 통합할 수 있지만, 각 조건이 어느 출처에서 왔는지 보호 토큰 대응에 남겨야 한다. 원문 인용은 읽기 전용 근거이며 사용자가 고치는 대상은 도출 본문이다.

## 4. 리치오 문서 표현

### 대안과 판정

| 대안 | 판단 |
| --- | --- |
| 전용 requirement 지시문 | 네이티브 admission 확장이 필요. 플러그인이 Core 요구사항 의미를 요구하게 되므로 제외. |
| 사용자 frontmatter·HTML 주석·JSON 코드 블록에 항목 저장 | frontmatter는 허용 키가 고정이다. 숨긴 내용·JSON만으로는 일반 문서 편집과 독해가 어렵다. 기준 자료로 쓰지 않는다. |
| 한 표의 한 행에 요구사항 전부 저장 | 현행 셀은 줄바꿈·중첩 블록을 담지 못한다. 긴 본문과 그림에 부적합하다. 목록 표는 파생 조회로만 쓴다. |
| **레이블 제목 + 속성 표 + 일반 본문** | 현재 일반 요소만 사용, 본문 직접 편집 가능, 제목 경계로 다시 읽을 수 있다. 이 안을 채택한다. |

문서 프로파일 v1은 다음과 같다. 일반 Litzio 문서인 것과 이 프로파일을 만족하는 것은 별도 검사다. 네이티브 valid가 업무 데이터의 유효성을 뜻하지 않는다.

1. frontmatter는 `litzio: 1`, 선택 `title`만 사용한다. 임의 메타데이터는 넣지 않는다.
2. 문서 첫 H1 아래 첫 2열 표(`필드`, `값`)에 `profile=requirements-extract/1`, `setId`, `exportNamespace`, `defaultLevel`을 쓴다. 이어 입력 문서 등록 표를 둔다(아래 5절).
3. 요구사항은 H2마다 하나. 바로 앞 명시 target이 요구사항 id와 같다. 첫 2열 표는 속성 표이고 필수 행은 id, kind, level, origin, strength, status, verification, rationale, confirmedDigest다. target과 id가 다르면 오류다.
4. 속성 표 뒤 H3 `본문`부터 다음 H3 전까지가 body다. 일반 문단·목록·직사각형 표·수식·그림 중 공개 계약이 지원하는 것만 쓴다. H3 `출처` 아래 고정 열의 출처 표, H3 `연결` 아래 관계 표를 둔다. 빈 연결 표는 헤더만 만든다. H3 `검토 메모`는 선택이며 내보내지 않는다.
5. 다음 H2에서 항목이 끝난다. 본문 안에 다른 H2/H3를 넣지 않는다. 요구사항 외 설명은 H1 도입부에 둔다. 알려지지 않은 필드·누락·중복 행·모호한 경계는 보존하고 오류로 알린다. 조용히 무시하지 않는다.
6. 표 값은 한 줄 텍스트. `|`·역슬래시 등은 공개 문서 작성 연산의 셀 인코딩을 따른다. 임의 문자열 분할로 Markdown 표를 읽지 않는다.

예시(아직 CLI 수락을 실행하지 않은 **작성 예**):

````markdown
---
litzio: 1
title: 합성 시스템 요구사항
---

# 요구사항 문서

| 필드 | 값 |

| setId | set-36b7797a-67e0-4cad-8121-bb50bdc9379e |
| exportNamespace | 8ecdb7b1-138e-49c8-a1e1-89a56f63a274 |
| defaultLevel | system |

| sourceKey | artifactDigest | nativeFile | nativeDigest | mapFile |
| --- | --- | --- | --- | --- |
| src-a | sha256:원본결과해시 | input.md | sha256:검수문서해시 | provenance.json |

(req-1593c157-e436-422d-a7aa-bee9aac26c26)=
## 출력 차단 지연

| 필드 | 값 |
| --- | --- |
| id | req-1593c157-e436-422d-a7aa-bee9aac26c26 |
| kind | performance |
| level | system |
| origin | derived |
| strength | mandatory |
| status | draft |
| verification | test |
| rationale | 합성 문장의 주체를 시스템으로 명시함 |
| confirmedDigest | 미확정 |

### 본문

시스템은 차단 요청 후 **10 ms 이하**에 출력을 차단해야 한다.

### 출처

| sourceKey | elementRef | selector | quote | quoteDigest |
| --- | --- | --- | --- | --- |
| src-a | #/texts/12 | full | 차단 요청 후 10 ms 이하에 출력을 차단해야 한다. | sha256:원문조각해시 |

````

예시의 해시 자리표시는 실제 프로파일 검사에서 거부한다. 출처 원문·ID를 손으로 바꿨을 때는 현재 입력과 재대조한다. 항목 내부의 같은 문서 참조는 `{ref}`를 쓸 수 있지만 **관계 표가 업무 관계의 정본**이다. 타 문서 참조는 현재 semantic cross-reference가 지원하지 않으므로 대상 ID를 텍스트로 기록하고 플러그인이 선택한 문서 집합에서 찾는다. URL 모양으로만 연결 성공을 판단하지 않는다.

생성은 `saveDocument({name, authoring, ...})` 또는 공개 CLI `create`의 공식 쓰기 경로를 사용한다. 읽기는 공개 `inspect --format json`의 의미 read model로 한다. 그 출력으로 필요한 target·표 셀·본문 경계를 얻을 수 있는지는 첫 구현 PR의 선행 검증이다. 부족하면 내부 parser나 직접 정규식 parser를 만들지 않고 10절의 범용 능력으로 요청한다.

## 5. 출처 사슬과 앞 단계에 요구하는 정보

요구사항 sources → 입력 아티팩트 식별 + 원본 `self_ref` + selector → 현재 검수 리치오 위치 → 고정 원본 PDF의 쪽·bbox로 잇는다. NodePath·문장 순번·인용 해시는 **식별자 아님**이다. self_ref 역시 한 Docling 결과 안에서만 의미가 있으므로 원본 결과 digest와 함께 쓴다.

앞 단계에 요구하는 최소 정보는 다음과 같다. 파일 이름·스키마는 앞 단계 계약과 합의해서 정하며, 이 문서의 `provenance.json`은 예시 이름이다.

| 정보 | 필요한 이유·검사 |
| --- | --- |
| 원본 PDF와 고정 Docling 결과의 digest, 문서 식별, 상대 파일 참조 | self_ref 충돌 방지와 원본 확인. 원본 파일을 찾지 못하면 출처 확인 불가. 절대 경로나 실행 환경 정보는 문서에 저장하지 않는다. |
| 생성 리치오 문서 revision과 complete/provenance 결합 | v1은 생성 시점 unreviewed다. bytes/revision 불일치는 거부하고 검수본·편집 후 갱신은 보류한다. |
| 원본 self_ref → 현재 리치오 요소/범위의 다대다 대응 | 병합·분할된 문단·표도 추적. 현재 NodePath·레이블·셀 범위는 이 대응표의 위치 값이지 영속 ID가 아니다. |
| 원문 물리 쪽·TOPLEFT pt bbox·쪽 크기 | v1 regions/pages를 보존한다. 회전/인쇄 쪽은 null이면 미확인으로 표시하며 추측하지 않는다. |
| 원문 인용과 그 문장이 문서에 표현된 텍스트 | 숫자 검사와 교정 차이 구별. 교정으로 바뀐 값은 검수 근거가 필요하다. |
| 원본 계보·disposition·손실·bindingState | v1의 생성 계보만 소비한다. 교정 이력/검수 완료 정보는 없으며 미검수·손실·삭제/불확실 상태를 전파한다. |
| sourceCell·tableModel의 원래 범위/머리 기여/병합/검수 표시 | 원문 값·span을 보존한다. regionPrecision=table이며 셀별 쪽을 추측하지 않는다. 반복된 숫자 확정 전에 사람 검수가 필요하다. |

selector는 `full`, `text:<start>:<end>`(검토 당시 요소 텍스트의 Unicode code point, 0부터 반개구간), `cell:<row>:<column>`(0부터) 중 하나다. 표·목록에서 세부 위치가 없으면 full로만 허용한다. quoteDigest는 UTF-8 원문 조각의 전체 SHA-256이며 공백·기호를 정규화하지 않는다. 셀 selector의 실제 어댑터 의미는 앞 단계와 합의 전까지 가정이다.

요구사항 문서를 손질해도 출처 표와 ID가 남으면 사슬은 유지된다. 본문 변경은 확정 해시를 무효화한다. 입력 리치오 문서를 손질하면 대응표를 갱신한 검수본과 새 revision을 명시적으로 채택해야 한다. 그전에는 PDF 출처를 과거 입력 기준으로만 표시하고 현재 위치 연결은 “낡음”이다. 문장이 우연히 같다고 자동 재연결하지 않는다. 요소가 사라지면 broken-source, 파일 누락은 missing-artifact로 표시한다. 해시 일치만으로 의미 정확성을 주장하지 않는다.

요구사항 문서 복사·이동 시 등록 표의 상대 참조를 다시 확인한다. 파일을 찾지 못하면 ID를 유지한 채 중단한다. 원문 범위를 출력에 중복 기록할 수 있으나 기준은 원본 요소 참조다. 앞 플러그인의 코드·비공개 함수를 호출하지 않고 계약 파일만 읽는다.

## 6. 도출 절차: 코드가 좁히고 비서가 판단한다

첫 버전은 플러그인이 별도 AI API를 부르지 않는다. 리치오 비서가 스킬을 따라 공개 플러그인 작업을 호출한다. 아래 작업 이름은 **설계 이름**이며 현재 플랫폼의 기존 명령이 아니다. Host 처리 코드는 AI 없이 단위 검사할 수 있어야 한다.

| 단계 | 코드의 일 | 비서에게 주는 자료·선택지와 의무 |
| --- | --- | --- |
| 0 입력 고정 | 문서 집합·revision·대응표·프로파일 검사, 검수 문제 표시 | 목적·대상 수준·문서 역할을 확인. 미검수 입력의 검수/확정은 보류, 근거 없이 검수 완료로 만들지 않음. PR3 초안 제안 판단은 16절 경계로만 진행. |
| 1 후보 수집 | shall/must/should/may, 해야 한다/금지/이내, 수치 범위, 표 행·셀, 의무 목록을 탐지. 후보 없는 구획도 목록화 | 문장뿐 아니라 앞뒤 단락·절 제목·표 머리글·단위·각주·참조 대상 제공. 채택 / 비요구사항 / 중복 후보 / 문맥 부족 / 보류 중 선택, 제외 이유 필수. |
| 2 분류·분해 | 선택지 enum·출처 존재 검사, ID 발급 준비 | kind·level·strength·verification, quoted/derived 선택. 한 의무 유지 / 여러 의무 분해 / 여러 출처 통합 선택. 조건·주체·반응·예외를 명시. 모르면 unknown·보류. |
| 3 값·품질 검사 | 보호 토큰 대응과 중복 텍스트·대조 표현 탐지 | 동일 / 의도된 차이 / 충돌 / 모호 / 판정 불가. 중복은 통합·별개·관련 중 선택. 모순을 AI가 자동 해소하지 않음. |
| 4 상위 연결 | 7절의 순위 후보와 누락 계산 | refines / relatesTo / 해당 없음 / 추가 후보 요청 / 보류. 왜 충족하는지·부분 충족인지 설명. 비슷하다는 이유만으로 refines 금지. |
| 5 비서 검수 | 항목·구획의 처리 수, 오류·미처리·보류 집계 | 채택안 전체를 원문과 재대조. 후보 없는 구획에서 놓친 의무도 제안. 확인된 것과 의심을 분리해 reviewed로 제출. |
| 6 사람 확정 | 확정 순간 최신 revision·해시 재검사, 새 문서 또는 확정값 안내 생성 | 문제 묶음 우선, 일반 채택안도 묶음 확인. 사람이 확정한 항목에만 confirmedDigest 기록. |
| 7 내보내기 | 기준 문서를 다시 읽어 전체 검사, ReqIF·검증 보고서 생성 | 오류를 임의 완화하지 않음. 내보내기 전 입력 집합과 차이 보고를 설명. |

제안 구조는 candidateKey, inputDigests, decision, choices, bodyBlocks, sources, relations, rationale, protectedTokenMappings, unresolved를 필수로 갖는다. 비서는 제공된 후보/출처/대상 ID만 참조한다. 추가 출처가 필요하면 코드의 읽기 작업으로 수집하고 다시 제안한다. 자유 텍스트만 반환한 결과나 enum 밖 선택은 형식 오류다. 재시도는 해당 구획에 한정하고 계속 실패하면 보류한다. 확률 점수로 확정하지 않는다.

### 보호 토큰

코드는 원문과 제안에서 수 부호·소수·범위·지수·단위·비교 기호·부정 표현을 원문 위치와 함께 추출한다. `≤`와 `<`, `-`와 `−`, `0.10`과 `0.1`, `ms`와 `s`를 동일시하지 않는다. 검색용 정규화와 내보내기 본문을 분리한다. 각 토큰에 출처 occurrence를 연결하고 추가·삭제·바꿈을 보고한다. 여러 출처 통합·분해에서는 단순 multiset 비교 대신 각 결과의 조건 범위와 원문 occurrence 대응을 검사한다.

명시적인 수치 환산·반올림은 첫 버전에서 허용하지 않는다. 오탈자라 보여도 원문 또는 앞 단계에서 검수한 값을 유지하고 예외로 올린다. 값이 같아도 조건·부정·적용 대상이 달라질 수 있으므로 토큰 통과만으로 확정하지 않는다. 표의 단위와 각주가 빠지면 문맥 부족이다.

### 수백 쪽의 진행·재실행

처리 단위는 절·표 묶음이며 기본 상한은 후보 20개 또는 입력 텍스트 12,000자(가정, 설정값)다. 표가 넘으면 머리글·공통 주석을 각 조각에 반복 제공하고 절단 경계를 기록한다. 앞뒤 문맥이 잘리면 추가 읽기 전 보류한다. 전체 쪽·구획·후보 수와 현재 구획, 검토 완료·확정·보류 수를 화면에 보여 준다.

작업 원장은 입력 digest, 정책 버전, 구획 키, 원문 참조, 후보 결정과 이유, 발급 ID, 제안 digest, 완료 상태를 JSON 파일로 보관한다. 작업별 불변 checkpoint 파일을 만들고 재개 시 마지막 유효 checkpoint를 읽는다. 캐시는 원장과 구분한다. 원장에는 제외 결정도 남으므로 문서와 함께 저장 수단에서 버전 관리한다. 숨은 DB를 기준 자료로 만들지 않는다.

동일 후보 키는 원본 결과 digest + self_ref + selector + quoteDigest + 탐지 규칙 버전이다. 같은 입력이면 채택·거절·보류 결정을 재사용하고 미처리만 진행한다. 정책 변경은 후보 탐지만 다시 실행하고 일치하는 판단 근거는 재사용 여부를 표시한다. 입력·출처·상위 항목이 바뀐 것은 영향 항목의 검토만 무효화한다. hash는 변경 감지이며 identity가 아니다.

기존 요구사항 파일 수정은 공개 화면 저장 계약에 없다. 따라서 처음에는 **새 기준 문서 초안**을 만들고 이후에는 기존 ID를 참조한 **변경 제안 문서**를 새 파일로 만든다. 사람이 기존 문서를 편집한 뒤 다시 검사한다. “확정” 버튼이 기존 문서를 갱신했다고 표시하지 않는다. 기존 기준 문서의 확정은 코드가 계산한 digest를 확정 안내에서 받고 사람이 속성 표의 status·confirmedDigest에 반영한 뒤 다시 읽어 확인한다. 문서가 안내 이후 바뀌면 해시가 맞지 않아 확정되지 않는다. 코드가 원문 파일을 직접 덮어쓰는 우회는 금지한다. 중단은 다음 구획 실행을 멈추고 마지막 checkpoint를 보존한다. 늦은 응답은 다른 revision에 채택하지 않는다.

## 7. 연계 상위 요구사항 찾기와 누락 조회

첫 버전에 **선택한 여러 문서 사이 한 단계의 Requirement↔Requirement 추적**을 넣는다. 먼저 상위 문서도 같은 프로파일의 항목으로 만들고 확인한다. 일반 원문 문장은 sources이고, 상위 요구사항 ID는 refines 대상이다. 둘을 혼동하지 않는다. TestCase와 verifies는 후속으로 같은 역할 체계에 추가한다.

1. 코드가 상위 수십 항목 전체를 색인한다. 제목·용어·주체·인터페이스·수치·원문 참조를 사용한 결정적 어휘 검색으로 기본 상위 5개와 그 이유를 보여 준다. 용어 동의어는 작은 설정 표로 시작하고 벡터 DB는 도입하지 않는다.
2. 비서는 후보 상위의 **전체 본문과 적용 조건**을 읽고 연결을 제안한다. 상위가 수십 개뿐이므로 절 단위 검토 마지막에 상위 전체 목록도 훑어 검색 탈락을 보완한다. 후보 순위는 정답이 아니다. “없음”을 고르려면 상위 범위를 확인한 이유를 쓴다.
3. 연결은 하위→상위 refines다. 하나가 여러 상위를 가리킬 수 있다. 부분 충족은 관계 이유와 남은 범위를 문제로 표시한다. 존재하는 연결 수만으로 충족 완료를 계산하지 않는다.
4. 코드가 역방향과 누락을 계산한다: 상위에 하위가 없음, 하위에 상위가 없음, 깨진 대상, 중복 ID, refines 순환, 대상 revision 변경, 미처리 원문 후보. 각각 실제 누락 / 범위 밖 / 정당한 독립 요구사항 / 보류로 비서가 분류하고 사람이 확인한다. 범위 밖은 이유 없이 숨길 수 없다.
5. 조회는 문서 집합·revision·제외 기준을 표시한다. 선택 범위 밖의 대상은 “없음” 대신 “범위 밖·미확인”이다. 변경된 상위가 있으면 본문이 같은 하위라도 관계를 재검토한다.

처음부터 그래프 화면은 필요 없다. 상위별 하위 수·문제 수를 가진 표와 선택 항목의 근거·관계 목록이면 된다. #347의 두 문서 연결과 누락 문제를 이 단계로 해결하고 이후 TestCase가 들어오면 시험 미연결 조회를 더한다. 첫 버전만으로 프로세스 평가의 추적성 전체를 충족한다고 주장하지 않는다.

## 8. ReqIF 1.2 내보내기

### 표준 모델 대응과 범위

목표는 OMG ReqIF 1.2와 prostep ivip Implementation Guideline v1.10의 보수적 공통분모다. 아래는 설계 매핑이다. 표준의 실제 클래스는 `SpecObjectType`·`SpecificationType`·`SpecRelationType`이며 SpecType은 공통 기반이다. 표준 세부는 [S1], 관례는 [S2]를 따른다.

| 문서 모델 | 내보내기 |
| --- | --- |
| requirement id | SpecObject.IDENTIFIER |
| 제목·본문 | `ReqIF.Name`·`ReqIF.Text`, 각각 XHTML 속성 |
| kind·level·strength·status·verification | 사용자 정의 Enumeration 속성(같은 이름, `ReqIF.` 접두사 없음) |
| origin·rationale | 사용자 정의 Enum·XHTML 속성 |
| sources | `SourceReferences` String(정규 순서 JSON), `SourcePages` String(사람용). 출처는 SpecRelation으로 만들지 않음. |
| setId·문서 제목 | Specification.IDENTIFIER·`ReqIF.Name` |
| 항목 순서 | Specification의 평평한 SpecHierarchy 목록 |
| refines·relatesTo | 역할별 SpecRelationType, SOURCE와 TARGET은 실제 SpecObject 참조 |

첫 내보내기 계층은 평평하게 정한다(가정). 제목 계층은 문서 읽기 편의이며 상하위 업무 관계는 SpecRelation이다. 표준의 주요 근거 절은 10.8.32(Identifiable), 10.8.37–44(계층·항목·관계·유형), 10.8.20(XHTML)이다. 선택 문서 집합에 관계 대상이 없으면 정식 내보내기를 막는다. 파일 안에 없는 객체를 가리키는 관계를 만들지 않는다. 여러 문서면 하나의 패키지에 여러 Specification과 공통 유형을 넣는다.

사람용 번호를 처음부터 추가하지 않는다. `ReqIF.ForeignID`는 후속 관리 번호용으로 비워 둔다. 이를 Polarion 갱신 키로 요구하는 환경이면 고정 ID만으로 갱신된다는 가정을 폐기하고 매핑을 재검토한다. 제목을 갱신 키로 쓰지 않는다.

### 식별자·시각·누락

프로파일의 고정 export namespace(UUID 하나)는 첫 기준 문서의 세트 속성 표에 저장한다. 함께 내보내는 문서 세트는 같은 namespace를 사용하며 다르면 병합하지 않고 설정 확인을 요구한다. 항목 ID는 그대로 쓰고, 유형·속성 정의·datatype·열거값·Specification·SpecHierarchy·관계 등 나머지 ID는 namespace + 고정 semantic key의 UUID v5에 `x-`를 붙여 만든다. hierarchy key는 setId+요구사항 id, 관계 key는 역할+정규 source/target ID다. 순번·제목·파일 경로는 쓰지 않는다. 열거값 key도 표시 이름과 분리한다. namespace·정책 변경은 내보내기 차이로 명시하고 자동 갱신하지 않는다.

`LAST-CHANGE`는 항목 의미 digest가 바뀌었을 때만 갱신한다. 생성된 export manifest에 ID별 digest·시각과 전체 대상 목록을 남기며 재실행에 재사용한다. manifest는 파생 이력이고 분실 시 ID는 복구 가능하지만 기존 변경 시각은 복구 불가라고 알린다. 헤더 생성 시각은 달라도 된다. 본문·관계·유형·열거값의 모든 IDENTIFIER를 비교한다.

정식 내보내기는 세트 전체다. 이전 manifest와 비교해 빠진 ID를 보고하고 자동 삭제하지 않는다. Guideline §2.16의 수신 도구 삭제 관례와 #347의 삭제 금지 사이 차이가 있으므로 **누락을 수신 도구가 어떻게 처리하는지 확인되기 전 반복 가져오기를 실사용 승인하지 않는다**. `ReqIF.ForeignDeleted`도 첫 버전에서는 보내지 않는다. obsolete 상태를 명시적으로 보존한다.

### 본문·첨부 처리

XHTML은 네임스페이스를 명시하고 문단·굵게·기울임·위아래 첨자·목록·기본 직사각형 표를 사용한다. 제목 h1–h6·스크립트·임의 HTML을 내보내지 않는다. 사용자 원문을 XML 문자열에 직접 이어 붙이지 않고 XML 라이브러리로 escape한다. 세부 서식은 [S2] §2.7–2.8의 관례를 따른다.

- 단순 표는 행·머리글·셀 값의 왕복을 검사한다. 병합 셀은 앞 단계 검수 후 표현을 사용하고 원문 손실 경고를 계승한다.
- 그림은 로컬 PNG를 MIME 유형과 대체 텍스트를 가진 XHTML object로 참조하고 `.reqifz`에 상대 경로로 포함한다. 원격 URL을 자동 다운로드하지 않는다. 파일 누락·해시 불일치는 오류다.
- 수식은 정확한 LaTeX 원문을 별도 `FormulaSource` 속성(여러 수식은 ID별 JSON)에 보존한다. 첫 버전에서 공개 경로로 검증 가능한 PNG 렌더링을 확보하지 못하면 수식 포함 항목의 정식 내보내기는 막는다. `$...$` 문자열만 넣고 수식 지원으로 보고하지 않는다. 사람이 동의한 PNG와 원문을 함께 내보내는 경로를 수락 시험한다.
- 같은 원칙으로 Mermaid는 검증된 PNG가 없으면 차단한다. unsupported 블록을 텍스트로 조용히 평탄화하지 않는다. 단순화가 필요하면 명시 검토와 isSimplified 처리 및 차이 보고가 필요하다.

ReqIF XML은 UTF-8·XML 선언, 첨부가 없으면 `.reqif`, 있으면 Deflate ZIP `.reqifz`다. String maxLength는 65,535로 시작하며 초과는 절단하지 않고 오류다. 필수 속성과 enum 값의 유일성·존재성을 검사한다. 임의 vendor extension은 첫 버전에 넣지 않는다.

### 도구 없이 하는 검증과 Polarion 수락

도구 없는 검사도 문자열 스냅샷만으로 끝내지 않는다. 공식 reqif.xsd와 XHTML driver 의존 스키마를 고정 출처·해시와 함께 검증 도구에 두고 외부 네트워크 없이 XML을 검사한다. 이어 독립 `reqif` parser의 parse→unparse→parse, 본문·관계·첨부의 의미 비교, StrictDoc의 실제 가져오기와 항목 수·ID·한글·표를 확인한다. 이 왕복은 제품의 ReqIF 역수입 기능이 아니다. 스파이크의 성공을 이번 결과로 재사용하지 않는다.

Polarion 수락 절차는 다음과 같다. [S3]의 매핑 안내는 기능 근거이며 실제 환경의 갱신 보증이 아니다.

1. 버전·격리 프로젝트·Work Item 유형·필수 필드·관계 역할을 기록하고 매핑 설정을 고정한다. ReqIF ID를 보존할 필드도 확인한다.
2. 합성 두 문서·요구사항 6개·다대다 관계·한글·표·PNG를 가져온다. SpecObject ID와 생성 Work Item ID 대응을 기록한다.
3. 리치오 기준 문서의 제목·본문·상태·관계를 수정하고 동일 ID로 내보낸다. 같은 대상에 갱신 가져오기, 항목 수·내부 ID·관계·첨부·서식을 비교한다.
4. 항목 추가·obsolete·누락을 각각 시험한다. 누락 시 삭제되지 않는 설정을 확인할 수 없으면 반복 교환 수락 실패다. ALM의 수동 수정이 다음 가져오기에서 어떻게 되는지도 기록한다. 본 설계는 리치오 기준이므로 자동 양방향 병합하지 않는다.
5. XSD 통과와 Polarion 수락을 별도 결과로 남긴다. 다른 ALM의 호환은 실제 시험 전 미확인이다.

### 라이브러리 판정

`strictdoc-project/reqif`는 Python ReqIF 모델·parser·writer·passthrough를 제공하고 Apache-2.0이다([S4]). **검증 도구로 채택**하고 구현 PR에서 버전·해시를 고정한다. 실행 제품에 묶는 것은 이번 기본안에서 채택하지 않는다. Node Host에 Python 런타임과 의존성을 함께 배포·검증해야 하기 때문이다. 라이선스상 포함은 가능하되 LICENSE·NOTICE와 전이 의존성 고지가 필요하며 기술적으로 JS 번들만으로 넣을 수 있는 것은 아니다.

제품은 Node에서 묶어 쓸 수 있는 XML builder로 좁은 표준 매핑을 작성하는 안으로 진행한다(가정). 후보는 MIT `xmlbuilder2`([S5])이며 버전·번들 크기·전이 라이선스는 구현 때 고정한다. XML 문법 parser를 새로 만들지 않는다. ReqIF 모델 전체를 일반화하지 않고 위 매핑만 구현하며 독립 Python 도구로 잘못된 자체 가정을 잡는다. 현재 조사로 적합한 JS ReqIF 전용 라이브러리를 확인하지 못했으며 “없다”고 단정하지 않는다.

## 9. 사람의 순서·최소 화면·비서 스킬

하나의 React 화면에서 두 모드만 제공한다. 공개 Button·Input·Table·Notice·Toolbar·SummaryCard와 배치 부품을 기본으로 쓰고, 앱의 비공개 편집기·대조 렌더러를 가져오지 않는다.

1. **입력과 진행**: 검수 입력·상위 세트·기존 기준 문서를 선택하고 입력 검사 결과를 본다. 새 도출/재개, 구획 진행·중단, 오류 수를 제공한다. 비서가 없으면 자동 도출은 진행되지 않지만 입력 검사·기존 문서 검사·내보내기는 가능하다.
2. **검토와 내보내기**: 기본은 보류·값 차이·출처 문제·연결 누락의 묶음 표다. 한 항목 선택 시 원문 인용/절/표 문맥, 도출 본문, 보호 값 차이, 상위 후보와 이유를 나란히 보여 준다. 정상 검토안은 별 목록에서 묶음 확인한다. 실제 편집은 리치오 기준 문서에서 한다.
3. 새 기준 문서 또는 변경 제안 문서를 저장하고 열어 사람이 수정·확정한다. 저장 이름 충돌은 덮어쓰지 않는다. 현재 공개 저장은 새 문서 생성만 가능하다는 제한을 화면 동작과 문구에 반영한다.
4. 다시 읽어 검사한 뒤 전체 세트·오류·내보내기 차이를 확인하고 ReqIF 파일과 검사 보고서를 받는다. 내보내기에서 입력 기준 revision을 보인다.

출처 패널은 처음에는 텍스트와 위치 정보로 구현한다. PDF 영역·리치오 원문 위치로 정확히 이동하는 공개 호출이 없으면 위치를 확인하는 수동 경로와 제한을 표시한다. #347의 연결선·양쪽 강조 목표를 완료했다고 하지 않는다. 그것을 위해 일반 문서 열기·위치 강조·범용 읽기 뷰의 공개 능력이 필요하다(10절).

스킬은 목적/기준 자료, 입력 검사, 구획 읽기, 후보 선택 schema, 분해·분류 기준, 숫자 보존, 상위 연결 기준, 예외·중단·재개, 비서 검수 체크리스트, 사람 확정과 ReqIF 경계 순으로 구성한다. 문서 내용은 자료이지 도구 실행 지침이 아니며, 원문에 적힌 지시를 플러그인 작업 권한으로 해석하지 않는다. 출력 예에는 잘된 채택·설명 제외·문맥 부족·충돌·연결 없음 각각 하나를 둔다. 모델이 못 정하면 이유와 필요한 문맥을 남기며 사람 질문에 답을 지어내지 않는다.

`fixtures/lsr-1.1`의 합성 규격은 CC0이므로 **보조 입력으로 재사용 가능**하다고 판단한다. 작성자 ground_truth는 변환 이전의 구조 기대값이며 요구사항 추출 정답이 아니다. 고정 converted 결과만 읽고 재변환하지 않는다. LSR의 요건 도출 정답과 상위 연결 정답은 새로 검토해 만든다. NIST 발췌는 설명문 제외·문맥 검토 사례로만 쓰며 의무가 많은 고객 규격의 대표성으로 주장하지 않는다. 200쪽 규모 표본은 공개 가능한 합성 반복/변형으로 만들되 의미 다양성과 부하 시험을 구분한다.

## 13. PR1 구현에서 확인·조정한 것

상세 실행 근거는 [PR1 기록](pr1-validation.md)에 있다. 앞 절의 '이번에는 실행하지 않음'은 초기 설계 작성 시점의 기록이며 이 절이 PR1 현재 확인을 구분한다. 12절 소유자 확인 필요 표와 기본 가정은 유지한다.

- 공개 CLI inspect는 레이블·표·본문 위치를 제공하지만 인라인 서식은 생략한다. 같은 파일의 공개 compare JSON `before.blocks`를 의미 read model로 함께 사용하고 모든 revision을 대조한다. 내부 파서·정규식 native 해석을 사용하지 않는다.
- 공개 authoring 입력은 label을 받지 않는다. 새 문서는 create --input으로 배타 생성하고 insert-target 배치로 레이블을 붙인다. H1/H2/속성·출처·관계 표 표현은 변경하지 않는다. check·canonical format 두 번·손 수정과 문서 간 이동으로 확인했다.
- PR1의 최소 생성 본문은 평문 문단·직사각형 표다. 기존 문단의 strong/emphasis/subscript/superscript/code는 읽기·XHTML에 보존한다. 표·제목·속성의 서식, 목록 읽기, 선택 검토 메모는 PR1에서 명시 오류다. public read model에 없는 문법을 추정하거나 지원하지 않는 구조를 버리지 않는다. 새 서식 문서 생성은 후속이며 authoring은 content 대신 text를 받는다.
- 확정 digest는 공식 의미 본문을 사용하며 위치·유효 상태·confirmedDigest를 제외한다. 표본의 사람 재확정은 시험 코드에서 명시적으로 모델링했고 제품의 자동 확정은 없다.
- Specification ID는 8절 식별자 정책의 UUID v5(namespace + specification:setId)를 사용한다. 표의 setId→Specification.IDENTIFIER는 이 안정적 대응을 뜻하며 setId 문자열을 직접 쓰지 않는다. 평평한 계층·역방향 관련 관계 중복 제거·manifest 시각 재사용을 구현했다.

## 16. PR3 후보와 비서 파일 절차의 구현 판정

6절 단계 0~3·5의 처리와 9절 비서 스킬을 [파일 절차](candidates.md)로 구현한다. 화면/Host 등록은 PR5다. 공개 master ad62b3cc의 제작 안내·CLI를 별도 checkout에서 확인했다. 공개 읽기/작성 형식만 사용하며 내부 소스나 다른 플러그인 코드는 import하지 않는다. 스킬은 후속 manifest의 skills 선언에 실을 수 있는 폴더지만 실제 Host 자동 등록/호출 검증을 주장하지 않는다. 긴 작업의 접수 후 짧은 공개 읽기 조회 관례는 플랫폼에 있으므로 새로운 공용 job store를 요구하지 않는다. 셸 Host 주소 자동 전달은 읽은 공개 문서에서 미확인이다.

설계의 구체화/변경은 다음과 같다.

- 후보 키는 원본 digest로 결합된 sourceId·selfRef·selector·quoteDigest·규칙 버전·후보 종류다. 표시 위치의 revision은 입력 digest에 따로 결합한다. 같은 원문이 반복된 병합 값은 후보 하나로 묶되 모든 위치·출처 등록·대체 문맥을 보존한다.
- 공식 inspect content를 후보/문맥으로 보존한다. 숫자 있는 행·셀, 의무 목록·문단과 후보 없는 구획/제목을 남긴다. 미지원 블록은 원래 projection+문제로 남는다. 수식 PNG/그림 첨부·미확인 참조의 채택 차단은 앞 PR 정책과 같다.
- 구획 상한에 반복 문맥·인용을 포함한다. 단일 항목이 상한을 넘으면 조용히 자르지 않고 진단/보류한다. 프로파일 상한 변경 또는 앞 단계 문서 분할 뒤 다시 준비한다. 구획 밖 통합도 보류하고 묶음 설정을 재검토한다.
- 모든 판단 enum·이유·출처 후보/문맥 키·구획 전수 결정·중복 대상/순환을 검사한다. 공통 머리글·캡션·미주·부모의 숫자/단위/부정 토큰을 버릴 수 없다. 보호 토큰은 제목·본문·연결 미주에 대해 발생 위치별 exact 대응을 요구한다. 환산 예외는 없다. 의미 동등성은 비서 재대조의 일이다.
- 원장 불변 checkpoint·해시 사슬·배타적 게시·CAS로 재개/동시 제출을 다룬다. 손상 파일은 보존하고 마지막 유효 상태를 진단과 함께 읽기만 한다. 안전한 첫 구현은 입력/프로파일 변경 때 **작업 전체**를 무효화한다. 영향 범위만 재검사하는 최적화는 이후다. 이전 판단·ID는 history/발급 표에 남기지만 늦은 요청은 거부한다.
- 유지/분해/통합의 outputKey는 후보 안 논리 부분을 식별하는 선택 키다. 같은 키의 항목 이동/수정에 code-issued req-UUID를 재사용한다. 방식·출처 집합·키가 바뀐 새 논리 항목에는 새 UUID다. 내용 hash나 출력 순번을 영속 ID로 쓰지 않는다.
- v1 인계는 unreviewed이다. 가짜 채택/비서의 구획 확인은 **초안 제안 판단**으로만 저장한다. source reviewed/confirmed로 승격하지 않는다. 새 기준 문서는 채택 초안만 담고 제외·보류·문맥 부족과 모든 이유는 원장·문제 보고에 남는다. 새 문서 완료 표지 전 공식 create/check/재읽기·출처 재검사를 수행한다.

## 17. PR14 값 보호 리뷰의 판정 수정

초기 토큰 multiset 판정은 전각 수치·식별자를 놓쳤고 범위 양 끝을 바꾸어도 통과했다. [전체 구간 증거 규칙](candidates.md#pr14-리뷰-보강-인식-결과가-아닌-원문-보존-증거)으로 대체한다. 인식한 토큰은 보조 정보이고, 인식하지 못한 것을 포함한 모든 출력 문자·구조가 출처의 **완전한 블록 구간**과 일치한다는 증거 및 원문 순서 검사가 있어야 한다. 숫자/식별자/단위/부등식/범위를 개별 토큰으로 재조립하지 않는다. 따라서 quoted와 derived 모두 전각·유니코드·신호/문서 번호·범위 구조를 잃거나 바꾼 본문은 거부한다.

파생 초안의 자유 재작성은 현재 자동 판정으로 증명하지 못하므로 사람 확인 대상으로 차단한다. 유지·분해·통합은 원문 완전 블록의 선택·복사·통합 범위로 제한한다. 한 블록의 부분을 자유 재작성하는 기능을 지원한다고 주장하지 않는다. 제목은 중립 생성 제목 또는 원문 전체 구간 증거를 요구한다. 머리글/캡션/미주/부모/표 행 문맥은 인식 토큰 유무와 무관하게 보존한다. 저장 응답도 제안 게시 직전에 다시 검사하고 정책 v1 판단은 무효화한다.

허용 정규화는 **일반 text의 CRLF→LF, 같은 문자열인 인접 순수 text-run 분할/병합, 공개 평문 text/content 표현 차이**뿐이다. 가로 공백·탭·trim, 숫자·전각·분수·지수·유니코드 부호·단위·대소문자·식별자·URL·code 원자의 정규화는 없다. 자세한 닫힌 표와 보류 조건은 실행 문서에 있다.

| 추가 소유자 확인(PR14 리뷰) | 안전한 기본안 | 변경 지점 |
| --- | --- | --- |
| 파생 문장의 자유 재작성과 한 블록 안 분해 허용 | 원문과 같다는 전체 구간 증거가 없으면 차단. 원문 블록 선택/복사/통합만 자동 검증 | 증거 schema·사람 검수 계약. 토큰 집합 검사로 되돌리지 않음 |
| 표기/공백 정규화 범위 | 위 닫힌 목록만 허용. 신호명/문서 번호·단위·code는 임의 정규화하지 않음 | 의미별 검증 근거·정답 표본·정책 버전 |


## 18. PR14 재검토: 결과마다 문맥 적용을 확인

초기 전체 결과의 합집합 검사는 조건을 한 형제에만 남길 수 있었다. apply 문맥은 분해의 모든 결과, 통합의 각 출처에서 나온 결과마다 상속한다. 문맥 키와 실제 본문/미주 구간 증거를 각 결과에서 검사한다. 형제의 조건으로 대신하지 않는다. 비해당인 결과는 선택적 contextExclusions에 key·이유를 명시하고 사람 우선 검토 report.reviewFirst/problems 선두에 결과 ID·조건·출처·이유를 표시한다. 원래 후보 본문의 값 보호와 프로파일 검사, draft-only 경계는 유지한다. 상세 규칙은 [결과별 공통 조건](candidates.md#결과별-공통-조건-보존pr14-재검토)에 있다. 보호 정책 /3에서 이전 판단을 무효화한다.


## 19. PR5 구현: 사람 검토 화면

공개 작업·설치 manifest·비서 스킬·문제 우선 화면을 더했다. 구체적인 순서와 실패 경계는 [화면 절차](screen.md), 실제 설치·CLI·renderer·ReqIF 확인과 미검증 조건은 [검증 기록](screen-validation.md)에 있다. 기존 9·10절의 위치 보기 제약 가운데 저장본 NodePath 이동/강조와 일반 문서 열기는 공개 master의 DocumentView/openDocument로 사용한다. 표 셀 개별 강조·저장하지 않은 편집 상태·PDF 영역 뷰·편집 탭 위치 이동은 여전히 제공되지 않는다.
