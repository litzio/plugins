# 문서 가져오기

PDF와 워드 문서(.docx)를 리치오 문서로 옮기고 저장된 문서와 원본을 나란히 확인합니다. 변환 서버와 AI 모델을 사용하지 않습니다.

## 공통 설치와 사용

최근 폴더를 플러그인 저장소에 보관하려면 리치오 Host `eb449e7a` 이상(플러그인 SDK 0.22.0)이 필요합니다.

- GitHub에서 설치하려면 **설정 → 플러그인 → GitHub에서 추가…**에서 `https://github.com/litzio/plugins`의 **문서 가져오기**를 고릅니다. CLI로는 `litzio plugins install https://github.com/litzio/plugins/tree/master/plugins/document-import --host <Host 주소> --json`을 실행합니다. 리치오는 내려받은 폴더에서 의존성을 설치합니다.
- 로컬 폴더에서 설치하려면 Node 24 환경에서 이 폴더의 `npm ci --omit=optional`을 실행하고 `litzio plugins install <이 폴더> --host <Host 주소> --json`으로 설치합니다. 이 폴더는 Host가 허용한 범위 안에 있어야 합니다.
- 기존 PDF·워드 가져오기를 교체할 때는 같은 Host에서 `litzio plugins unregister local.pdf-import --host <Host 주소> --json`과 `litzio plugins unregister local.word-import --host <Host 주소> --json`으로 기존 등록을 지운 뒤 문서 가져오기를 설치합니다.

리치오 탐색기의 파일 우클릭 메뉴에서 **문서 변환**을 누르면 고른 파일로 바로 시작합니다. PDF는 PDF 탭의 **⋯ → 문서 변환**에서도 시작할 수 있으며 탐색기에서 한 번 누르면 PDF 보기로 열립니다. 워드 문서(.docx)는 탐색기에서 한 번 눌러 문서 가져오기로 열 수 있습니다. 작업 탭 머리에 파일 이름과 PDF 쪽 수·제외 쪽이 표시됩니다. 변환이나 내용 저장 중 다른 파일을 넘기면 진행 중인 작업과 저장이 끝난 뒤 새 파일로 이동합니다.

플러그인의 **문서 고르기**에서도 PDF나 워드 문서(.docx)를 고를 수 있습니다. **변환한 문서** 목록에서 두 종류의 저장본을 최근 변환순으로 열 수 있습니다. PDF의 검토 상태와 워드의 **변환 완료**를 같은 열에 표시합니다. 종류, 변환 시각, PDF 쪽 수와 확인할 곳은 각각 같은 열을 씁니다. 목록은 이 브라우저가 기억하는 최근 10개 폴더의 바로 아래 결과 폴더를 읽습니다. 처음에는 원본이 든 폴더에서 문서를 한 번 고르면 기존 저장본도 목록에 나타납니다.

**변환과 검수 흐름**은 처음 화면에서 목록 위에 보입니다. 접으면 다음에도 접힌 채 열립니다. 변환 중에는 현재 단계가 강조되고, 저장 뒤에는 머리 줄의 **흐름** 단추에서 현재 단계를 읽거나 그림을 펼칠 수 있습니다. 좁은 화면에서는 그림 안을 가로로 스크롤합니다. 점이 있는 칸은 사람이 하는 일이며 마우스를 올리거나 키보드 초점을 주면 한 문장 설명이 나타납니다. 비서 검수는 예정입니다.

PDF의 구조 분석 안에서 양식을 판별하고 규칙을 적용합니다. 워드는 문서를 저장한 뒤 원본 쪽과 위치를 준비합니다. **확인할 곳 보기**의 수는 이번에 연 화면에서 아직 보지 않은 곳의 수입니다. 문서를 다시 열면 처음부터 셉니다. 모두 본 뒤에는 **원본과 대조**를 표시하고, PDF에서 사용자가 검토 완료로 바꾸면 **검토 완료**를 표시합니다. 워드는 문서 검토 상태를 저장하지 않습니다.

격리 HTTP Host에서 공개 표본 6개의 저장 문서 SHA-256을 기준판과 대조해 모두 일치함을 확인했습니다. [흐름 화면 캡처](shared/test/captures/flow)에는 표준 문서에 확인할 곳이 남은 장면을 위해 공개 표본 notes-lists와 clause-links를 차례로 이어 변환한 예도 포함합니다.

PDF와 워드 문서의 대조 화면은 한 벌([`shared/compare.jsx`](shared/compare.jsx))입니다. 왼쪽 원본 쪽(보이는 쪽과 앞뒤 두 쪽만 그림), 블록 상자와 종류 색·범례, 뺀 영역의 빗금과 문서 제목 상자, 연결 띠, 양쪽 선택과 강조, 함께 스크롤, 배율(100·75·50·40%, 두 종류가 같은 값을 기억), `원본 · i / N쪽`, **확인할 곳 i / N · 이전 · 다음**을 이 화면이 맡습니다. PDF의 변환 경고와 워드의 확인할 곳은 화면에서 모두 `확인할 곳`으로 부릅니다(머리 줄 `변환 완료 · 확인할 곳 N`, 목록 `확인할 곳 N`, 원본 상자에 올렸을 때 `종류 · 확인할 곳: 이유`). 옆 파일의 필드 이름은 그대로입니다. PDF는 고치기(상자 메뉴, 여러 개 고르기, 나누기, 되돌리기)를 이 화면에 넘겨 붙이고 고치기의 처리와 상태는 PDF 쪽에 둡니다. 워드는 넘기지 않아 읽기 전용입니다.

대조 화면의 공통 동작 몇 가지(2026-11-25):

- **원본 쪽의 경계.** 원본 칸의 바탕은 리치오 PDF 탭과 같은 `--id-color-surface-subtle`, 쪽은 테마와 무관한 흰 `--id-color-pdf-paper`이고, 쪽마다 `--border-width`의 `--id-color-border` 선을 두르며 위·아래·오른쪽에도 쪽 사이와 같은 간격(`--space-2`)을 둡니다. 전에는 바탕이 `--id-color-canvas`, 쪽이 `--id-color-paper`와 `--shadow-paper`였는데, 리치오 설정의 **페이지 모양 → 평면**에서는 바탕이 종이색이 되고 그림자가 없어져 밝은 테마에서 흰 쪽과 바탕이 같아졌습니다(어두운 테마에서는 PDF 그림이 흰색이라 구분됨). 종이 모양에서도 첫 쪽 위와 쪽의 오른쪽 변은 칸 가장자리에 붙어 있었습니다. 2026-11-18의 V-02 변경 뒤 이 부분의 코드는 PR #80에서도 바뀌지 않았습니다. 캡처(75%): [종이 모양 전](shared/test/captures/compare-view/edges-paper-light-75-before.png)·[후](shared/test/captures/compare-view/edges-paper-light-75-after.png), [평면 전](shared/test/captures/compare-view/edges-flat-light-75-before.png)·[후](shared/test/captures/compare-view/edges-flat-light-75-after.png), 100% [전](shared/test/captures/compare-view/edges-paper-light-100-before.png)·[후](shared/test/captures/compare-view/edges-paper-light-100-after.png), [어두운 테마](shared/test/captures/compare-view/edges-paper-dark-75-after.png), [어두운 테마 1440](shared/test/captures/compare-view/dark-1440.png), [1920×1080](shared/test/captures/compare-view/wide-1920.png).
- **고른 블록의 종류.** 도구 줄의 `N개 선택` 옆에 종류를 글자로 보입니다(아래 [연결 띠와 훑어보기 배율](#연결-띠와-훑어보기-배율)). 워드 대조에서는 블록을 고르면 범례 자리에 `1개 선택`과 종류가 보입니다. 워드 원본 상자에는 제목 단계가 없어 `제목`으로 보입니다([워드 도구 줄](shared/test/captures/compare-view/toolbar-kind-word-1440.png)).
- **다른 탭에 갔다 올 때.** 리치오는 다른 탭으로 가면 이 화면을 내리지 않고 숨깁니다. 화면의 상태(문서, 배율, 고른 블록, 확인할 곳 번호, 되돌리기)와 오른쪽 문서의 위치는 남지만, 숨긴 동안 원본 칸의 스크롤 위치가 0이 되어 돌아오면 1쪽이 보였습니다. 이제 원본 칸이 다시 보이는 순간 마지막 스크롤 위치로 되돌립니다. 격리 HTTP Host에서 공개 LSR(7쪽 부근, 50%, 확인할 곳 6/15로 고른 블록)과 워드 공개 표본(블록 하나를 누른 상태)으로 탐색기의 다른 문서를 연 뒤 돌아왔을 때, origin/master는 원본 스크롤이 2,183px·87px 어긋났고(오른쪽 문서는 PDF 0px, 워드 24px) 이 변경은 원본·문서 모두 0px였습니다. 배율, 고른 블록, 확인할 곳 번호는 두 판 모두 같았습니다. 탭을 누른 뒤 자리가 잡혔음을 확인한 시간은 0.10초(PDF)·0.08초(워드)였고 되돌리는 처리 자체는 1ms 미만이었습니다. 다시 그리는 동안의 깜박임은 측정하지 않았습니다.

직접 의존성은 Apache-2.0의 `pdfjs-dist` 6.5.438입니다. `node shared/prepare.mjs`로 고정된 worker 문자열을 다시 만들 수 있습니다. `npm test`는 PDF·워드 단위 검사와 두 종류의 목록 정렬 검사를 실행합니다.

합친 대조 화면은 격리 HTTP Host(리치오 64bf0416, Windows, 1440·1920×1080, 밝음·어두움)에서 origin/master와 나란히 확인했습니다. 실제 Host에서 화면까지 본 것과 단위 검사만 한 것을 나눠 적습니다.

- **변환 결과 불변(화면으로 변환):** 공개 표본 6개와 별도 큰 표본 3개(큰 PDF 1·2, 큰 워드)의 결과 문서 SHA-256이 모두 같았습니다. PDF 대응 자료는 변환 시각을 빼고 같았고, 워드 옆 파일은 실행마다 달라지는 값(변환 시각, Word가 내보낸 PDF의 해시, 시간 측정)과 새 `source.excluded`를 빼고 같았습니다. `source.excluded`는 합성 워드 표본 4개(2쪽 × 머리글·바닥글), 큰 워드 표본 593개입니다. 머리글·바닥글을 더한 합성 워드 표본의 결과 문서는 더하기 전 표본의 결과와 같은 해시입니다.
- **PDF 고치기(화면):** 쪽 고르기 → 변환 → 대조, 확인할 곳 이전·다음, 원본 상자 누르기, 배율 바꾸기(보던 상자 높이 212px → 212px), 원본 휠 → 문서 따라옴, 문서 휠 → 원본 따라옴, 종류 바꾸기, 문서 제목으로, 문서에서 빼기(뺀 영역 빗금), 합치기, 나누기(줄 고르기), 각각의 되돌리기, Shift 여러 개 고르기, 고친 뒤 연결 상자 수 유지(43 → 43)와 선택 유지, 검토 완료와 초안으로 되돌리기, 목록으로 갔다 다시 열기를 두 판에서 같은 순서로 했고 결과 값(스크롤 위치 포함)이 같았습니다. 같은 장면을 찍어 픽셀을 비교하면 머리 줄과 도구 줄(상태 문구, 범례의 `! 확인할 곳`, 넘기기 이름)만 달랐습니다.
- **워드 대조(화면):** 고르기 → 원본 쪽 붙음 → 표 상자 누르기(문서 짝 강조) → 확인할 곳 다음·다음·이전 → 머리글·바닥글 빗금에 올려 `제외 · 머리글·바닥글` → 다시 열기를 확인했습니다. 이 기능 전에 원본을 준비해 둔 합성 표본과 큰 워드 표본을 새 판으로 열었을 때 Word 프로세스는 뜨지 않았고 `X.source.pdf`는 바이트까지 같았으며 빗금 자료만 옆 파일에 채워졌습니다(큰 워드 표본은 열기부터 대조 화면까지 약 8.1초, 한 번).
- **큰 워드 표본의 빗금 실측:** 313쪽에 593곳, 쪽당 2곳 296쪽·1곳 1쪽·0곳 16쪽(0곳인 쪽은 Word가 표시한 머리글·바닥글 글자가 없는 쪽). 무작위 20쪽을 원본 위에 그려 눈으로 보았고 본문을 빗금으로 만든 곳은 없었습니다. artifact로 좁히기 전(모든 글자 층)에는 옮기지 않는 목차·그림 목차의 첫 줄과 끝 줄 27곳이 잡혔습니다.

| 큰 워드 표본 끝까지 휠 스크롤, 50ms 넘는 멈춤(150ms 넘는 것) | 14(10) · 21(8) · 14(7) | 18(11) · 23(9) · 16(11) |

뜨는 시간은 목록 줄을 누른 때부터 첫 쪽 그림, 연결 상자, 문서 글자가 모두 보인 때까지입니다. 스크롤은 원본 칸에서 600px 휠을 16ms 간격으로 끝까지 보냈습니다. 두 판의 차이는 회차 사이의 흔들림 안에 있습니다. 확인하지 못한 것: 설치형 Desktop, Windows 이외 Host, 640px 같은 좁은 창의 대조 화면, 터치패드 입력.

통합을 검증한 격리 HTTP Host(리치오 64bf0416, Windows)에서는 공개 표본 6개와 별도 큰 표본 3개를 통합 전과 후에 화면으로 변환했습니다. 저장 문서 SHA-256과 실행마다 달라지는 값을 제외한 대응 자료가 모두 일치했습니다. 두 종류의 기존 결과 재열기, PDF 블록 종류 바꾸기·되돌리기, 워드 원본 쪽과 확인할 곳 이동, 지원하지 않는 파일 안내를 확인했습니다. 두 공개 표본의 대조 화면은 플러그인 제목 영역만 픽셀이 달랐습니다. 설치형 Desktop과 Windows 이외 Host의 화면은 이번에 확인하지 않았습니다.

## PDF 가져오기

글자 층이 있는 PDF를 리치오 문서로 만들고, 원본 쪽과 저장된 문서를 나란히 봅니다. 변환 서버와 AI 모델은 쓰지 않습니다.

### 설치와 사용

처리 코드가 SDK 0.16.0의 표 주석 연산과 SDK 0.18.0의 `documentViewChange`를 가져오므로 그 전 Host에서는 플러그인이 올라오지 않습니다. 변환한 문서는 공개 `ui.ItemList`로 표시합니다. 대조 화면에는 공개 ContextMenu·Select hideLabel과 DocumentView의 스크롤·클릭·배치 보고·scale·`target.top`을 사용합니다. 플러그인 선언에는 최소 SDK 버전 필드가 없습니다.

PDF가 든 폴더를 리치오에서 열고 **문서 가져오기 → 문서 고르기**로 파일을 고릅니다. 다음은 전체 폭의 **뺄 쪽 고르기** 격자입니다. 격자는 제외 제안을 기다리지 않고 열립니다. 제안이 도착하면 직접 바꾸지 않은 쪽에만 적용합니다. 누르거나 Shift 범위로 바꾼 쪽은 사용자의 선택을 유지합니다. 제안 확인 중에도 변환을 누르면 그때 고른 대로 진행합니다. 이전 파일의 저장된 제외 선택은 바로 적용합니다. 128px 미리 보기를 누르면 포함·제외가 바뀌고 Shift로 범위를 고릅니다. 키보드 Enter·Space와 Shift도 같습니다. 쪽 번호 아래에는 그 쪽의 첫 책갈피 제목을 한 줄로 표시하며 hover·focus로 전체 제목을 확인합니다. 책갈피가 없으면 번호만 표시합니다. **취소**는 파일을 고르기 전으로 돌아갑니다.

미리 보기에 hover·focus하면 **크게 보기** 아이콘이 보입니다. 크게 보는 동안 이전·다음 쪽 버튼이나 좌우 화살표로 넘기고 포함·제외를 바꿀 수 있습니다. Esc나 닫기로 원래 격자 위치와 focus에 돌아옵니다. 범위 조작 설명은 격자 상태 글의 hover·focus에, 큰 쪽의 단축키는 해당 버튼의 hover·focus에 표시합니다. 공개 화면 부품에 일반 Dialog·Popover가 없어 격자 자리를 큰 쪽으로 바꾸는 방식을 씁니다.

**변환**을 누르면 PDF 폴더 아래 PDF 이름의 폴더를 만들고 그 안에 같은 이름의 `.md`와 `.pdf-source.json` 대응 자료, `assets/`의 그림을 만들고 원본과 저장본을 나란히 보는 **대조 화면**으로 갑니다. 대조 화면에는 쪽 고르기 조작이 없습니다. 머리 줄은 변환 경고가 붙은 블록 수를 `확인할 곳 N`으로 표시합니다. 도구 줄의 **확인할 곳 i / N** 옆 이전·다음은 같은 블록을 순회하며 현재 번호와 이유는 그 아래 한 줄에 표시합니다. 머리 줄에는 PDF 고르기·다시 변환·문서 열기와 검토 상태 버튼을 둡니다. 원본 상자를 누르면 문서 블록을 강조하고 누른 상자와 같은 높이에 둡니다(아래 "누른 블록의 짝 맞추기"). 함께 스크롤은 기본으로 켜져 있으며 양방향으로 동작합니다. 원본 스크롤이 멈추면 강조 없이 문서가 따라오고, 문서를 스크롤하면 맨 위에 보이는 블록의 원본 상자가 왼쪽 높이의 1/3 지점에 옵니다. 최근 휠·스크롤바·스크롤 키 입력을 받은 칸이 주인이며 반대쪽의 늦은 보고는 무시합니다. 함께 스크롤을 끄면 양쪽 모두 따라가지 않습니다. 오른쪽 블록을 누르면 원본의 같은 블록이 선택되어 그 블록과 같은 높이로 오고 해당 동작 줄과 강조가 표시됩니다. 이 누르기는 함께 스크롤을 꺼도 동작하며 문서를 다시 읽지 않아 더블클릭한 글자 선택을 유지합니다. 원본 대응이 없는 블록은 스크롤 때 가장 가까운 앞 대응을 쓰고 누르기는 무시합니다. 문서가 바뀌었거나 고치는 중이면 보고를 무시합니다. 따라가는 블록은 왼쪽 분류 막대의 색으로 표시합니다. 선택과 올림에는 리치오 편집기의 블록 윤곽을 씁니다. 제목은 H1~H6, 목록은 변환 결과에 2 이상 단계가 있을 때 여백에 단계를 표시합니다. 문서 열기는 일반 탭을 엽니다.

PDF 읽기, 구조 분석, 그림 만들기, 문서 저장, 원본 연결 만들기 중 실패한 단계가 상태 줄에 표시되며 자세한 원인은 오류 영역에 나옵니다. 문서 저장 뒤 원본 연결 만들기에 실패하거나, PDF를 고를 때 결과 폴더에 문서만 있고 대응 자료가 없으면 **문서 열기**와 **다시 변환**을 사용할 수 있습니다. 다시 변환을 확인하고 쪽을 고르면 이전 문서를 복구용으로 옮긴 뒤 새 문서와 대응 자료를 만듭니다. 이전 그림은 소유 기록이 없으면 보존합니다.

대조 화면 머리 왼쪽의 **변환한 문서**를 누르면 같은 탭에서 방금 갱신된 목록으로 돌아갑니다. 대조 화면에서도 **PDF 고르기**를 사용할 수 있습니다. 목록에서 검토 완료 문서의 확인할 곳 수는 숨깁니다. 변환한 때는 다시 열기, 교정, 검토 상태 변경 뒤에도 유지되며 다시 변환하면 갱신됩니다. 변환 시각을 기록하기 전에 저장한 결과는 대응 자료 파일의 수정 시각을 표시합니다. 원본이 없거나 바뀌면 상태를 표시하고 저장된 PDF 결과 열기를 막습니다.

[변환 경고를 표시한 대조 화면](pdf/test/captures/first-use/after-warning-1440-light.png)(지금은 `확인할 곳`으로 부름)과 [변환한 때를 표시한 목록](pdf/test/captures/converted-time/list-1440-light.png)을 볼 수 있습니다.

제외한 쪽은 흐린 원본 위에 반투명 대각선 **제외** 글자와 위험색 테두리로 표시합니다. 대상 정보에는 떨어진 제외 범위도 표시하며 다섯 구간을 넘으면 개수만 표시합니다. 제외 목록은 대응 자료에 보관합니다.

변환한 문서 목록에서 저장본을 열면 바로 대조 화면으로 갑니다. PDF 고르기로 이전 파일을 고르면 그때 저장한 제외 선택이 적용된 격자로 갑니다. 대조 화면의 다시 변환은 확인 후 같은 선택의 격자로 돌아갑니다. 변환을 실행할 때 기존 문서와 대응 자료를 같은 결과 폴더의 `previous` 복구용 사본으로 옮기고 새 문서를 만듭니다. 새 저장과 대응 검증이 끝나면 복구 사본과 쓰이지 않는 이전 그림을 정리합니다. 실패하면 복구 사본을 남기며 자동 복구는 하지 않습니다. 격자를 취소하면 기존 저장본은 바뀌지 않습니다. 그림은 생성 당시 기록한 이름·SHA-256이 일치하는 파일만 지웁니다. 사용자가 수정한 그림과 다른 파일은 보존하며, 결과 폴더에 다른 문서가 있으면 공유 가능성이 있어 이전 그림도 보존합니다. 문서를 고쳤으면 대응 이동을 막습니다. 대응 자료를 잃은 기존 문서는 자동 덮어쓰지 않습니다.

짝이 맞는 각주는 공식 미주로 저장합니다. 동일 번호의 정의가 여러 개면 모호한 호출과 모든 정의를 글자로 보존하고 각주 짝 경고를 붙입니다. 정의 없는 표시는 `[n]` 글자로, 표시 없는 정의는 해당 쪽의 문단으로 보존하고 경고합니다. 괘선 표는 글자 표로, 믿을 수 없는 표와 그림은 원본 영역 PNG로 저장합니다. 캡션은 각 작성 블록의 공식 캡션을 사용합니다. 같은 종류의 번호 캡션이 붙은 그림·표는 원문 번호를 고정 번호로 가지며 본문의 같은 번호 참조가 리치오 참조가 됩니다(아래 "그림·표 참조"). 인식할 영역이 없는 독립 캡션은 문단으로 남습니다. 캡션은 Table/Figure 번호 뒤의 줄표·하이픈·마침표·쌍점을 인식하며, 보통 글자는 같은 쪽의 인접 영역이 있어야 합니다. Figure 아래 작은 글자의 축 줄만 사이에 있으면 영역을 아래로 넓혀 PNG에 포함합니다. 본문 크기의 줄을 넘어서 연결하지 않습니다.

글자 표의 주석은 설명마다 한 문단으로 표에 저장합니다. 원본에서 각 주석은 자기 **각주** 상자를 유지하며, 상자를 누르면 오른쪽에서 표 전체가 강조됩니다. 한 글자 표시는 위첨자로 보존하며, 같은 표시가 표 칸이나 캡션에서 작은 글자로 올라가 있으면 그곳도 위첨자로 둡니다. 표 밖 문단은 표와 가까이 이어지고 표시의 순서·작은 글자·표의 위첨자 중 하나가 확인될 때만 주석으로 인식합니다. 미주 호출이 든 주석은 본문에 두고 확인할 곳으로 알립니다. 표가 그림으로 들어가거나 다른 표의 주석이 합쳐지는 사례는 [사례집](pdf/cases.md)에 기록합니다.

쓰는 pdf.js 기능과 쓰지 않는 기능의 판단은 [pdf.js 기능 장부](pdf/docs/pdfjs-features.md)에 있다. `node pdf/pdfjs-probe.mjs <PDF>`는 PDF에 어떤 신호(태그 구조, 링크, 쪽 표시 번호, 레이어 등)가 있는지 개수만 출력한다.

수식 그림을 LaTeX로 바꾸는 로컬 모델 조사(판단 보류)는 [수식 OCR 조사](pdf/docs/formula-ocr-research.md)에 있다.

변환 중에는 구조 분석·그림 만들기·문서 저장·원본 연결 단계를 표시합니다. 뺀 쪽이 있으면 머리에서 전체 쪽 수와 포함한 쪽 수를 보여 줍니다. 다시 변환할 때는 이전 문서 정리 단계가 앞에 추가됩니다. 실패하면 해당 단계와 오류를 표시하고 기존 복구 동작을 제공합니다.

### 확인 범위

격리 HTTP Host(리치오 61381ee4, Windows, 너비 1440px)에서 LSR 4쪽의 a·b 주석이 같은 표 안에 표시되고, 원본 주석 상자를 누르면 그 표가 강조되는 것을 확인했습니다. **본문으로**, **표 주석으로**, 각 동작의 **되돌리기**를 실행했습니다. 워드 합성 표본에서 칸의 여러 문단이 줄바꿈으로 보이는 것을 확인했습니다. SDK 통합 검사는 두 방향의 교정과 표 잇기에서 문서 바이트 및 원본 상자 대응을 복원할 수 있는지 확인합니다.

- LSR 4쪽 [이전](pdf/test/captures/table-breaks-notes/before-pdf-1440.png), [표 안 주석](pdf/test/captures/table-breaks-notes/after-pdf-1440.png), [원본 주석 선택](pdf/test/captures/table-breaks-notes/pdf-note-selected-1440.png), [표 주석으로](pdf/test/captures/table-breaks-notes/pdf-table-note-menu-1440.png), [어두운 테마](pdf/test/captures/table-breaks-notes/pdf-dark-1440.png)

LSR의 공식 정답에서 `table_note_for` 관계가 있는 `footnote` 요소 일곱 개 중 다섯 개를 예상한 글자 표의 주석으로 확인했습니다. 11쪽 두 요소는 나란한 표가 한 이미지로 들어가 표 소속을 확인할 수 없습니다(T-05). 각주·표 주석 맞음 하한은 5에서 10으로 올라갔습니다.

변환 단계 화면은 격리 HTTP Host에서 공개 표본의 첫 변환과 다시 변환, 그림 진행, 완료 후 대조 화면을 확인했습니다. 640px 어두운 화면의 구조 분석 실패 안내도 확인했습니다. 그림 저장 위치를 파일로 막은 시험에서 실패했으나 실패 원인은 확정하지 못했습니다. 공개 캡처는 `pdf/test/captures/conversion-steps/`에 있습니다.

`npm test`는 리치오 없이 공개 LSR 표본의 제목·글자 분류·제외·쪽 간 문단·결과 형태, 쪽 제외 제안과 선택한 쪽의 글자·그림 제외, 짝 없는 표시, 영역 합치기와 각주 공백 보존, 캡션과 축 포함, 같은 크기 각주 번호·쪽 간 짝 맞추기, 최근 폴더 목록의 원본 변경·삭제를 검사합니다. 실제 격리 HTTP Host에서 공개 표본과 별도 큰 디지털 PDF의 선택·변환·저장·강조·전체 스크롤을 확인했습니다. 저장본 재사용, 확인 후 이전 사본 보관, revision 변경 시 이동 차단, 640px 안내와 밝고 어두운 테마를 확인했습니다. 공개 표본 캡처는 `pdf/test/captures/`에 있습니다.

OCR, 스캔 PDF, 글자 교정, 옵션과 설정 화면은 없습니다. 패키징된 Desktop, 다른 OS·폰트·회전/세로쓰기 PDF, 변환 중 종료 뒤 복구는 검증하지 않았습니다. 같은 쪽에서 크게 겹치는 영역은 읽기 순서와 무관하게 하나로 합치고, 그 밖의 연속 도형은 본문·제목·캡션·각주가 경계가 됩니다. 공개 표본에는 영역 밖 축 글자의 본문 혼입, 옆에 놓인 표의 합침, 수식 도형과 본문의 분리, 작은 글자 본문의 각주 포함은 큰 줄 간격을 경계로 고쳤습니다. 여러 단 이름 목록과 나란한 표의 주석 합침은 남아 있습니다. 원문 각주 번호와 리치오가 표시하는 미주 번호는 다를 수 있습니다. 저장본을 불러올 때 revision을 확인하고 이후 stale-target 알림이 오면 이동을 막습니다.

직접 의존성은 Apache-2.0의 `pdfjs-dist` 6.5.438 하나입니다. pdf.js worker와 `PDFJS-LICENSE`는 같은 배포물에서 가져옵니다. 스크립팅은 계속 끕니다. `npm audit`에서 취약점 0건을 확인했습니다.

`npm ci --omit=optional` 설치 상태에서 추출과 검사를 실행했습니다. 선택적 canvas와 그리기 전역에 관한 pdf.js 경고는 나지만 글자·도형 추출에 사용되지 않아 전역 대체는 추가하지 않았습니다.

`node pdf/measure.mjs <PDF>`는 문서를 저장하지 않고 추출·규칙을 실행해 제목·각주·캡션 등의 검증 통계를 JSON으로 출력합니다. 저작권 입력의 통계와 내용은 저장소 밖에서만 보관합니다.

이번 화면 변경은 격리 HTTP Host에서 공개 표본의 쪽 선택·Shift 범위·키보드 선택·재변환 확인·목록 재열기와 경고 필터를 확인했습니다. 각주 정의가 든 쪽을 제외한 경우도 통합된 각주 짝 판정을 사용합니다. DocumentView의 공개 경로 보고와 target을 사용하며 내부 에디터나 스크롤 DOM에 접근하지 않습니다.

### 문단과 목록 판정

본문 크기(±0.6pt) 글자들의 기준선으로 줄 간격을 잽니다. 쪽마다 긴 본문 줄의 오른쪽 끝 90백분위수를 구하고 1.25em 이내를 가득 찬 줄로 봅니다. 그 비율이 45% 이상이면 양끝 맞춤으로 판정합니다. 평소 기준선 간격의 1.45배를 넘는 간격, 0.7em을 넘는 들여쓰기 변화는 문단을 나눕니다. 양끝 맞춤에서 짧은 줄은 문단을 끝내며 줄 끝 하이픈은 이어짐의 보조 신호입니다. 겹치는 문자 조각의 기존 조립은 유지합니다. 쪽 끝의 가득 찬 줄은 다음 쪽 본문과 잇고, 신호가 어긋날 때만 `paragraph-boundary` 경고와 이유를 남깁니다. 소문자 시작 자체는 경고가 아니며 `용어: 설명`도 정상입니다.

목록은 기호·순서 표시와 내어쓰기 위치를 보존하며, 같은 높이에 떨어진 표시와 본문을 합칩니다. 변환 블록의 `marker`, `level`, `contentX`에 표시와 단계를 담습니다. 공식 작성 입력의 순서 목록(style/start/delimiter)과 중첩 목록을 사용합니다. `(a)`처럼 지원하지 않는 표시는 글머리 목록 항목 글자에 그대로 둡니다. 연속 목록을 묶은 경우 각 원본 항목은 저장된 최상위 목록 경로에 대응합니다. 단독 `i)`는 뒤의 `ii)`가 없으면 영문자로 해석하는 모호성이 남습니다.

`node pdf/compare-paragraphs.mjs <PDF 또는 변환 결과 JSON> <비교 자료 JSON> [첫 쪽]`은 개발용 경계 비교입니다. 비교 자료는 Docling의 texts 또는 공개 표본의 elements를 받습니다. 영문자·숫자로 정규화한 25자 이상 문단·목록의 앞뒤 22자를 같은 쪽 ±1에서 비교합니다. 목록 표시는 새 변환 블록의 marker로 본문에서 분리하며, 비교 자료에서 여러 쪽에 반복되는 머리글을 제외합니다. 원문과 비교 자료는 포함하지 않습니다.

공개 LSR 정답의 문단·목록 부분을 CC0 표본으로 두고 경계를 검사합니다. 이 표본은 가득 찬 줄 약 33%의 오른쪽이 들쭉날쭉한 문서입니다. 경계 비교는 각주 뒤 본문 두 개를 분리하여 33/46에서 35/48이 되었으며, 기존의 영역·수식·쪽을 넘는 정답 단위 차이도 분모에 남습니다. 이름만 배치한 명부를 표시가 있는 목록으로 추정하지 않습니다. 큰 PDF와 공개 표본은 격리 HTTP Host에서 목록을 포함한 문서 저장 및 대응 자료 생성을 확인했습니다. 다단 본문과 임의 순서 표시를 폭넓게 검증한 것은 아닙니다.

각주 짝은 블록 조립 뒤 실제 저장 대상의 문단·목록·제목·번호 없는 제목 후보·캡션 전체에서 다시 셉니다. 작성 계획도 전달받은 블록 목록으로 재판정하므로, 정의가 제거된 표시는 `[n]` 글자와 각주 짝 불일치 경고로 남습니다. 참조가 없어진 정의는 원래 위치의 문단으로 남습니다. 완성된 작성 입력의 중첩 목록·그림 캡션까지 순회해 같은 입력 안에 정의가 없는 미주 호출이 있으면 번호를 담은 오류로 저장 전에 중단합니다. 공개 표본에서 정의 블록을 제거한 경우와 입력 간에만 정의가 존재하는 경우를 검사합니다. 통합한 쪽 제외 화면에서 각주 정의가 든 쪽을 제외한 뒤 저장하고, 남은 호출이 글자와 경고로 보존되는 것도 확인했습니다.

### 대조 화면에서 고치기

원본 상자를 누르고 Shift로 범위를 고릅니다. 고칠 수 있는 원본 상자의 우클릭·Shift+F10·메뉴 키는 공통 ContextMenu를 엽니다. 선택 안에서 열면 여러 선택을 유지하고, 선택 밖에서 열면 그 블록 하나로 바뀝니다. 메뉴와 도구 줄은 같은 조건·이유·동작을 쓰며 쓸 수 없는 항목의 이유는 hover·focus로 보입니다. 메뉴는 종류 바꾸기(본문으로·제목 1~6으로·참고로·문서 제목으로), 구조 바꾸기(합치기·나누기·목록으로·표로·미주로), 빼기(문서에서 빼기·이 쪽에서 고른 것만 남기기) 순으로 나열하고 같은 종류는 비활성입니다. 공통 메뉴에 구분선이 없어 묶음은 순서로만 나눕니다. 고른 것의 종류에 전혀 해당하지 않는 항목(표를 골랐을 때의 미주로 등)은 숨깁니다. 그림·제외 상자에는 메뉴가 없고 고치는 중이나 대응이 바뀌면 열리지 않습니다. 메뉴를 닫거나 실행하면 원본 상자로 focus가 돌아오며, 뺀 상자는 다음 대응 상자로 옮깁니다. 동작 줄의 **합치기**는 이웃한 본문, 또는 같은 종류(번호 목록끼리, 기호 목록끼리)의 이웃한 목록 둘 이상을 하나로 합치고, **나누기**는 본문 하나의 둘째 원본 줄부터 처리합니다. **종류**에서 본문·제목 1~6·참고·문서 제목을 고르고 **문서에서 빼기**로 본문·제목·목록·참고 상자를 제외합니다(여러 블록은 아래 [여러 블록 한 번에 빼기](#여러-블록-한-번에-빼기)). 목록·표·미주·참고 상자로 바꾸기는 아래 [목록·표·미주·참고 상자](#목록표미주참고-상자)를 봅니다. 그림 영역과 캡션으로의 변환은 지원하지 않습니다. 목록을 합치면 뒤 목록의 항목이 첫 목록 뒤에 붙고 번호 모양과 시작 번호는 첫 목록을 따릅니다. 합친 목록이 100항목을 넘으면 합치지 않습니다. 목록 여러 항목이 같은 문서 블록에 묶였으면 개별 항목을 빼지 않습니다. Esc는 줄 선택을 취소합니다. **되돌리기**는 이 화면의 직전 동작부터 복원합니다. 각주 호출이 든 블록을 빼면 정의가 사라질 수 있고 공식 SDK에 원래 표지를 지정한 정의 복원 연산이 없어 확인 후 처리하며 되돌리기 기록을 비웁니다.

대응 자료의 줄 자료·문서 종류·고친 표시와 이력은 저장됩니다. 옛 위치와 옛 형식의 결과는 지원하지 않습니다. 같은 프로세스의 공식 SDK `readDocument`로 문서와 revision을 읽고, Core 연산을 적용한 뒤 `writeDocument`로 한 번 저장합니다. 사전 revision·블록 수·종류 검사와 쓰기의 revision 충돌 거부를 유지합니다. 저장 직후의 검사는 공식 쓰기가 쓴 바이트를 다시 읽어 돌려준 문서로 합니다(아래 [고치기의 중복 읽기](#고치기의-중복-읽기)). 블록 수·종류를 대응 자료와 맞추고 그 문서의 인라인 스냅샷을 대응 자료에 보관한 뒤 화면에 반환합니다. 이 검사는 화면 뒤로 미루지 않습니다. 오른쪽 문서는 쓰기 전에 고친 결과를 먼저 보이고(아래 [고친 결과 먼저 보이기](#고친-결과-먼저-보이기)), 원본 상자와 연결 띠는 확인 결과를 받은 뒤 갱신합니다. 어긋나면 대응 이동을 멈추고 되돌리기는 남깁니다. 화면을 닫으면 되돌리기 기록은 없어집니다. 문서를 탭에서 고치는 중인지 SDK가 알 수 없어 저장본 수정은 허용됩니다. 미저장 탭에서 나중에 저장하면 충돌로 거부되므로 먼저 저장하거나 닫은 뒤 대조 화면에서 고치세요.

단위 검사는 `npm test`로 실행하며 SDK 없는 환경에서는 통합 검사 열 개를 건너뜁니다. SDK 통합 검사는 공개 SDK를 해석할 수 있는 환경에서 필요한 TypeScript loader를 사용하고, `PDF_IMPORT_TEST_CLI_ARGS`에 공식 CLI 실행 인자 배열(JSON)을 지정하여 `node --test pdf/test/corrections-host.test.mjs pdf/test/structure-host.test.mjs pdf/test/content-edit-host.test.mjs`를 실행합니다. CLI는 검사 문서 생성과 최종 유효성 검사, 아래 미주로와 그 되돌리기, 이름표를 되살리는 되돌리기에만 쓰며 나머지 교정·조회는 SDK로 실행합니다. 줄 글자와 문서의 글자·미주 호출을 공백 차이만 허용하여 전체 대조하며 위치를 확정하지 못하면 나누지 않습니다.

격리 HTTP Host에서 공개 표본의 합치기·되돌리기·다시 합치기·나누기·종류 변경과 되돌리기·빼기와 되돌리기를 확인했습니다. 오른쪽 문서 ready까지 0.54~0.64초였습니다. 큰 문서의 같은 흐름은 2.07~3.10초여서 1.5초 목표를 충족하지 못했습니다. 큰 문서에서 26회 연속 교정 중 plugin process failure는 재현되지 않았습니다. 공개 표본의 7가지 교정과 각각의 되돌리기는 master의 CLI 경로와 문서 바이트 및 사후 검사가 끝난 대응 자료 전체가 같았습니다. 각주 호출 삭제는 기존과 같이 확인 후 되돌리기 기록을 비우며, 원래 표지를 지정한 정의 복원 기능은 여전히 제공하지 않습니다. 처리 코드에 남은 CLI 호출은 없습니다. 설치형 Desktop은 검사하지 않았습니다.

### 목록·표·미주·참고 상자

공개 LSR 3쪽의 세 열 이름 명단(L-04)과 4쪽의 호출 없는 쪽 각주(F-08) 같은 것을 대조 화면에서 고칩니다. 우클릭 메뉴에는 **목록으로**·**표로**·**미주로**·**참고로**가 각각 보이고, 도구 줄은 폭이 늘어 두 줄로 바뀌지 않도록 **합치기**·**나누기** 단추 옆의 **종류** 선택에 **목록**·**표**·**미주**·**참고**를 더했습니다(쓸 수 없는 항목의 이유는 **종류** hover에 `표: …`처럼 보임). 모두 SDK 제작 안내의 조합대로 인라인 내용을 읽어 블록을 끝에서부터 빼고 첫 자리에 새 블록을 넣으며, 미주 정의가 살아 있도록 메모리에서 조합을 마친 뒤 한 번에 씁니다. 인라인 서식·링크·미주 호출·참조는 그대로 옮깁니다. 되돌리기는 원래 바이트로 돌아옵니다(SDK 통합 검사로 확인).

- **목록으로.** 이웃한 본문을 하나 이상 고르면 켜지고, 글머리 목록 하나가 됩니다. 고른 줄을 원본 글자 조각으로 칸을 나눠 한 줄에 칸이 둘 이상인 줄이 있으면 칸마다 항목 하나, 아니면 본문 하나가 원본 줄 둘 이상이면 줄마다 항목 하나, 그 밖에는 본문 하나가 항목 하나입니다. 줄마다·칸마다 나뉜 항목은 자기 원본 상자(줄이나 칸의 영역)를 가집니다. 100항목을 넘으면 꺼집니다.
- **칸 나누기 규칙.** 화면이 고른 블록의 쪽에서 pdf.js 글자 조각을 읽고(대응 자료에는 줄 상자만 있습니다) 처리 코드가 같은 규칙을 다시 돌립니다. 고른 모든 줄의 조각이 덮는 가로 구간을 합치고, 모든 줄을 위에서 아래로 관통하는 14pt 이상(추출이 한 줄을 조각으로 나누는 간격과 같음)의 빈 세로 띠가 열 경계입니다. 조각의 가운데가 든 열이 그 조각의 칸입니다. 칸 경계는 줄의 글자(공백 제외, 미주 호출 `[^n]`은 원본에 보이는 `n`)와 조각의 글자가 같을 때만 정하고, 미주 호출 가운데는 자르지 않습니다. 맞지 않으면 칸을 나누지 않습니다.
- **읽는 순서.** 열 우선(왼쪽 열의 위에서 아래, 다음 열)이 기본입니다. 빈 칸이 둘 이상이고 모두 마지막 행에만, 그 행의 오른쪽 끝에 몰려 있을 때(행부터 채운 모양)만 행 우선입니다. 빈 칸 하나는 두 모양 모두에 맞아 열 우선입니다. LSR의 18명은 열 우선으로 알파벳 순서 18항목이 됩니다.
- **본문으로(목록).** 목록 하나를 고르면 항목마다 본문 하나로 풉니다. 하위 목록이 있거나 원본 상자와 항목의 짝이 맞지 않으면 꺼집니다.
- **표로.** 이웃한 본문을 하나 이상 고르면 켜집니다. 같은 칸 나누기로 원본 줄 하나가 행 하나, 열 하나가 칸 하나인 표를 만듭니다. 리치오 표는 머리글 행이 반드시 있어 첫 행을 머리글로 두고, 그 표에 확인할 곳 `첫 행을 머리글로 두었습니다. 머리글이 아니면 문서 탭에서 고치세요.`를 붙입니다. 열이 둘 이상으로 나뉘지 않거나(`원본 글자 사이에 세로 틈이 없어 열을 둘 이상으로 나눌 수 없습니다.`) SDK 표 한도(`DOCUMENT_AUTHORING_LIMITS`, 500행·32열·8,000칸)를 넘으면 꺼지고, 원본 글자를 읽는 동안은 `원본 글자 위치를 읽는 중입니다.`입니다.
- **표 주석으로·본문으로(표 주석).** 표 바로 뒤의 이어진 본문 하나 이상을 골라 표의 주석 끝에 붙입니다. 미주 호출이 든 본문은 꺼집니다. 원본에서 주석 상자 하나를 고르고 **본문으로**를 쓰면 표 바로 뒤에 꺼냅니다. 두 동작 모두 서식과 원본 상자를 유지하며 **되돌리기**로 복원할 수 있습니다. 표 잇기는 두 표의 주석도 순서대로 잇습니다. 주석 교정과 주석이 있는 표 잇기는 SDK 0.16.0의 `insertTableNote`·`removeTableNote`로 메모리에서 조합해 다른 고치기와 같이 `writeDocument` 한 번으로 저장합니다. 그 전의 공식 CLI `apply-batch`(표 잇기는 형제 임시 파일에 대한 `--dry-run`)와 문서 바이트·대응 자료가 같음을 합성 표본의 12단계(주석으로·본문으로·되돌리기, 주석 있는 표 잇기와 되돌리기)에서 확인했습니다.
- **표 잇기.** 이웃한 표 둘 이상을 고르고 열 수가 같으면 **합치기**가 켜집니다. 뒤 표의 첫 행이 첫 표의 머리글과 글자가 같으면(반복된 머리글) 버리고, 다르면 본문 행으로 둡니다. 캡션·이름표·고정 번호·번호 숨김은 첫 표의 것을 남깁니다. 뒤 표의 이름표를 가리키던 참조는 첫 표에 이름표가 있으면 본문·제목·참고 상자 안의 것을 첫 표로 바꾸고, 바꿀 수 없는 참조(표 칸·목록·각주 안, 또는 첫 표에 이름표가 없음)는 끊깁니다. 뒤 표에 캡션이 있거나, 끊길 참조가 있거나, 되돌리기가 원래 바이트로 돌아오지 않으면(표 정렬은 공개 노드에 보이지 않아 메모리에서 미리 왕복해 봅니다) **표 잇기** 확인 창에서 묻습니다. 되돌릴 수 없는 경우는 확인 뒤 되돌리기 기록을 비웁니다. 이은 표가 표 한도를 넘으면 잇지 않습니다.
- **미주로.** 본문 하나(주석 글)를 고르면 켜지고, 그 글이 앞 블록 끝의 미주가 됩니다. 주석 글만 골랐으면 같은 쪽에서 주석 글보다 앞에 있는 마지막 본문(제목·목록·표, 짝을 찾지 못해 본문이 된 다른 각주는 건너뜀) 끝에 호출을 붙이고, 붙일 본문과 주석 글을 함께 골랐으면(Shift 범위나 끌어 고르기) 처음 고른 본문 끝에 마지막 고른 주석 글을 붙입니다. 함께 고를 때 마지막 블록은 앞에 번호나 기호가 있는 주석 글이어야 합니다. 주석 글 앞의 원문 표시(숫자, `[18]` 같은 괄호 숫자, 기호 하나와 빈칸, 또는 위첨자 표시)는 떼어 냅니다. 리치오가 미주 번호를 다시 매깁니다. 미주 호출이 든 글, 붙일 본문을 찾지 못한 경우는 꺼지고 이유를 알립니다. 공개 SDK에 미주를 넣는 연산이 없어 이 동작과 그 되돌리기만 공식 CLI `apply-batch` 하나(`remove-block`, `insert-footnote` / `remove-footnote`, `insert-block`, `--if-revision`)로 저장하고, 저장 뒤에는 파일을 다시 읽어 검사합니다. 원본 상자는 미주 정의로 옮겨 갑니다.
- **참고로·본문으로(참고 상자).** 본문 하나를 참고 상자(`note`)로, 참고 상자 하나를 본문으로 바꿉니다. 참고 상자도 **문서에서 빼기**와 되돌리기가 됩니다(SDK 0.13.0의 `insertAdmonition`). 참고 상자와 이름표가 있는 제목을 함께 빼는 것은 이름표를 되살리는 CLI가 상자의 글자만 받아 따로 빼게 합니다.

### 고치기의 중복 읽기

한 번의 고치기에서 문서 전체를 읽어 해석하는 일이 두 번(고치기 전 읽기와 고친 뒤 검사) 있던 것을 줄였습니다.

- 처리 코드는 직전 고치기가 쓴 문서(또는 화면이 열며 읽은 문서)를 revision과 함께 문서 하나에 대해서만 기억합니다. 다음 고치기에서 파일 바이트의 SHA-256(리치오의 revision과 같은 값)만 계산해 기억한 revision과 같으면 다시 해석하지 않습니다. 다르면 기억을 버리고 지금처럼 읽습니다. 다른 PDF를 열거나 변환하면, 화면이 닫히면(`forget`), 쓰기나 검사가 실패하면 기억을 버립니다.
- 고친 뒤의 검사는 공식 쓰기가 돌려준 문서로 합니다. SDK 0.15.0(리치오 0407a0dd 이후)의 `writeDocument`는 쓴 바이트를 정규 쓰기 검증에서 다시 읽은 Core 문서와 그 revision을 돌려줍니다. 처리 코드는 파일의 바이트가 아직 그 revision인지만 확인하고, 블록 수·종류는 그 문서의 노드로 대응 자료와 맞춥니다. 그 전에는 메모리에서 만든 문서를 한 번 더 직렬화해 영수증과 비교했고, 미주 호출이 하나뿐인 블록을 뺄 때(공식 쓰기가 짝 잃은 정의를 떨굼)는 파일을 다시 읽었습니다. 이제 그 경우도 돌려받은 문서에 정의가 이미 없어 다시 읽지 않습니다. 쓰기가 문서를 돌려주지 않거나(SDK 0.15.0 전의 Host) 파일이 그 사이 바뀌었으면 지금처럼 파일을 다시 읽어 검사합니다. 공식 CLI로 저장하는 고치기(미주로, 이름표를 되살리는 되돌리기)는 CLI 결과에 문서가 없어, 변환 직후의 대응 만들기는 화면의 `saveDocument`가 저장해 처리 코드가 받은 문서가 없어 지금처럼 저장본을 읽습니다. 그 대응 만들기와 저장된 문서를 다시 열 때 읽은 문서는 기억해 첫 고치기와 첫 내용 저장 확인이 다시 읽지 않습니다.
- 대응이 어긋난 채 저장되는 것을 막던 보호는 그대로입니다. 밖에서 파일이 바뀌면 revision이 달라 기억을 쓰지 않고 다시 읽어 대응 자료의 revision과 비교해 멈추며, 쓰기의 revision 검사도 그대로입니다. 쓰기가 메모리의 문서와 다른 내용을 남기면 돌려받은 문서의 블록이 대응 자료와 달라 대응 표시를 멈추고 기억을 버립니다. SDK 통합 검사(`7` 검사)가 다른 내용을 남기는 쓰기, 문서를 돌려주지 않는 쓰기, 마지막 미주 호출을 뺀 쓰기를 넣어 확인합니다.

격리 HTTP Host에서 큰 PDF 표본 1(138쪽, 블록 약 1,320개)로 이웃한 두 본문의 합치기와 되돌리기를 3회씩, origin/master와 나란히 쟀습니다(처리 코드의 단계 시간, 누름부터 오른쪽 문서가 다시 보이기까지). 이 변경의 첫 고치기는 문서를 연 직후라 기억이 없습니다.

### 고친 결과 먼저 보이기

SDK 0.18.0(리치오 0f2dc01a, [litzio#1995](https://github.com/litzio/litzio/issues/1995))의 문서 보기 `apply`로, 고친 결과를 쓰기 전에 오른쪽 문서에 먼저 보입니다. 쓰기와 그 검사는 그대로 처리 코드의 공식 쓰기(`writeDocument`)가 맡습니다.

- **순서.** 처리 코드가 Core 연산을 메모리에서 마치면 쓰기 전에 SDK `documentViewChange(고치기 전 문서, 고친 문서)`로 바뀐 최상위 블록을 계산해 둡니다. 화면은 고치기 결과를 묻는 요청(`correctionResult`)으로 그것을 받아 문서 보기의 `apply`에 넘기고, 받았다고 알리면 처리 코드가 쓰기를 시작합니다. 화면이 5초 안에 받아 가지 않으면 그냥 씁니다. 쓰기와 대응 검사가 끝나면 같은 요청에 쓴 revision(`saved`)을 넘기고, 보기는 그 파일을 뒤에서 읽어 편집기를 다시 만들지 않고 이어받습니다. 원본 상자와 연결 띠는 그때 새 대응으로 돌아옵니다(쓰기를 기다리는 동안 띠가 멈추는 것은 리치오 계약이 감수한 것입니다).
- **머리 줄.** 계산하는 동안 `고치는 중`, 보기가 바뀐 블록을 보이고 쓰기를 기다리는 동안 `저장 중`, 이어받으면 `저장됨`입니다. 쓰기가 실패하면 보기가 직전 저장본으로 되돌리고 보기 안 오류 알림에 이유를 보이며 머리 줄은 `저장 실패`입니다. 밖에서 파일이 바뀌어 쓰지 않았으면 같은 방식으로 되돌리고 지금처럼 `문서가 바뀜`으로 멈춥니다.
- **다시 읽기로 돌아가는 경우.** 보기가 거절하거나(읽는 중, 저장하지 않은 내용 편집, 다른 revision) 5초 안에 답하지 않으면, 쓰기를 마친 뒤 지금처럼 `reloadKey`로 다시 읽습니다. 답하지 않은 보기는 그 화면에서 다시 쓰지 않습니다. 공식 CLI로 저장하는 고치기(미주로와 그 되돌리기, 이름표를 되살리는 되돌리기)는 쓰기 전 문서가 없어 지금처럼 다시 읽습니다. 검토 상태 바꾸기도 지금처럼 다시 읽습니다.
- **되돌리기**도 같은 흐름입니다.

### 오른쪽 문서에서 내용 고치기

대조 화면의 오른쪽 문서에서 블록 안의 글자, 표 칸, 인라인 수식, 목록 항목, 캡션을 바로 고칩니다. 변환이 놓친 표 칸의 수식이나 오타를 그 자리에서 채우는 용도입니다. 따로 켜는 단추는 없고 대응이 유효한 동안 늘 고칠 수 있습니다. 리치오 문서 보기의 내용 편집(SDK 0.14.0의 `editContent`)을 쓰므로 리치오 dee008ac 이후의 Host가 필요합니다. 그 전 Host에서의 동작은 확인하지 않았습니다. 블록의 수·순서·종류와 표의 행·열 수는 바뀌지 않으며, Enter로 문단 가르기나 여러 문단 붙여넣기 같은 구조 변경은 문서를 바꾸지 않고 리치오의 안내 `이 화면에서는 블록을 나누거나 합치거나 바꿀 수 없습니다. 블록 안의 내용만 고칠 수 있습니다.`만 뜹니다. 표 칸에서 `$…$`를 입력하면 인라인 수식이 됩니다.

- **저장과 대응 확인.** 고친 블록을 벗어나거나(다른 블록을 누름) 오른쪽 밖으로 focus가 나가거나 Ctrl+S를 누르면 리치오가 공식 저장 경로로 저장합니다. 저장이 받아들여지면 리치오 보기가 `onSave`로 Host가 받아들인 문서에서 만든 바뀐 최상위 블록의 노드(`blocks`, SDK 0.17.0)를 알립니다. 처리 코드는 파일이 아직 그 저장의 revision이고 저장 전 노드를 기억하고 있으면, 저장본을 읽지 않고 기억한 노드의 그 블록들을 받은 노드로 바꿔 블록 수·종류를 대응 자료와 맞춥니다(고치기와 같은 대응 검사). 맞으면 대응 자료의 revision과 인라인 스냅샷을 새 저장본으로 옮깁니다. `blocks`가 없거나(그 전 Host), 파일이 그 revision이 아니거나(교정·거부, 이어진 다른 쓰기), 저장 전 노드를 모르면 지금처럼 저장본을 한 번 읽습니다. 보기가 `저장 충돌`로 바뀌면 그 전에 받은 `blocks`는 쓰지 않고 다시 읽은 뒤의 revision부터 맞춥니다. 맞지 않거나, 저장이 시작된 revision이 대응 자료의 revision과 다르면 `문서가 바뀌어 대응을 표시할 수 없음`으로 멈춥니다. `blocks`로 옮긴 뒤에는 Core 문서가 없어 다음 구조 고치기가 저장본을 한 번 읽습니다(읽어 확인했으면 그 문서를 기억해 다시 읽지 않음). 오른쪽 문서는 다시 읽지 않습니다(보기가 이미 그 내용을 보이고 있음).
- **머리 줄.** 저장하는 동안(대응 확인 포함) `저장 중`, 저장하지 못하면 `저장 실패`, 밖에서 파일이 바뀌어 저장이 거부되면 `저장 충돌`을 보이고, 확인이 끝나면 `저장됨`을 보입니다.
- **구조 고치기는 기다림.** 오른쪽에 저장하지 않은 고침이 있거나, 저장·확인 중이거나, 저장 실패·충돌인 동안 합치기·나누기·종류·빼기·되돌리기와 우클릭 메뉴의 항목, 검토 상태 단추를 끕니다. 이유는 hover·focus로 보입니다(`고친 내용을 아직 저장하지 않았습니다. 다른 블록을 누르면 저장됩니다.`, `고친 내용을 저장하는 중입니다.`, `고친 내용을 저장하지 못했습니다. 문서 보기에서 Ctrl+S를 눌러 다시 저장하세요.`, `밖에서 문서가 바뀌어 고친 내용을 저장하지 못했습니다. 문서 보기의 다시 읽기를 누르세요.`). 저장과 확인이 끝나면 다시 켭니다. **변환한 문서**(뒤로), **PDF 고르기**, **다시 변환**은 누르면 저장과 확인이 끝난 뒤 이어서 실행합니다.
- **되돌리기 기록.** 내용이 저장되면 고친 블록에 닿는 구조 고치기와 그보다 오래된 기록을 지우고, 고친 블록과 떨어진 최근 기록은 남깁니다. 되돌리기는 고치기 때의 블록 내용을 그대로 다시 넣으므로, 고친 블록이 그 고치기가 바꾼 범위(앞뒤 한 블록 포함) 안에 있으면 방금 고친 내용이 사라지기 때문입니다. 범위는 고치기 전후 문서의 최상위 블록을 앞뒤에서 맞대어 정하며 제목의 구역 범위와 번호처럼 순서에서 나오는 값은 빼고 비교합니다. 처리 코드가 저장 전 문서를 기억하지 못하면 기록을 모두 지웁니다.
- **밖에서 바뀐 것.** 대조 화면이 보이는 동안 2초마다 처리 코드가 문서 파일 바이트의 SHA-256만 계산해 대응 자료의 revision과 비교합니다. 다른 탭에 가 있거나 창이 보이지 않으면 쉬고, 오른쪽에 저장하지 않은 고침이 있거나 저장·확인 중이면 건너뜁니다. 다르면 저장본을 읽어 블록 수·종류가 같을 때(문서 탭이나 비서가 내용만 고친 경우) 대응을 새 revision으로 옮기고 오른쪽 문서를 다시 읽으며, 맨 위에 보이던 블록을 같은 높이에 둡니다(`밖에서 고친 내용을 반영함`). 다르면 바뀐 것을 안 그 자리에서 `문서가 바뀌어 대응을 표시할 수 없음`을 알리고 오른쪽 문서를 읽기 전용으로 다시 읽습니다. 한 번 멈춘 파일은 다시 바뀌기 전까지 다시 읽지 않습니다. 닫혀 있는 동안 내용만 바뀐 문서도 다시 열 때 같은 검사로 이어 붙입니다.
- **충돌.** 오른쪽에서 고치는 중에 밖에서 파일이 바뀌면 리치오 보기가 저장을 거부하고 고친 내용을 남긴 채 `다시 읽기(고친 내용 버림)` 안내를 보입니다. 다시 읽으면 위의 검사로 대응을 확인합니다.
- **한계.** 블록의 수와 종류만 봅니다. 같은 수·종류인데 내용이 블록 사이로 옮겨진 경우(한 문단의 글자를 이웃 문단으로 옮기고 지움)는 구별하지 못하고 원래 원본 상자에 이어 붙입니다. 리치오 보기를 닫을 때의 확인과 복구 기록은 없으므로, 저장하지 않은 고침은 블록 하나 범위에서 잃을 수 있습니다.

**확인 범위.** 리치오 없이 도는 단위 검사(`shared/test/follow.test.mjs`)가 블록 종류 비교, 고친 블록 찾기, 고치기의 범위와 순서에서 나오는 값 빼기, 되돌리기 기록 남기기, 확인 결과의 판정, 머리 줄 상태와 이유, 저장된 `blocks`로 노드·종류 목록 바꾸기와 최상위 블록이 아닌 `blocks`의 거부를 봅니다. SDK 통합 검사(`pdf/test/content-edit-host.test.mjs`)가 SDK 쓰기로 보기의 저장을 흉내 내어 PDF와 워드의 대응 옮기기, 구조가 바뀐 파일과 다른 revision에서 시작한 저장의 멈춤, 표 칸을 고친 뒤 떨어진 합치기의 되돌리기와 합친 문단을 고친 뒤 기록 지우기를 봅니다. 같은 검사가 `inspect`와 같은 모양으로 만든 `blocks`로 읽지 않고 옮긴 대응이 저장본을 읽은 것과 같은지, 파일이 그 저장의 revision이 아니면 읽는지, 다른 종류로 알린 블록에서 멈추는지를 봅니다.

### 여러 블록 한 번에 빼기

표지·목차 쪽처럼 뺄 블록이 많은 쪽을 몇 번의 동작으로 정리합니다.

- **끌어 고르기.** 원본 쪽의 빈 곳(상자가 아닌 곳)을 누르고 5px 넘게 끌면 리치오의 선택 색(`--id-color-interaction`) 테두리의 사각형이 그려지고, 놓으면 사각형에 걸친 원본 상자가 모두 골라집니다. Shift를 누른 채 끌면 지금 고른 것에 더합니다. 원본 칸의 위·아래 가장자리 24px 안으로 끌면 칸이 스크롤되어 쪽을 넘어 고를 수 있습니다. 아무 상자에도 걸치지 않으면 고른 것을 지웁니다. 상자 위에서 누른 것은 지금처럼 그 상자의 누르기·Shift+누르기·우클릭이고, 5px 안의 움직임은 끌기가 아니라 누르기입니다. 스크롤바, 휠, Ctrl+휠 배율은 그대로이며 배율을 바꾸거나 Esc를 누르면 끌기를 멈춥니다. 원본 칸의 글자는 선택되지 않습니다. 워드 대조(고치기 없음)에서는 끌어도 아무 일이 없습니다.
- **문서에서 빼기**는 고른 것이 모두 본문·제목·목록·참고 상자면 여러 개여도 켜지고 한 번에 뺍니다. 표·그림·각주처럼 지금 뺄 수 없는 종류가 섞이면 꺼지고 `고른 것에 표 블록이 있어 뺄 수 없습니다. 본문·제목·목록·참고 상자만 뺄 수 있습니다.`처럼 그 종류를 이유로 보입니다. 같은 문서 블록의 원본 상자를 일부만 고른 경우의 이유는 지금과 같습니다.
- **Delete.** 원본 칸에 초점이 있고 고른 것이 있으면 **문서에서 빼기**와 같습니다. 꺼져 있으면 아무 일도 없습니다. 끌어 고른 뒤에는 첫 상자에 초점이 가므로 바로 Delete를 누를 수 있습니다.
- **이 쪽에서 고른 것만 남기기**(우클릭 메뉴). 고른 블록이 모두 한 쪽에 있을 때 켜지고, 그 쪽의 다른 블록 가운데 뺄 수 있는 것을 한 번에 뺍니다. 문서 제목 상자를 우클릭해도 같은 항목이 있어, 표지에서 제목을 **문서 제목으로** 보낸 뒤 바로 나머지를 뺄 수 있습니다. 표·그림·각주, 다른 쪽으로 이어지는 블록, 고른 블록과 같은 문서 블록에 묶인 상자는 그대로 두고, 남긴 것이 있으면 `이 쪽의 표 1개는 뺄 수 없어 그대로 두었습니다.`처럼 한 문장을 도구 줄 아래에 보입니다. 고른 것은 그대로 고른 채 남습니다. 더 뺄 것이 없으면 `이 쪽에 더 뺄 수 있는 블록이 없습니다.`, 여러 쪽에 걸치면 `고른 블록이 모두 한 쪽에 있어야 합니다.`로 꺼집니다.
- 여러 블록을 빼는 것은 한 번의 동작입니다. 블록 하나를 뺄 때와 같이 SDK로 문서를 한 번 쓰고(뒤 블록부터 빼고, 뺀 제목의 이름표도 함께 뺌) 같은 사후 검사를 거친 대응 자료를 저장합니다. 대응 자료는 블록을 하나씩 뺀 것과 같고 이력만 한 줄입니다. **되돌리기** 한 번에 모두 돌아옵니다(이름표를 되살리는 되돌리기는 지금처럼 공식 CLI). 뺀 블록 가운데 하나라도 각주 호출이 있으면 지금처럼 확인한 뒤 되돌리기 기록을 비웁니다.

**확인 범위.** 리치오 없이 도는 단위 검사(`pdf/test/bulk-remove.test.mjs`)가 여러 블록 빼기의 대응 자료와 블록 하나씩 뺀 결과의 일치(제목의 이름표, 두 블록이 부른 각주, 같은 문서 블록의 목록 항목 포함), 이웃하지 않은 블록, 되돌리기, 빼기의 켜짐과 이유, `고른 것만 남기기`의 대상과 알림 문장, 끌어 고르기의 상자 판정, 종류 글자를 봅니다. SDK 통합 검사는 이웃하지 않은 두 블록을 한 번에 뺀 문서 바이트와 대응 자료가 하나씩 뺀 것과 같은지, 되돌리기 한 번에 원래 바이트로 돌아오는지(첫 검사), 문단과 이름표 있는 제목을 함께 빼고 되돌리는지(S-02 검사)를 봅니다.

격리 HTTP Host(리치오 0d0d43cd, Windows, 1440·1920×1080)에서 공개 LSR(1쪽 포함, 50%)로 소유자의 사례를 origin/master와 나란히 했습니다. 1쪽의 대제목을 **문서 제목으로**(우클릭과 메뉴, 2회) 보낸 뒤 나머지 17블록을 빼는 데 origin/master는 우클릭과 **문서에서 빼기**를 17번 되풀이해 모두 36회(약 10.1초), 이 변경은 제목 상자 우클릭과 **이 쪽에서 고른 것만 남기기**로 4회였습니다. 끌어 고른 뒤 Delete로도 4회(끌기 1, Delete 1)였습니다. 두 판의 마지막 상태는 1쪽 상자 0개, 문서 블록 92개로 같았고, 되돌리기 한 번에 17블록이 돌아왔으며, 다시 뺀 뒤 화면을 닫고 목록에서 다시 열어도 제목과 뺀 상태가 그대로였습니다. 오른쪽 문서 갱신(`pdf-import-correction`)은 블록 하나를 Delete로 뺄 때 0.54·0.44·0.42초, 1~2쪽을 끌어 고른 24블록을 한 번에 뺄 때 0.54·0.49·0.45초였습니다(각 3회). origin/master에서 블록 하나씩 뺀 17번은 0.41~0.52초였습니다. 같은 Host에서 5px 안의 누르기가 상자 선택으로 남는 것, Shift+끌기로 2개에서 5개로 더해지는 것, 표가 섞이면 빼기가 꺼지고 Delete가 아무 일도 하지 않는 것, 기존 합치기·나누기·종류 바꾸기·문서 제목으로·하나 빼기와 각각의 되돌리기, 워드 대조에서 끌어도 사각형이 없는 것을 확인했습니다. 캡처: [끌어 고르는 중](pdf/test/captures/bulk-remove/drag-1440.png), [여러 개 고른 메뉴](pdf/test/captures/bulk-remove/menu-many-1440.png), [뺀 뒤](pdf/test/captures/bulk-remove/removed-1440.png), [종류 글자가 보이는 도구 줄](pdf/test/captures/bulk-remove/toolbar-kind-pdf-1440.png). 설치형 Desktop은 검사하지 않았습니다.

### 문서 제목

첫 번호 조항 위의 대제목은 제목 단계가 아니라 리치오의 문서 제목(머리말 `title`)으로 보냅니다. 조항 제목의 단계는 번호 깊이 그대로 둡니다(`1. Overview`는 제목 1). 변환은 문서 제목을 스스로 정하지 않습니다. 번호 없는 큰 글자는 지금처럼 제목 후보 경고(사례집 H-01)로 남고, 사람이 **종류 → 문서 제목**(메뉴는 **문서 제목으로**)을 고릅니다.

- 본문이나 제목 블록 하나를 골랐을 때만 쓸 수 있습니다. 여러 개, 목록·표·그림·각주, 미주 호출이 든 블록, 수식·인용이 든 블록은 비활성이고 이유를 메뉴와 **종류** hover에 보입니다(**종류**의 다른 항목은 쓸 수 있을 때 `문서 제목: …`으로 표시).
- 블록의 글자에서 서식을 떼고 줄바꿈과 연속 빈칸을 빈칸 하나로, 앞뒤 빈칸을 다듬어 제목으로 씁니다. 그림·표 참조는 원문 글자(`Figure 3`)로 씁니다.
- 그 블록은 본문에서 빠집니다. 원본 상자는 제목 색으로 표시하고 상자 옆에 **제목**을 적습니다. 상자를 고를 수 있으며 hover·focus 설명은 **문서 제목으로 쓰임**입니다. 이 상자에서 종류 바꾸기·합치기·나누기·빼기는 사용할 수 없고 **되돌리기**로 복원합니다. 새 색 범례는 더하지 않았습니다. 제목 후보 경고는 블록과 함께 사라집니다.
- 이미 제목이 있으면 **문서 제목 바꾸기** 확인 창에서 묻습니다. 이전 제목 블록은 본문으로 되살리지 않습니다.
- **되돌리기**는 블록을 원래 종류와 자리로, 문서 제목을 이전 값(없었으면 없음)으로 함께 돌립니다. 기존 되돌리기 기록과 대응 자료를 그대로 씁니다.
- SDK 0.13.0의 `updateDocumentTitle`로 블록 빼기와 함께 메모리에서 바꾸고 다른 고치기와 같이 `writeDocument` 한 번으로 저장합니다(그 전에는 공식 CLI `apply-batch`였습니다). 이름표가 있는 제목을 보낸 뒤의 되돌리기는 이름표를 되살리는 SDK 연산이 없어 지금처럼 공식 CLI로 저장합니다.

제목 상자를 고르면 연결 띠를 그리지 않고 오른쪽 문서를 움직이지 않습니다. 첫 본문을 대상으로 이동하는 실험에서는 제목이 보이는 영역 밖으로 밀렸습니다.

격리 HTTP Host에서 공개 LSR의 표지를 포함해 변환하고, 제목으로 보내기·선택·되돌리기·다시 보내기·문서 목록에서 다시 열기와 실제로 뺀 블록의 빗금을 확인했습니다. [이전](pdf/test/captures/title-box/before-1440.png), [변경 후](pdf/test/captures/title-box/after-1440.png), [어두운 화면](pdf/test/captures/title-box/dark-1440.png)을 확인했습니다.

### 원본의 영역 표시

일반 블록은 종류별 옅은 면과 왼쪽 띠로 표시합니다. 마우스를 올리거나 키보드로 초점을 주면 블록 윤곽과 설명이 보입니다. 스크롤 추적은 띠 색만 바꿉니다. 경고·단계·고침은 왼쪽 여백에 나란히 둡니다. 줄 선택선은 나누기 중에만 표시합니다. 제외 영역은 빗금으로 구별하고 hover와 focus에서 제외 이유를 표시합니다. 설명은 조작 줄 아래의 예약된 공간에 있어 원문을 덮지 않습니다. 종류별 색과 조작 방법은 같습니다.

격리 HTTP Host의 공개 표본에서 7쪽 각주 선택 전후, 다중 선택, 나누기, 머리글·바닥글과 사용자가 뺀 영역, 단계·경고·고침의 동시 표시, 표와 그림, 밝고 어두운 테마를 확인했습니다. 종류별 면은 토큰 색 12%, hover/focus 18%, 선택 22%를 곱하기 혼합으로 표시합니다. 혼합은 쪽 단위로 묶습니다. 제외는 text-muted 70%와 surface 30%를 섞은 회색에서 80% 빗금 선(2px, 주기 7px)과 35% 면을 만듭니다. 제외 영역만 사방 3px 넓혀 작은 머리글·바닥글에서도 무늬가 보이게 합니다. 범례도 같은 무늬입니다. 임의 PDF의 극히 좁은 왼쪽 여백과 본문까지 겹친 원본 상자는 확인하지 않았습니다. 설치형 Desktop은 이번 변경에서 검사하지 않았습니다.

### 쪽 고르기의 검증과 비용

격리 HTTP Host에서 공개 표본(책갈피 있음/제거한 사본)과 별도 138쪽 PDF로 선택 → 격자 → 변환·대조, 누르기·Shift 범위·크게 보기·키보드 조작, 취소·다시 변환·저장본 바로 열기를 확인했습니다. 공개 표본 캡처는 `pdf/test/captures/page-picker/`입니다. 범위 선택과 공개 PDF의 첫 책갈피 대응은 리치오 없이 검사합니다.

미리 보기는 화면과 300px 주변만 그리며 동시에 두 장까지 그립니다. 지나간 쪽은 대기·진행 중 그리기를 취소합니다. 완성된 캔버스는 격자를 닫을 때까지 재사용합니다. 138장을 그린 뒤 왕복 스크롤에서 크기 재설정 0건을 확인했습니다. 크게 보기는 해당 쪽만 큰 배율로 그립니다.

SDK 0.6.0 Host의 1440×1000 창에서 128px·8열로 24장이 완전히 보이고 일부가 보이는 것까지 32장입니다. 첫 화면 완료는 5.52초에서 1.75초로 줄었습니다. 파일 전달 0.56초, PDF 준비 0.12초, 책갈피 대응 0.01초였고 제안은 별도로 진행합니다. 완성된 138장으로 왕복했을 때 재그리기 0건, 전체 격자 스크롤의 50ms 초과 long task는 17회·최대 71ms였습니다. 캔버스 픽셀 저장량은 약 11.2MiB이며 GPU·프로세스 전체 메모리 값은 아닙니다.

처리 코드는 같은 sha256의 추출 Promise와 결과를 한 파일분만 메모리에 보관합니다. 제안 완료 뒤에는 기존에도 추출을 다시 하지 않았습니다. 이제 제안 추출 도중 변환을 시작해도 같은 작업을 기다리며 중복 추출하지 않습니다. 같은 선택의 변환은 변경 전 14.48초, 변경 후 13.30초였으며 둘 다 추출 대기는 약 0ms였습니다. 이 차이를 추출 재사용에 의한 개선으로 해석하지 않습니다. 제안 응답을 끝까지 보류하고 그 전에 시작한 변환은 남은 추출 대기 2.11초를 포함해 14.96초였습니다. 저장된 제외 선택이 사용자 선택 그대로이고, 늦은 응답이 대조 화면을 바꾸지 않는 것을 확인했습니다.

제안 응답을 늦춰 직접 포함·제외와 Shift 범위를 먼저 바꾼 경우도 확인했습니다. 앞 부속을 포함한 변환에서 발견한 중복 각주 정의는 F-07로 기록했고, 모호한 짝을 글자로 보존하여 공식 저장과 CLI 검사를 통과했습니다. 설치형 Desktop, 다른 OS, 회전·세로쓰기·가로세로가 혼재한 대형 PDF는 검증하지 않았습니다.

### 양방향 대조 검증

PR litzio#1716을 포함한 격리 HTTP Host에서 공개 표본과 별도 큰 PDF의 양쪽 휠·스크롤바·키보드 이동, 번갈아 조작하기, 함께 스크롤 끄기, 오른쪽 제목·문단·목록·표·그림 누르기와 고친 뒤 새 대응을 확인했습니다. 오른쪽 누르기로 선택한 문단을 합치고 되돌린 뒤에도 이동했습니다. 더블클릭한 단어 선택이 유지됐습니다. 공개 표본의 일부 대응을 비운 시험 자료에서 누르기는 기존 선택을 유지하고 스크롤은 바로 앞 블록의 원본을 사용했습니다.

큰 PDF에서 1800px 휠 이동마다 120ms와 두 animation frame을 기다리며 처음부터 끝까지 측정했습니다. 50ms 초과 long task는 왼쪽 15회·최대 107ms, 오른쪽은 새로 연 PDF에서 25회·최대 109ms였습니다. 앞선 순회로 그림이 준비된 상태의 오른쪽은 0회였습니다. 이전 왼쪽 기록 33~34회·최대 99~108ms와 비교해 최댓값은 비슷하지만 조작·캐시 조건이 같지 않아 횟수 차이를 성능 개선으로 해석하지 않습니다. 빠르게 끝까지 옮긴 뒤 약 120ms 간격으로 2.3초 동안 두 칸 위치를 기록했고, 왼쪽 주도는 263ms 이후, 오른쪽 주도는 137ms 이후 안정적이었습니다. 소유권 해제를 위한 고정 대기는 없으며 기존 왼쪽 스크롤의 150ms 모음만 유지합니다. packaged Desktop과 다른 OS는 검증하지 않았습니다. 터치패드·터치는 지원 대상이 아닙니다.

### 가벼운 위쪽 줄과 블록 메뉴

도구 줄 왼쪽은 범례와 선택 동작을 바꿔 보이고, 오른쪽은 확인할 곳 넘기기·함께 스크롤·배율·되돌리기를 한 묶음으로 둡니다. 되돌리기는 기록이 있을 때만 한 자리에 나타납니다. 종류 선택은 공개 Select의 hideLabel을 쓰며 접근성 이름은 유지합니다. 도구 줄은 32px 버튼 한 줄이고, 그 아래 안내는 24px 한 줄을 늘 차지합니다. 나누기 안내가 확인할 곳 이유보다 우선합니다. 내부 폭이 940px 이하면 오른쪽 묶음을 다음 줄로 보내 범례와 선택 동작 사이의 높이 차이를 막습니다.

지정 격리 Host에서 공개 표본의 선택 없음·하나·여러 개·나누기·경고 이동·되돌리기 상태에서 원본 칸 시작 높이가 같은 것을 확인했습니다. 1440·1000·900·800px 창에서 가로 넘침과 겹침을 확인했습니다. 메뉴에서 합치기·나누기·종류·빼기와 되돌리기를 실행했고, 메뉴 안의 비활성 이유와 키보드 진입·focus 복귀를 확인했습니다. 공개 표본 캡처는 pdf/test/captures/top-bar-context-menu/에 있습니다. packaged Desktop과 다른 OS는 확인하지 않았습니다. 터치패드·터치는 지원 대상이 아닙니다.

### 연결 띠와 훑어보기 배율

대조 화면은 리치오의 `LinkedDocumentView`를 사용합니다. 원본과 문서가 도구 줄 아래 남은 높이를 채우고 각 칸에서 따로 스크롤합니다. 종류별 색의 연결 띠는 채움으로 표시되며, 창 높이와 스크롤 위치에 맞춰 다시 그려집니다. 띠를 누르면 대응 블록을 고릅니다. 쪽을 넘는 블록은 상자마다 이어집니다. 저장본이 바뀌어 대응을 표시할 수 없으면 띠를 숨깁니다.

Shift로 여러 블록을 고르면 마지막 블록에 리치오 윤곽과 활성 띠가 보입니다. 나머지 선택은 원본의 옅은 면과 가는 선으로 표시하며, 도구 줄에 전체 선택 개수와 고른 블록의 종류(`본문`, `제목 2`, `목록`, `표`, `각주`처럼 범례의 이름, 섞였으면 `여러 종류`, 문서 제목 상자는 `문서 제목`)가 나옵니다. 오른쪽 문서의 블록을 눌러 고른 경우도 같습니다.

도구 줄 오른쪽 배율과 양쪽 칸 안의 Ctrl+휠은 100·75·50·40%를 함께 바꿉니다. 기본은 75%이며 브라우저의 기존 localStorage 방식으로 기억합니다. 칸 밖의 Ctrl+휠은 가로채지 않습니다. 원본은 기준 위치의 블록을 같은 높이에 두고 새 크기의 canvas를 다시 그립니다. 문서는 공개 scale의 재배치와 위치 유지를 사용합니다. 작은 배율에서 보이는 쪽과 앞뒤 두 쪽을 그리고, 40%에서는 단계와 고침의 여백 글자를 점으로 줄입니다. 우클릭·선택·나누기 좌표는 같은 축소 비율을 사용합니다.

격리 HTTP Host의 합성 표본에서 두 스크롤 영역은 1440×1000에서 664px, 1440×700에서 364px였고 탭 하단까지 채웠습니다. [밝음](pdf/test/captures/linked-document-view/light-selected.png), [어두움](pdf/test/captures/linked-document-view/dark-selected.png), [1440×700](pdf/test/captures/linked-document-view/short-selected.png), [여러 블록 선택](pdf/test/captures/linked-document-view/multiple-selected.png)에서 확인할 수 있습니다.

아래 수치와 이전 캡처는 화면 자체 연결 띠를 쓰던 버전의 기록입니다. 격리 HTTP Host(SDK 0.9.0)에서 공개 표본과 큰 PDF로 네 배율, 양방향 스크롤, 양쪽 hover, 띠 클릭, 한쪽 화면 밖으로 빠지는 띠, 표·그림·쪽을 넘는 문단과 제외된 쪽 구간을 확인했습니다. 50%에서 합치기·나누기와 각각의 되돌리기 뒤 새 대응이 그려졌습니다. 40%의 우클릭 메뉴와 작은 여백 점도 확인했습니다. stale에서는 띠가 없습니다. 공개 표본의 스크롤 직후 다음 frame에서 측정한 양 끝 위치 오차는 0.01px 이내였고, 네 배율을 왕복했을 때 원본 기준 블록의 높이 변화는 0.3px 미만이었습니다. Ctrl+휠은 양쪽 안에서만 브라우저 확대를 막았고 재진입 시 배율이 복원됐습니다. 1000·900px에서도 가로 넘침이 없으며 800px에서는 기존 세로 배치와 함께 띠를 숨깁니다.

공개 캡처 여섯 장은 pdf/test/captures/links-and-scale/에 있습니다. 1440×1120 창의 50% 캡처에는 일부까지 3쪽·전체 1쪽, 40%에는 일부까지 4쪽·전체 2쪽이 보입니다. 기본 배율은 소유자가 정한 75%이며 기억된 선택이 있으면 그 값을 씁니다. 옅은 띠는 글자를 덮지 않으며 선택하기 전의 대응 방향을 알 수 있어 유지하는 편이 낫다고 판단했습니다. 겹치는 띠를 하나씩 추적하는 용도보다는 hover·선택으로 짝을 찾는 방식이 명확합니다.

큰 PDF를 매번 다시 열고 1800px 휠 이동마다 120ms와 두 frame을 기다려 끝까지 측정했습니다. 선 없음은 시험용 설치 사본에서 SVG만 빼고 같은 틈·배치 보고·배율을 유지했습니다. 각 칸은 50ms 초과 long task 횟수 / 최댓값입니다.

| 조건 | 왼쪽 | 오른쪽 |
| --- | --- | --- |
| 이전 양방향 스크롤 측정, 100% | 15 / 107ms | 25 / 109ms |
| 이번 100%, 선 없음 | 25 / 127ms | 37 / 123ms |
| 이번 100%, 선 있음 | 27 / 100ms | 31 / 122ms |
| 이번 50%, 선 없음 | 29 / 121ms | 33 / 165ms |
| 이번 50%, 선 있음 | 25 / 100ms | 25 / 115ms |

한 번씩의 측정에서 선 유무에 따른 일관된 long task 증가는 없었습니다. 이전과는 칸 폭·SDK·보이는 캔버스 수가 달라 횟수 차이를 개선으로 해석하지 않습니다. 별도 100% 오른쪽 순회에서 SVG 갱신 395회의 99백분위는 약 1.1ms, 최댓값은 약 2.1ms였습니다. 이는 경로 갱신의 실행 시간이며 PDF 그리기와 SDK 배치의 비용을 포함하지 않습니다. 설치형 Desktop·다른 OS·임의 회전 PDF는 확인하지 않았습니다. 터치패드·터치는 지원 대상이 아닙니다.

master의 PDF별 폴더 저장 변경을 병합한 뒤 litzio#1725 이후 Host에서도 두 PDF를 새로 변환했습니다. 공개 표본과 큰 PDF의 합치기·나누기·되돌리기와 띠를 다시 확인하고 캡처를 갱신했습니다. 위 순회 비용은 저장 변경 병합 전 SDK 0.9.0 Host에서 잰 값입니다.

### 누른 블록의 짝 맞추기

원본 상자를 누르면 오른쪽 문서의 짝이 그 상자의 보이는 윗선과 같은 높이에 옵니다. 누른 상자의 블록에서 화면에 걸친 첫 상자의 윗선(원본 칸 위 가장자리 기준 px)을 공개 `document.target.top`으로 넘기고, 누를 때마다 `target.request`를 바꿉니다. 그래서 문서만 스크롤한 뒤 같은 블록을 다시 눌러도 다시 맞춥니다. 위 가장자리에 걸려 잘린 상자는 음수 높이를 넘겨 문서 블록도 같은 만큼 잘립니다. 문서 블록을 누르면 반대로 문서는 그대로 두고, `onVisibleBlockLayoutChange`가 알린 그 블록의 윗선에 원본 블록의 첫 상자 윗선이 오도록 원본 칸을 직접 스크롤합니다. 양쪽 모두 처음·끝 스크롤 한도에서는 갈 수 있는 데까지만 가고, 차이가 8px 이하면 움직이지 않습니다(리치오 `target.top`과 같은 기준). 원본이 한도에 막혀 맞추지 못하면 문서는 움직이지 않습니다. 경고 이전·다음은 지금처럼 원본 블록을 원본 칸 높이의 1/3 지점에 두고, 문서 짝을 그 높이에 맞춥니다. 고치기 뒤 다시 읽을 때도 결과 블록의 원본 상자가 보이면 같은 높이에 맞춥니다. 이 기능은 이전의 "이미 보이면 그대로 둔다" 동작을 대신합니다.

**함께 스크롤과의 우선.** 누른 직후에는 누른 정렬이 이깁니다. 누르기는 그 짝을 보겠다는 분명한 요청이고, 함께 스크롤은 훑어보는 동안의 대략적인 대응이기 때문입니다. 누를 때 원본에서 기다리던 따라가기를 취소하고, 정렬로 생긴 원본 스크롤은 사용자 입력이 아니므로 따라가기를 일으키지 않으며, 문서 쪽 `target` 이동은 리치오가 보이는 블록 알림을 보내지 않습니다. 다음 휠·스크롤바·스크롤 키 입력부터 그 칸이 다시 주인이 되어 함께 스크롤이 따라옵니다. 누른 뒤 아무 칸도 스크롤하지 않았으면 배율을 바꿔도 누른 짝을 기준으로 원본을 다시 놓고 문서 짝을 같은 높이에 다시 맞춥니다.

격리 HTTP Host(리치오 07cdfe31)에서 공개 LSR 표본으로 확인했습니다. 두 윗선의 차이는 원본 클릭(문서 짝이 위·아래·안, 위 가장자리에 잘린 상자, 75%·100%) 0.22~0.36px, 문서 클릭(원본 짝이 위·아래·안) 0.06~0.47px, 문서만 스크롤한 뒤 같은 블록 다시 클릭 0.31~0.36px였습니다. 함께 스크롤을 켜고 원본 휠 뒤 원본 클릭, 문서 휠 뒤 문서 클릭, 경고 다음·이전, 배율 75%↔100%, 본문을 제목으로 고친 뒤와 되돌린 뒤 모두 0.22~0.33px였고, 매번 정렬 뒤 40 animation frame 동안 두 칸의 스크롤 위치가 바뀌지 않았습니다(흔들림 없음). 한도에서는 문서 처음(문서 0px에서 34.8px 차이로 멈춤)·문서 끝(끝에서 64.0px 차이)·원본 처음(원본 0px에서 31.8px 차이, 문서는 그대로)을 확인했습니다. 이 표본에서는 원본 끝 한도에 막히는 문서 블록이 없어 원본 끝은 단위 검사로만 확인했습니다. 앞의 두 경고는 문서 처음에 있어 같은 이유로 3.4~26.1px 차이에서 멈춥니다(75%). ### PDF별 저장

`X.pdf`는 원래 위치에 두고 `X/X.md`, `X/X.pdf-source.json`, `X/assets/`에 저장합니다. 그림 key는 그림으로 저장되는 표·그림 순서로 `table-001`, `figure-002`처럼 정합니다. 실제 파일은 같은 이름의 `.png`이고, 기존 이름에 다른 내용이 있으면 Host 계약에 따라 내용 해시 8자리가 붙습니다. 원본 위치는 대응 자료의 PDF 이름과 결과 폴더의 부모로 찾습니다. 이전 평면 저장 위치를 찾거나 변환하는 코드는 없습니다.

고친 이력은 PC 시간대에 관계없이 한국 시간 `YYYY-MM-DD HH:mm:ss`를 사용합니다. 목록은 대응 자료의 수정 시각을 한국 시간 기준의 ‘오늘 14:20’, ‘어제’, ‘11월 17일’ 등으로 보여 줍니다. 대응 자료에는 최초 변환 시각이 없으며, 저장본을 다시 열거나 교정하면 수정 시각이 바뀔 수 있습니다.

이번 변경은 격리 HTTP Host에서 공개 LSR와 책갈피를 제거한 LSR 사본을 같은 입력 폴더에서 변환했습니다. 각각 그림 10개가 별도 assets에 저장되고 대조 화면·일반 문서 탭에서 표시됐으며 합치기·되돌리기와 목록 재열기를 확인했습니다. 재변환 전후 모두 문서 1개·대응 자료 1개·그림 10개였고 복구 사본은 남지 않았습니다. 큰 디지털 PDF에서도 저장과 그림 정리를 확인했습니다. 실패 후 수동 복구, 다른 OS와 packaged Desktop은 확인하지 않았습니다. 터치패드·터치 입력은 검사 범위가 아닙니다.

### 문서 검토 상태

새 변환과 다시 변환은 항상 초안으로 저장합니다. 머리 줄과 목록의 검토 상태는 문서에서 읽습니다. 검토 완료 버튼은 approved로, 초안으로 되돌리기는 draft로 바꿉니다. 검토 중과 상태 없음에서는 검토 완료를 제공합니다. 변환 경고가 남아 있어도 완료할 수 있고 hover·focus에 남은 개수를 알립니다. 문서가 바뀌거나 고치는 중에는 이유와 함께 버튼을 비활성화합니다. 상태만 바꿀 때 대응 자료의 revision과 기존 되돌리기의 revision을 맞추며 고치기 이력에는 추가하지 않습니다.

이번 상태 변경은 격리 HTTP Host에서 공개 표본의 변환 → 초안 → 검토 완료 → 합치기·되돌리기 → 초안 복귀, 공식 CLI의 검토 중 변경 후 재열기, 재변환 뒤 초안과 check 유효성을 확인했습니다. 외부 상태 변경도 revision을 바꾸므로 대응 이동과 상태 버튼은 기존 보호에 따라 멈춥니다. 새 배율 기억을 지운 뒤 75%, 50%를 선택한 뒤 화면 재열기에서 50% 유지와 경고 개수 설명의 keyboard focus를 확인했습니다. 1440px의 초안·검토 완료·목록·다크 캡처는 pdf/test/captures/draft-status-*.png입니다. 머리 줄 control의 높이·중심과 줄 넘침을 직접 확인했습니다. 설치형 Desktop·다른 OS·터치 입력과 저장 도중 강제 종료는 확인하지 않았습니다.

### 괘선 표를 글자로 옮기기

가는 채움(1.5pt 미만)과 stroke 경로에서만 괘선을 얻습니다. 넓은 채움 사각형의 배경은 경계로 쓰지 않으며, 열 경계는 전체 높이의 15% 이상을 덮는 선분으로 정합니다. 2pt 이내 선 위치를 모으고 이웃 칸의 경계가 절반 이상 없으면 병합 칸으로 복원합니다. 짧은 내부 분수선은 격자 경계로 쓰지 않습니다.

머리글은 경계를 가로지르는 병합을 따라 늘립니다. 마지막 머리글 행에서 시작하고 끝나는 가로 병합(전체 폭 제외)은 바로 아래 행이 그 열 범위를 둘 이상의 칸으로 나눌 때만 한 줄 늘립니다. 끝까지 늘어나면 한 줄로 되돌립니다. 열별 머리글은 같은 칸을 한 번씩 ` / `로 잇고, 본문 병합 값은 덮는 칸마다 반복합니다. 전체 폭 제목은 첫 칸에만 두며, 아래에 이어진 전체 폭 주석 행은 자기 원본 상자를 가진 본문으로 뺍니다. 테두리 아래에서 왼쪽 정렬로 시작한 글자도 주석 문단 하나로 보존합니다. 문장별로 다시 나누지는 않습니다. 칸 안의 줄은 문단과 같은 하이픈 잇기 함수를 씁니다. 같은 보이는 칸 줄에서 바로 앞 낱말보다 크기가 0.8배 미만이고 기준선이 1pt 넘게 올라간 낱말도 위첨자로 판정합니다. 정의가 유일한 숫자 위첨자는 공식 미주 호출로, 그 밖의 위첨자는 공식 서식으로 옮깁니다. 글자가 아닌 내용이 의심되는 칸은 위첨자·미주로 해석하지 않고 보통 글자로 둡니다. 본문 위첨자 판정은 바꾸지 않습니다. 번호 캡션이 붙은 표·그림은 원문 번호를 고정 번호로 넣고 캡션 앞의 번호를 뗍니다(아래 "그림·표 참조"). 그 밖의 표·그림은 원본 캡션을 그대로 두고 공식 enumerated:false로 자동 번호를 숨깁니다. 캡션이 없어도 번호는 붙지 않습니다.

세로로 쌓인 영역은 모두 각각 변환할 수 있을 때만 분리합니다. 하나라도 실패하면 전체를 그림으로 남깁니다. 가로로 나란한 격자는 나누지 않습니다. 격자 없음, 칸 밖 글자, 떨어진 두 격자, 직사각형이 아닌 병합, 100행·32열 초과는 이유를 붙인 그림입니다. 글자 표의 PNG는 만들지 않습니다. 원래 격자·병합 범위·머리글 줄 수·내보낸 주석 수는 대응 자료에만 남깁니다.

병합을 푼 표는 `table-unmerged`, 칸 안의 짧은 분수선·이미지·사각형이 아닌 작은 채움 도형은 `table-cell-graphic` 경고를 붙입니다. 배경 사각형과 격자 행 경계는 의심 신호에서 뺍니다. 글자 겹침/기준선 차이 신호는 위첨자와 혼동하므로 쓰지 않습니다. 수식을 복원하지 않아 빈칸이나 조각난 글자가 남을 수 있습니다. 의심 칸은 비서나 사람이 원본으로 확인해야 합니다. 글자 표 자체를 대조 화면에서 빼거나 그림으로 바꾸지는 못하며 문서 탭에서 고칩니다. 쪽을 넘는 표도 잇지 않습니다.

정답 채점은 원래 격자의 행·열과 병합 범위를 비교합니다. 칸 값은 NFKC와 빈칸 정리만 하며 부호·단위·소수점·대소문자를 보존합니다. LaTeX 수식 칸은 일치/불일치에서 제외합니다. 수치는 이 합성 표본의 진단이며 대표 정확도가 아닙니다.

넓은 7열 표는 대조 화면의 문서 칸에서 오른쪽 열이 한 번에 보이지 않습니다. 75%·100%에서 가로 휠로 마지막 열까지 읽을 수 있고 일반 문서 탭에서도 가로 휠로 닿습니다. 화면을 고치지 않고 제약으로 남겼습니다. 설치형 Desktop·터치 입력·임의 스캔/회전 PDF와 모든 수식의 의미는 검증 범위가 아닙니다.

격리된 최신 Host에서 공개 표본의 변환·저장·표 선택·경고 hover·밝음/어두움, 표 뒤 문단의 합치기·나누기·빼기와 되돌리기를 확인했습니다. 큰 문서에서는 전체 변환·저장·공식 check, 분리한 표와 원본의 대응, 표 밖으로 내보낸 주석의 대응과 교정을 확인했습니다. 공개 표본에는 이번 규칙으로 새로 분리되는 주석 행이 없어 그 형태는 합성 단위 검사로 고정하고 실제 주석 교정은 큰 문서에서 확인했습니다. 새 표 자체의 고치기는 기존 그림처럼 비활성입니다.

공개 SDK는 격리 Host가 공급하며 플러그인 작업 폴더의 node_modules에는 pdf.js만 있습니다. Host 패키지로 가는 junction/symlink를 만들지 않았습니다. 첫 격리 checkout은 기존 추적 패키지 삭제와 손상된 의존성 설치가 있었고 `--force` 재설치가 다른 플랫폼용 선택 의존성까지 설치해 고지 검사가 실패했습니다. 그 checkout은 보존하고 새 격리 checkout에서 일반 설치와 편집기·CLI 전체 빌드를 통과한 Host로 검증했습니다. 원인 추정은 확인된 삭제 원인으로 단정하지 않습니다.

검토 수정 뒤 단위 검사 42개와 별도 SDK 통합 검사 1개가 통과했습니다. 격리 Host에서 두 PDF의 재변환·공식 저장·check를 다시 확인했으며 합성 표본의 캡션 번호는 한 번만 보입니다(`pdf/test/captures/table-text/caption.png`).

### 번호 있는 독립 수식

줄 전체가 `(1)` 또는 `(A.1)` 꼴이고, 제외되지 않은 본문 폭의 오른쪽 20%에 있으며, 같은 높이의 오른쪽에 글자가 없고 왼쪽에 글자나 영역이 있는 번호를 닻으로 씁니다. 왼쪽 목록 표시는 닻으로 잡지 않습니다. 번호 없는 수식은 찾지 않습니다.

옆 그림이 없으면 번호와 세로로 겹치는 글자 상자부터 겹치거나 거의 닿은 상자(번호 높이의 10% 이내)를 연결합니다. 본문 폭의 80% 이상을 채우는 줄은 연결하지 않습니다. 수식 근호·분수의 가로 괘선은 글자 경계에서 번호 높이 이내인 것까지 그림에 포함합니다. 보통 문단 간격과 `where` 설명은 연결하지 않습니다. 뜻·폰트 이름·특정 쪽 번호는 신호로 쓰지 않습니다.

한 그림에 번호가 여럿이면 번호 띠 사이의 빈 곳에서 세로로 나눕니다. 괘선 격자 아래 번호가 있으면 격자 아래 끝을 표의 끝으로 남겨 엄격한 기존 표 판정에 맡깁니다. 분리된 수식은 이후 영역 병합에서 보호합니다. `figure`와 `formula:true`, 경고 `formula-as-image`(수식을 그림으로 둠)로 내고 대체 글자는 `수식 영역`입니다. 캡션·자동 번호는 붙이지 않습니다. 화면 코드는 바꾸지 않습니다.

채점은 정답 수식마다 `own_image`(다른 정답 표·수식과 겹치지 않는 자기 그림 하나), `merged`, `fragmented_text`, `missing`을 별도로 냅니다. 수식의 의미 일치를 검사하지 않습니다.

11쪽의 표가 수식과 분리되어 글자 표가 됩니다. 표 칸의 수식 두 개는 기존 의심 칸 경고로 남습니다. 표 밖 채점의 모든 칸과 관계(맞음 18·틀림 1·확인 안 함 3)는 그대로입니다. 이 수치는 합성 표본의 진단이며 대표 정확도가 아닙니다. 기준선은 글자 표 지표와 자기 그림 수의 하락을 막습니다.
격리 HTTP Host에서 두 표본 모두 공식 저장과 공식 `check`의 valid=true를 확인했습니다. 합성 표본은 8쪽의 두 수식을 각각 선택하고 경고 다음·이전으로 이동하여 오른쪽의 해당 수식 그림이 강조됨을 확인했습니다. 공개 캡처는 `pdf/test/captures/formula-regions/`에 있습니다. 원본 영역 다섯 개와 사라진 본문 블록은 원본 쪽 그림으로 직접 대조했습니다. 합성 표본에서는 사라진 본문이 없고, 큰 문서에서 사라진 여섯 블록은 수식 본체·한계·분모·번호였습니다. 두 표본 모두 글자 표의 누락·중복 낱말은 0입니다.

번호 없는 독립 수식·본문 안 수식·표 칸의 수식 복원과 `where` 기호 설명 정리는 범위 밖입니다. 수식의 의미 정확도, 다른 문서의 다단 배치·폰트·회전·스캔, 설치형 Desktop과 다른 OS는 검증하지 않았습니다. 공유 그림과 표의 복합 영역 분리는 작은 합성 줄 자료로도 검사했으며, 실제 표본에서는 추출기가 남긴 별도 도형 영역을 이후 병합에서 보호하는 경로로 분리됐습니다. 새 플랫폼 우회는 없습니다.

### 엔진과 문서 형식 프로필

변환 규칙은 공통 엔진(`rules.mjs`, `extract.mjs`, `table-grid.mjs`, `formula-regions.mjs`)과 문서 형식 프로필(`pdf/profiles/`)로 나뉩니다. 엔진은 어느 PDF에나 통하는 모양·배치 신호를 읽고, 프로필은 한 문서군의 글자 약속만 담습니다. 프로필은 번호 제목 해석 함수 `heading`, 링크 글자·제목의 조항 번호를 읽는 `linkedNumber`·`sectionNumber`, 캡션 패턴 `caption`과 캡션이 가리키는 종류 `captionKind`, 본문의 그림·표 참조 글자 `reference`와 링크 없는 문서에서 다른 규격의 번호를 거르는 `foreignReference`, NOTE 문단 `note`, NOTE 문단을 알아보고 알림 상자 본문을 정하는 함수 `noteBody`, 표 아래 NOTE 줄 `tableNote`, 본문 시작 제목 `bodyStart`만 가집니다. `null`은 그 약속을 쓰지 않는다는 뜻입니다.

- `ieee`: IEEE 표준의 약속.
- `sheet`: 도면 용지 요구사양서. 같은 위치의 좌우 외곽선과 아래 칸, 상단 번호와 대괄호 식별자가 두 쪽 이상에서 함께 보일 때 선택합니다.
- `generic`: 문서군을 모를 때의 기본값. NOTE 문단, NOTE 알림 상자와 표 아래 NOTE 줄은 끕니다. 부록 제목, 캡션 모양, 그림·표 참조 글자, 본문 시작 제목은 공개 표본이 기대고 있어 켜 두었습니다(재검토 대상).

**선택.** `pdf/profiles/index.mjs`의 `selectProfile`은 첫 두 쪽에 `IEEE Std <번호>`로 시작하는 줄이 있거나 PDF 제목이 그렇게 시작하면 `ieee`를 고릅니다. 다음으로 도면 용지 신호를 확인하고 둘 다 해당하지 않으면 `generic`을 고릅니다. 문장 속 인용이나 PDF의 다른 정보 칸에 IEEE가 나오는 것은 신호가 아닙니다(공개 표본의 주제 칸이 그렇습니다). 고른 이름은 변환 결과·대응 자료·`measure.mjs` 출력의 `profile`에 남습니다. 화면은 아직 이 값을 쓰지 않으며, 이 칸이 없는 이전 대응 자료도 그대로 읽힙니다.

도면 용지에서는 최소 3쪽 중 80% 이상에서 0.5pt 단위 좌표가 같은 양쪽 외곽선과 아래 칸을 확인하고, 그 틀의 선·하단 그림을 영역 후보에서 뺍니다. 기존 영역 하나가 쪽 면적의 65%를 넘고 P 또는 표 칸에 연결된 글자가 95% 이상인 쪽에서 태그 경계를 사용합니다. 큰 블록은 좌표로 정렬합니다. 같은 절에 이어지는 제목은 쪽별 원본 상자를 유지하며 한 번만 씁니다. 준거 규격 두 열은 표로, 식별자는 절 아래 제목으로, 대괄호 소제목은 굵은 문단으로 옮깁니다. 번역문을 나눌 때는 같은 태그 안에서 가나·한자 비율이 15%를 넘는 줄을 구분합니다.

### NOTE 알림 상자와 쪽을 넘는 목록

**NOTE(IEEE 프로필).** `NOTE—`, `NOTE 1—`처럼 시작하는 본문 문단은 리치오 알림 상자 `note`(화면 이름 "참고")로 저장합니다. 상자 본문은 원문 글자 그대로입니다(소유자 결정, 2026-11-18). `NOTE` 낱말, 번호, 구분 기호와 빈칸을 바꾸지 않으므로 상자의 종류 이름표("참고")와 `NOTE`가 겹쳐 보이는 것은 받아들입니다. 구분 기호는 줄표(—, –, ―)와 하이픈을 받습니다.

| 원문 | 알림 상자 본문 |
| --- | --- |
| `NOTE—text` | `NOTE—text` |
| `NOTE 2—text` | `NOTE 2—text` |
| `NOTE 3 – text` | `NOTE 3 – text` |

쪽을 넘는 NOTE는 쪽을 넘는 문단 잇기(P-02)가 먼저 한 문단으로 이은 뒤 상자로 바뀌므로 상자 하나에 원본 상자 둘이 대응합니다. NOTE 뒤에 NOTE 표시 없이 이어지는 문단은 상자에 넣지 않습니다. **목록 항목 안의 NOTE(L-07, 소유자 결정 2026-11-18)**는 상자로 빼지 않습니다. 바로 앞 블록(사이의 각주는 건너뜀)이 같은 쪽의 목록 항목이고 NOTE의 왼쪽 끝이 그 항목의 표시보다 0.7em 넘게 들어가 있으면(항목 글 열) 그 항목 안의 NOTE로 봅니다. 리치오 목록 항목은 문단 하나(인라인 내용 하나와 중첩 목록)만 담으므로, 원문 글자 그대로 항목 글 뒤에 빈칸 하나를 두고 이어 붙이고 원본 상자도 그 항목에 합칩니다. 그래서 목록이 NOTE에서 끊기지 않습니다. 목록 여백에 놓인 NOTE는 전처럼 목록 뒤의 상자입니다. 큰 표준 문서에서는 106쪽의 NOTE 하나가 해당하며, 원본에서 그 NOTE는 항목 글 열에 맞춰 들어가 있습니다(PDF 구조 태그는 이 NOTE를 목록 밖 문단으로 태그하지만, 이 문서의 목록 태그는 표 캡션에도 붙어 있어 배치를 따랐습니다). 알림 상자는 37개, 목록은 51개(이 NOTE 뒤에서 이어지던 목록이 없어 그대로)입니다. 리치오 알림 상자는 문단 하나만 담고, 큰 표준 문서에는 여러 문단으로 된 NOTE가 없었으며(NOTE 뒤에 NOTE 표시 없이 NOTE 크기로 이어지는 문단이 없음), 글자 크기만으로 뒤 문단을 NOTE에 붙이면 잘못 붙일 위험이 있기 때문입니다. 글자 표에서 주석으로 빼낸 표 아래 NOTE는 그대로 문단입니다. 범용 프로필은 바뀌지 않습니다.

**쪽을 넘는 목록(엔진).** 쪽을 넘는 문단 잇기와 같은 단계에서, 쪽의 첫 본문 블록이 목록 항목이고 앞 쪽이 목록으로 끝났으면 앞 쪽 끝의 목록 항목 가운데 들여쓰기가 같은(0.7em 이내) 항목을 찾습니다. 그 항목과 표시 모양이 같고 번호가 바로 다음이면(`a)`→`b)`, `1)`→`2)`, `(i)`→`(ii)`, 같은 기호) 이어진 목록으로 표시합니다. 사이에 든 각주는 건너뜁니다. 번호가 끊기거나(`a)`→`c)`), 모양이 다르거나(`a)`→`(b)`, `a)`→`B)`, 다른 기호), 들여쓰기가 다르면 잇지 않습니다. 작성 계획은 이 표시가 있을 때만 쪽 경계에서 목록을 잇습니다. 다음 쪽이 더 깊은 단계의 새 하위 목록으로 시작하는 경우는 잇지 않습니다. 표시 없이 다음 쪽으로 넘어간 항목의 글(L-06)도 잇지 않습니다. 변환 결과의 `continuesList`가 이 표시이고 `stats.lists.cross_page_joined`가 그 수, `stats.notes`가 알림 상자 수입니다.

**큰 표준 문서(IEEE) 결과.** NOTE로 시작하는 문단은 40개이고 그중 38개가 알림 상자가 됐습니다. 나머지 둘은 글자 표에서 빼낸 표 아래 NOTE입니다. 원본 쪽과 PDF 구조 태그(검증용으로만 대조)를 보고 놓친 것과 잘못 바꾼 것이 없음을 확인했습니다. 표 바로 아래 왼쪽 끝에서 시작해 표 영역에 들지 않은 NOTE 하나는 알림 상자가 됐고, 목록 항목 안에 든 NOTE 하나는 처음에 목록 뒤의 상자가 됐고, 지금은 그 항목의 글로 둡니다(L-07, 아래). 알림 상자는 38개에서 37개가 됐습니다. 쪽을 넘는 목록은 7곳을 이었고(그중 5곳은 사이에 각주가 있어 이전에는 두 목록이었음) 원본에서 잘못 이은 것은 0입니다. 저장 목록은 56개에서 51개가 됐습니다. 제목 240(1~5단계 19·77·92·35·17), 책갈피 일치 188, 각주 정의 141, 표 캡션 48, 그림 캡션 26, 글자 표 62, 쪽을 넘는 문단 11, 경고 75, 분류되지 않은 글자 0은 그대로입니다. 작성 입력은 공식 CLI `create`와 `check`를 통과했습니다(그림은 문단으로 바꿔 검사).

**공개 표본과 채점.** 공개 LSR 표본은 범용 프로필이고 쪽을 넘는 목록이 없어 변환 결과·작성 입력이 새 통계 칸을 빼고 바이트 단위로 같습니다. 정답 자료에도 NOTE 상자와 쪽을 넘는 목록이 없어 채점과 `answer-key-baseline.json`은 바뀌지 않습니다(정답의 NOTE 세 개는 범용 프로필에서 문단이 맞는 답입니다). 새 동작은 손으로 만든 줄 자료와 합성 표본 `pdf/test/fixtures/notes-lists.pdf`로 검사합니다.

**대조 화면.** 알림 상자 블록은 "참고"로 표시하고 본문과 같은 색을 씁니다. 격리 HTTP Host에서 합성 표본으로 알림 상자 선택과 띠, 두 쪽에 걸친 목록이 오른쪽의 한 목록에 대응하는 것, 이웃한 번호 목록 둘의 합치기와 되돌리기, 목록과 본문을 섞어 고르면 합치기가 막히는 것을 확인했습니다. SDK 통합 검사는 각주 호출이 든 목록의 합치기·되돌리기가 문서 바이트를 원래대로 돌리는 것을 확인합니다. 캡처는 [알림 상자 선택](pdf/test/captures/notes-lists/note-selected.png), [쪽을 넘는 목록](pdf/test/captures/notes-lists/list-continued.png), [목록 합치기](pdf/test/captures/notes-lists/lists-merged.png)입니다. 큰 표준 문서는 Host에서 다시 변환하지 않았고 설치형 Desktop·다른 OS·어두운 테마는 이번에 확인하지 않았습니다.

### 그림·표 참조

원문과 번호가 같은 그림·표 참조는 리치오 참조로 바꿉니다. PDF의 문서 안 링크가 조항·부록 제목을 가리키면 원문 글자를 유지하는 일반 링크로 저장합니다. 수식·참고문헌·각주·표 주석 참조는 글자로 둡니다.

**대상(그림·표).** 같은 종류의 번호 캡션(`Figure 3—…`, `Table B.2—…`)이 붙은 그림 영역과 글자 표는 이름표(`fig-3`, `tab-B.2`)와 원문 번호를 고정 번호로 받습니다. 리치오가 캡션 앞에 `Figure 3`을 그리므로 캡션 글자에서 `Figure 3—`를 뗍니다. 원문의 줄표 구분자는 리치오의 `. `가 됩니다. 그림으로 들어간 표는 리치오에서 `Figure n`으로 보이므로 번호를 넣지 않고 원래 캡션 글자를 그대로 둡니다. 이어지는 표처럼 같은 번호 캡션이 다시 나오면 첫째만 대상이고 둘째는 원래 캡션 글자를 둡니다. 나머지 그림·표는 전처럼 `enumerated:false`이므로 문서의 번호 방식은 고정 번호이고 번호 경고가 나지 않습니다.

**조항·부록 링크.** 대조 화면 오른쪽에서 링크를 Ctrl+클릭하면 제목으로 이동합니다(리치오 #1957 이후). 원문에 목적지 높이가 있고 주석 상자가 덮은 글자 범위를 확인할 수 있을 때 연결합니다. 글자와 제목에 모두 번호가 있으면 두 번호가 같아야 합니다. 범위가 모호하거나 대상 쪽을 뺐으면 원문 글자를 보존합니다. 링크 주석이 없는 PDF에서는 조항 번호로 대상을 추정하지 않습니다.

제목 번호에서 이름표를 만듭니다(`sec-4-2-1`, `annex-b`, `annex-b-1`). 번호가 없으면 제목에서 영문·숫자를 최대 70자로 추려 쓰고, 쓸 글자가 없으면 `section`을 씁니다. 겹치면 `-2`부터 붙입니다. 공식 작성 입력에 실제로 쓰인 링크의 제목 앞에만 `target`을 넣습니다. 저장 후 `inspect`는 이름표와 제목을 별도 블록으로 셉니다. 원본 상자는 제목에 연결하며 대응 검사에서는 두 블록의 자리를 모두 셉니다.

연결된 제목을 본문으로 바꾸거나 문서에서 빼거나 문서 제목으로 보내면 이름표도 함께 뺍니다. 화면에서 끊기는 링크 수를 알려 주며 되돌리면 이름표와 대응이 복원됩니다. 단위 검사는 합성 PDF의 표시 글자, 번호 불일치, 쪽 제외와 이름 충돌을 확인합니다. 격리 HTTP Host에서는 합성 PDF와 138쪽 표본 각각 앞·가운데·끝 제목으로 이동했습니다. 합성 표본의 [이동 전](pdf/test/captures/clause-links/source.png)과 [이동 후](pdf/test/captures/clause-links/destination.png)를 확인할 수 있습니다.

**참조 찾기.** 층을 나눕니다.

- 공통 엔진: PDF의 문서 안 링크 주석(`getAnnotations`)의 목적지 쪽·높이에서 대상 블록을 찾습니다. 목적지는 대개 대상보다 약 20pt 위(앞 블록의 끝)를 가리키므로 목적지를 덮는 블록, 없으면 그 아래에서 시작하는 첫 블록입니다. 대상이 캡션이면 캡션이 붙은 그림·표입니다. 링크 상자가 놓인 원본 줄에서 상자에 가장 가까운 참조 글자를 고릅니다. 줄을 넘어 두 상자로 나뉜 링크도 한 참조입니다. 글자 표 칸 안의 링크는 그 칸의 같은 참조 글자를 모두 바꿉니다(병합 값은 덮는 칸마다 반복되므로).
- IEEE 프로필: 참조 글자 `Figure n`·`Table n`(`B.2` 같은 부록 번호 포함)을 읽습니다. 링크가 가리키는 대상의 종류와 번호가 글자와 같을 때만 바꿉니다. 대상이 그림으로 들어간 표처럼 종류가 다르거나 번호가 다르면 글자로 둡니다.
- 글자 규칙: 문서에 문서 안 링크가 하나도 없을 때만 씁니다. 같은 번호의 대상 그림·표가 문서에 있어야 하고, 바로 앞에 다른 규격 이름(`ANSI C84.1 Table 1`)이 오면 버립니다. 제목과 캡션 자기 번호는 찾지 않습니다. 링크 있는 문서에서 글자 규칙 후보는 잘못 찾음이 많아 쓰지 않습니다.

참조는 Core 작성 입력의 `{kind:"reference", role:"numref", label}`로 넣습니다. 작성 계획은 실제로 넣는 블록에 대상이 있는 참조만 넣으므로 대상이 빠지면 그 참조는 글자로 남습니다. 변환 결과의 블록 `refs`(`at`, `length`, `label`)와 글자 표 칸의 `refs`가 찾은 참조이고 `stats.references`가 방식(`links`/`text`), 링크 수, 바꾼 수, 대상 수입니다.

**그림·표 참조 고치기.** 그림·표 참조는 블록 하나 안의 글자이므로 합치기·나누기·종류 바꾸기·빼기와 되돌리기가 참조를 그대로 옮깁니다. 나누기는 참조를 원문 글자(`Figure 3`) 한 자리로 셉니다. 그림·표 블록은 대조 화면에서 빼거나 종류를 바꿀 수 없어 이 화면에서는 대상이 사라지지 않습니다. 문서 탭에서 대상을 지우면 리치오가 그 참조를 "해결되지 않은 참조"로 표시합니다. 리치오 계약은 이것을 저장을 막지 않는 작성 상태로 허용합니다(완성 문서 작성 입력만 없는 대상을 거부합니다).

**IEEE 1547 결과.** 원문 문서 안 링크 1,373개 중 그림·표 참조 183개를 대상 73개(그림 25, 표 48)로 바꿨습니다. 측정 보고의 179개보다 많은 4개는 측정이 글자 모양으로 분류하지 못한 진짜 참조입니다(줄을 넘어 링크 상자 둘로 나뉜 `Table n` 둘과 `Figure X.n` 하나, 링크 상자가 글자 일부만 덮은 `Figure n` 하나). 그래서 대상도 하나 많습니다. 원본 쪽과 대조해 리치오 표시가 원문 글자와 다른 것 0, 잘못 바꾼 것 0입니다(번호 앞 빈칸이 U+00A0인 것만 다름). 바꾸지 못한 그림 참조 링크 3개는 모두 같은 그림을 가리키며, 그 그림은 영역을 찾지 못해 캡션이 그림에 붙지 않았거나 링크 목적지가 쪽 끝·제목을 가리킵니다. 캡션 번호를 뗀 그림·표 73개 모두 원문 번호와 리치오 번호가 같고 공식 `check`는 유효·해결되지 않은 참조 0·번호 방식 고정·번호 경고 0입니다. 제목 240, 책갈피 일치 188, 각주 정의 141, 표 캡션 48, 그림 캡션 26, 경고 75 등 다른 통계는 바뀌지 않았습니다.

**공개 표본(LSR).** 링크가 없어 글자 규칙으로 후보 5개(`Table 1`, `Table 3` 두 번, `Figure K.1`, `Figure K.2`)가 모두 같은 번호의 대상으로 바뀝니다. 그림으로 들어간 `Table L.2`와 이어지는 표의 둘째 `Table 3` 캡션은 원래 글자를 둡니다. 격리 HTTP Host에서 변환한 문서를 열어 다섯 참조가 모두 해결되어 링크로 보이고, 누르면 `Figure K.1` 그림과 `Table 3` 표가 선택되는 것을 확인했습니다. 캡처는 [문서의 참조와 대상](pdf/test/captures/figure-table-refs/document-reference.png), [그림 블록을 고른 대조 화면](pdf/test/captures/figure-table-refs/figure-selected.png)입니다. 정답 채점과 `answer-key-baseline.json`은 바뀌지 않습니다.

단위 검사는 링크 목적지 → 대상 블록, 번호·종류 일치, 같은 블록의 같은 번호 중 링크가 덮은 것 고르기, 캡션 번호 떼기, 글자 규칙의 캡션 존재·링크 없음 조건, 대상이 빠진 참조, 나누기 위치를 손 입력으로 검사합니다. SDK 통합 검사는 참조가 든 문단의 나누기·합치기·종류 바꾸기·빼기와 되돌리기가 문서 바이트를 되돌리고 `check`에 해결되지 않은 참조가 없음을 확인합니다. IEEE는 Host에서 다시 변환하지 않았고 어두운 테마·설치형 Desktop은 이번에 확인하지 않았습니다.

### 원본 쪽 그리기 실패

원본 칸과 쪽 고르기 화면의 쪽 그림이 실패하면 그 쪽 자리에만 "이 쪽을 그리지 못했습니다."와 **다시 그리기**를 보입니다(쪽 고르기 미리 보기는 "그리지 못했습니다"를 보이고 다시 보일 때 그립니다). 다시 그리기에 성공하면 안내가 사라집니다. 배율 변경·스크롤로 취소된 그리기와 화면에서 내려간 쪽은 실패로 보지 않습니다. 같은 canvas에는 이전 그리기를 취소하고 끝나기를 기다린 뒤 다시 그립니다(`page-render.mjs`, V-03). 화면 위의 오류 상자에는 닫기가 없으므로 다음에 성공한 동작(블록 고르기, 경고 이전·다음, 배율 바꾸기, 문서 열기)에서 사라집니다.

격리 HTTP Host에서 공개 표본의 한 쪽만 그리기에 실패하게 만들어, 수정 전에는 화면 전체 오류 상자가 뜨고 남는 것을, 수정 후에는 그 쪽 자리 안내만 뜨고 다시 그리기로 사라지는 것을 확인했습니다([캡처](pdf/test/captures/page-render-error/page-failed.png)). 소유자가 본 오류의 실제 종류는 재현하지 못했습니다. 큰 표준 문서에서 배율 연속 변경, 빠른 스크롤, 고친 뒤 다시 읽기, 쪽이 들어오자마자 내려가는 경합을 섞어도 나온 것은 내려간 쪽의 취소뿐이었습니다. 설치형 Desktop은 확인하지 않았습니다.

### 글자 서식과 인라인 수식

문단·목록 항목·알림 상자·각주 정의·글자 표의 칸에서 일부만 굵거나 기울어진 글자를 옮긴다. 정의 항목의 굵은 머리말도 여기에 포함된다. 경계의 빈칸과 문장부호, 낱말 중간에서 끊긴 강조, 제목과 캡션의 서식은 생략한다. 원본 글자 조각을 작성할 문장의 끝과 공백을 제외하고 맞출 수 있어야 한다. PDF 글꼴 이름에 굵기나 기울임 정보가 없으면 해당 서식을 추정하지 않는다.

첨자는 앞 글자 크기의 45% 이상 80% 미만이고 두 조각의 수평 간격이 앞 글자 크기의 −16% 이상 12% 이하일 때 검사한다. 기준선이 아래로 3.5% 이상 또는 위로 12% 이상 움직이고 그 차이가 65% 이하인 수평 글자가 대상이다. 로마자·그리스 글자 하나에 영숫자 첨자가 붙으면 인라인 수식으로 옮긴다. 위첨자 변수는 기울임 글꼴을 요구한다. 여러 글자의 곧은 첨자 낱말은 LaTeX의 `\mathrm{}`로 표시한다. 단위의 제곱·세제곱과 서수는 위첨자로, 화학식처럼 변수로 확정하기 어려운 작은 글자는 아래첨자로 남긴다. 연결할 정의가 있는 숫자 호출은 각주를 유지한다.

대조 화면에서 서식이 있는 문단도 원본 줄의 첫 글자를 찾아 나눈다. 인라인 수식은 문서 위치 한 칸을 차지한다. 줄 경계가 수식 안에 있거나 전체 글자가 대응하지 않으면 나누기를 거절한다. 분수·근호·여러 줄 식과 그림으로 들어간 기호는 기존 그림과 경고를 보고 검수한다.

격리 HTTP Host의 1440px 창에서 LSR 정의 항목의 [변환 전](pdf/test/captures/inline-styles/lsr-before.png)과 [변환 후](pdf/test/captures/inline-styles/lsr-after.png)를 대조했다. 별도의 합성 PDF로 문단과 표 칸의 수식 표시 및 합치기·나누기·되돌리기도 확인했다. SDK 통합 검사는 굵은 범위 안에서 나눈 뒤 되돌리면 저장한 문서의 바이트까지 복원되는지 검사한다.

## 워드 가져오기

워드 문서(.docx)를 리치오 문서로 옮깁니다. 워드는 제목 단계, 번호, 표, 캡션, 참조 대상을 파일에 적어 두므로 추정하지 않고 그대로 읽습니다. 변환이 끝나면 **원본 쪽과 변환된 문서를 나란히** 놓고, **옮기지 못했거나 바꿔 적은 곳**(확인할 곳)을 넘겨 가며 봅니다. 원본 쪽은 Word가 같은 문서를 PDF로 내보낸 것이고, 변환은 지금처럼 워드 파일에서 합니다. 변환 서버와 AI 모델은 쓰지 않습니다.

### 설치와 사용

**필요한 Host는 SDK 0.12.0과 [litzio#1957](https://github.com/litzio/litzio/pull/1957)(문서 안 링크)을 포함한 리치오(dba55078 이후)입니다.** 그 전의 Host에서도 변환과 저장은 되지만 문서 안 링크를 눌러 이동하지 못합니다.

워드 문서가 든 폴더를 리치오에서 열고 **문서 가져오기 → 문서 고르기**로 .docx를 고르면 바로 변환합니다. 묻는 선택지는 없습니다. 변환 중에는 **구조 읽기 → 그림 만들기 → 문서 저장** 세 단계와 진행 막대(그림 단계는 `그림 i / n`)가 보이고, 실패하면 그 단계에 머물러 원인을 한 문장으로 알립니다.

끝나면 먼저 왼쪽에 **확인할 곳**, 오른쪽에 변환된 문서가 보이고, 그 위에 `원본 쪽 준비 중` 한 줄이 뜹니다. 원본 쪽이 준비되면 화면이 **비교 화면**으로 바뀝니다.

- 왼쪽은 원본 쪽(세로로 이어짐, 보이는 쪽과 앞뒤 두 쪽만 그림)과 블록마다 옅은 상자, 오른쪽은 변환된 문서입니다. `ui.LinkedDocumentView`로 이어 상자와 블록 사이에 띠를 그리고, 한쪽을 누르면 다른 쪽의 짝이 같은 높이로 와서 강조되며, 한쪽을 스크롤하면 다른 쪽이 따라옵니다. 비교 화면은 PDF 대조와 같은 공용 화면([`shared/compare.jsx`](shared/compare.jsx))이라 상자 색과 범례(제목·본문·목록·표·그림·제외·확인할 곳), 함께 스크롤과 그 끄기, 배율과 Ctrl+휠(같은 기억 값), Esc로 선택 풀기, 좁은 창 안내가 PDF와 같습니다. 고치기는 없어 읽기 전용입니다.
- 머리글·바닥글과 쪽 번호는 PDF 대조의 머리글·바닥글처럼 빗금 영역으로 보입니다(올리면 `제외 · 머리글·바닥글`). Word가 내보낸 PDF에서 Word가 artifact로 표시한 글자 가운데, 어느 블록의 원본 상자와도 겹치지 않고, 쪽의 위·아래 12% 띠에 있으며, 다른 쪽 하나 이상에서 같은 높이(위·아래 끝 ±1.5pt)에 다시 나오는 줄을 잡습니다. 글자는 쪽마다 달라도 됩니다(쪽 번호). 한 줄 안에서 글자 높이의 두 배보다 멀리 떨어진 글자는 따로 잡습니다. artifact만 보는 까닭은 옮기지 않는 목차·그림 목차의 첫 줄과 끝 줄도 어느 블록에도 이어지지 않고 같은 띠의 같은 높이에 있기 때문입니다. 판정은 [`word/frames.mjs`](word/frames.mjs)의 순수 함수입니다. PDF 쪽의 머리글·바닥글 판정(`pdf/rules.mjs`의 줄 분류, 숫자를 뺀 같은 글자)과 반복 틀 찾기(`pdf/frames.mjs`, 도형)는 글자의 자리로 판정하는 이 경우에 맞지 않아 같이 쓰지 않고, 결과의 모양만 PDF 대응 자료의 `excluded`와 같게 했습니다.
- 도구 줄 오른쪽의 **확인할 곳 i / N · 이전 · 다음**으로 확인할 곳을 차례로 넘깁니다. 넘기면 양쪽이 그 블록으로 가고, 도구 줄 아래 한 줄에 위치와 설명이 보입니다. 원본 위치를 찾지 못한 블록이면 문서만 가고 그 줄에 `원본 위치 없음`이 붙습니다. 확인할 곳에 해당하는 원본 상자는 왼쪽 띠가 경고 색이고 `!`가 붙습니다. 배율은 100·75·50·40%입니다.
- 화면 폭이 목록·원본·문서 세 칸을 감당하지 못해 비교 화면에서는 확인할 곳 목록 칸을 두지 않고 이 넘기기로 옮겼습니다. 플러그인 화면에 접는 칸 부품이 없고, PDF 대조와 같은 넘기기(지금은 같은 화면)를 씁니다.
- 원본 쪽이 아직 준비 중이거나 준비하지 못했으면 목록과 문서 화면을 그대로 씁니다. 준비하지 못한 이유는 한 문장으로 보입니다(예: `Word를 찾을 수 없어 원본 쪽을 준비하지 못했습니다.`).

목록 화면에서는 확인할 곳이 종류별로 묶이고, 줄마다 가까운 제목 번호나 캡션과 짧은 설명이 있습니다. 줄을 누르면 오른쪽 문서가 그 블록으로 가서 강조됩니다. 문서 안 링크(원래 REF 필드)는 누르거나 Ctrl+클릭하면 대상으로 갑니다. 머리의 **문서 열기**는 저장된 문서를 일반 탭으로 열고, **다시 변환**은 확인 뒤 새로 만듭니다.

첫 화면의 **변환한 문서** 목록은 이름, 변환 시각, 확인할 곳 수를 보이고, 줄을 고르면 변환하지 않고 그 결과를 엽니다. 원본 쪽과 위치 자료가 있으면 바로 비교 화면이 뜨고, 없으면(이 기능 전에 변환한 문서 등) 그때 준비를 시작합니다. 이미 변환한 워드 문서를 다시 골라도 같습니다.

**저장 위치:** `X.docx`는 그 자리에 두고 `X/X.md`, `X/assets/figure-001.png`…, 확인할 곳과 블록 경로를 담은 `X/X.word-source.json`, Word가 내보낸 원본 `X/X.source.pdf`를 만듭니다. 블록의 원본 위치는 옆 파일의 `source`에 블록별 `{path, kind, page, boxes}`로 더하고(못 찾은 블록은 넣지 않음), 머리글·바닥글 영역은 `source.excluded`에 PDF 대응 자료의 `excluded`와 같은 `{page, kind: "margin", box}`로 더합니다. 문서 본문에는 좌표를 넣지 않습니다. 머리글·바닥글 영역이 생기기 전에 원본을 준비해 둔 문서는 열 때 Word를 다시 띄우지 않고 저장된 `X.source.pdf`의 글자 층에서 이 영역만 채워 옆 파일에 씁니다. 옆 파일에는 PDF와 그 PDF를 만든 워드 문서의 SHA-256도 적어, 다시 변환해도 워드 문서가 같으면 PDF를 다시 만들지 않고 위치만 새로 잇습니다. 문서는 초안 상태로 저장됩니다. 다시 변환은 이전 문서와 목록을 복구용 사본으로 옮긴 뒤 새로 저장하고, 확인할 곳까지 연결되면 사본과 더는 쓰지 않는 그림을 지웁니다. 실패하면 사본이 남습니다.

**Word가 필요한 부분(원본 쪽):** 원본 쪽은 Windows에 설치된 Word로 만듭니다. 문서가 저장된 뒤 `X.source.pdf`가 없으면 Windows PowerShell에서 **새 Word 인스턴스**를 보이지 않게 띄워 워드 문서를 읽기 전용으로 열고(최근 파일에 넣지 않음) 제목 책갈피와 문서 구조 태그를 넣은 PDF로 내보냅니다. 사용자가 열어 둔 Word는 건드리지 않습니다. 띄우는 동안 새로 생긴 WINWORD 프로세스가 정확히 하나일 때만 그것을 이번 인스턴스로 보고(PID와 시작 시각을 기록), 하나가 아니면 아무것도 하지 않고 멈춥니다. 끝나면 그 인스턴스만 `Quit()`으로 닫고 30초 안에 끝나지 않으면 그 PID만 끝냅니다. 10분 안에 끝나지 않으면 PowerShell을 멈추고, PID와 시작 시각이 기록과 같을 때만 그 Word 프로세스를 끝냅니다. PDF는 임시 이름으로 쓴 뒤 다 써졌을 때만 `X.source.pdf`로 바꿉니다. Word가 없거나 실패하면 원본 쪽 없이 목록 화면을 그대로 쓰고 이유를 알립니다. 변환과 문서는 영향을 받지 않습니다. 변환한 뒤 워드 문서가 바뀌었거나 없으면 원본 쪽을 준비하지 않습니다.

**원본 위치 잇기:** 블록의 글자를 알고 있으므로, PDF의 글자 층(머리글·바닥글은 Word가 artifact로 표시해 뺌)을 쪽 순서대로 따라가며 같은 글자를 순서대로 찾습니다. 글자와 숫자만 비교하고(공백·구두점·대소문자·목록 기호는 무시), 긴 블록은 24자 조각으로 나눠 60% 이상이 가까이 이어 나오면 찾은 것으로 봅니다. 제목은 PDF 책갈피를 닻으로 삼아 그 자리부터 찾고(목차의 같은 글자에 붙지 않음), 이 플러그인이 넣은 제목 번호가 Word가 그린 번호와 다르면 번호 없이 다시 찾습니다. 표는 칸 글자를 순서대로 찾되 병합을 풀며 반복한 값과 나눈 표가 반복한 머리 행은 바로 그 자리에서만 찾고, 캡션과 함께 표 전체를 쪽마다 상자 하나로 잡습니다. 그림은 캡션의 위치와 그림 쪽 이웃 블록 사이의 영역으로 잡고, 캡션이 없으면 앞뒤 블록이 같은 쪽에 있을 때만 그 사이로 잡습니다(표 밖으로 뺀 그림은 잡지 않음). 못 찾은 블록은 `원본 위치 없음`으로 두고 다음 블록은 마지막으로 찾은 블록 뒤에서 이어 찾습니다.

기존 방법으로 찾지 못한 인라인 그림은 양쪽 이웃 블록이 같은 쪽이나 연속한 두 쪽에 있을 때 추가로 찾습니다. 이웃 위치 사이에 Word에 기록된 가로·세로 크기와 각각 0.75pt 이내로 일치하는 PDF 그림 객체가 하나일 때 그 객체의 상자를 연결합니다. 래스터는 PDF의 Figure 태그, EMF·WMF는 Word가 PDF에 내보낸 Form의 경계를 사용합니다. 근거가 부족한 경우 원본 위치는 비워 둡니다. 기존 저장본에 새 연결을 적용하려면 **다시 변환**을 사용합니다.

**Windows 전용인 부분(그림):** EMF·WMF(와 JPEG·GIF·BMP·TIFF) 그림은 Windows PowerShell의 GDI+로 PNG를 만듭니다(원래 크기의 2배, 긴 변 최대 4,000px, 흰 바탕). 그림 전부를 PowerShell 한 번 실행으로 처리합니다. 다른 OS에서는 그 그림을 옮기지 못하고 "그림을 옮기지 못함"에 남깁니다. PNG는 어디서나 그대로 씁니다.

| 문서 속성의 제목 | 리치오 문서 제목. 없으면 정하지 않습니다 |
| 숨긴 글자 | 워드가 보이지 않게 둔 글자는 옮기지 않고 알립니다. 문단 표시가 숨김이고 보이는 내용이 없는 번호 문단(워드에서 번호째 숨겨짐)은 옮기지 않되 번호 계산에는 넣어, 뒤따르는 제목이 워드와 같은 번호를 가집니다. 이 문단은 문서 전체에서 한 줄로 알립니다 |

### 하지 않는 것

비교 화면의 오른쪽 문서에서 글자·표 칸·수식을 바로 고칠 수 있습니다([비교 화면에서 내용 고치기](#비교-화면에서-내용-고치기)). 구조 고치기(합치기·나누기·종류 바꾸기), 쪽 고르기, 검토 상태 버튼, 변환 옵션, 설정은 없습니다. 사용자가 같은 이름의 PDF를 직접 내보내 둔 것을 원본 쪽으로 받는 길도 없습니다(옆 파일에 기록이 없는 `X.source.pdf`는 다시 내보내 바꿉니다).

### 비교 화면에서 내용 고치기

PDF 대조의 [오른쪽 문서에서 내용 고치기](#오른쪽-문서에서-내용-고치기)와 같습니다. 워드 비교 화면에는 구조 고치기가 없으므로 내용 편집만 켭니다. 저장되면 `X.word-source.json`의 revision과 원본 위치 자료(`source`)의 revision을 함께 새 저장본으로 옮깁니다. 블록 수·종류는 옆 파일에 새로 적는 최상위 블록 종류 목록(`structure`)과 맞춥니다. 보기가 `onSave`로 바뀐 블록의 노드를 알리면 저장본을 읽지 않고, 옆 파일에 함께 적는 각 종류의 최상위 블록 번호(`tops`)로 그 자리의 종류만 바꿔 맞춥니다. `tops`가 없는 옆 파일(이 변경 전에 변환한 결과)은 첫 저장 확인에서 저장본을 한 번 읽어 적습니다. 이 기능 전에 변환한 결과는 비교 화면을 처음 열 때 문서가 기록된 revision 그대로이면 그 자리에서 목록을 적고, 이미 바뀌었으면 맞출 기준이 없어 지금처럼 `변환한 뒤 문서가 바뀌어 확인할 곳으로 이동할 수 없습니다.`를 알립니다. 확인할 곳은 블록 경로로 이어져 있어 그대로 유효합니다. 머리 줄에는 `변환 완료 · 확인할 곳 N` 옆에 `저장 중`·`저장 실패`·`저장 충돌`·`저장됨`·`밖에서 고친 내용을 반영함`을 보입니다. **변환한 문서**, **워드 문서 고르기**, **다시 변환**은 저장과 확인이 끝난 뒤 이어서 실행합니다. 원본 쪽이 아직 준비되지 않은 목록 화면의 문서는 지금처럼 읽기 전용입니다.

격리 HTTP Host(리치오 dee008ac)에서 합성 표본으로 문단 끝에 글을 더하고 표 칸을 고쳤습니다. 각각 블록을 벗어난 뒤 0.17~0.45초에 `저장됨`(그중 확인 0.04~0.06초), 연결 띠가 그대로였고 저장본에 두 고침이 남았습니다([캡처](word/test/captures/content-edit-1440.png)). 옆 파일과 원본 위치 자료의 revision이 함께 옮겨지는 것, 구조가 바뀐 파일과 다른 revision에서 시작한 저장의 멈춤은 SDK 통합 검사로 확인합니다. 큰 워드 표본의 저장 시간은 [PDF 쪽의 표](#오른쪽-문서에서-내용-고치기)에 있습니다.

### 확인한 범위

`npm test`는 리치오 없이 합성 표본([`word/test/fixtures/`](word/test/fixtures/README.md))으로 제목 번호와 목차 대조, 서식, 2단계 목록, 병합 풀기와 칸 문단 잇기, 캡션 번호, REF 링크와 이름표, 확인할 곳의 종류와 수, 글자 유실 0, 그림을 옮기지 못했을 때, 저장본 블록 경로의 대응과 수가 다를 때의 오류를 검사합니다. 원본 위치 잇기는 합성 입력(블록 목록과 쪽별 줄·상자)으로 순서대로 맞춤, 쪽을 넘는 문단의 상자 둘, 캡션을 포함한 표 상자와 병합을 푼 값·칸 문단 잇기, 못 찾은 블록 뒤에서도 이어지는 맞춤, 목차가 아니라 책갈피 자리의 제목, Word가 그린 제목 번호가 있거나 없을 때, 캡션으로 잡는 그림 영역을 검사합니다. 머리글·바닥글 빗금 판정은 합성 입력으로 쪽마다 같은 자리의 머리글과 글자가 바뀌는 쪽 번호, 한 쪽에만 있거나 쪽 가운데에 있거나 원본 상자와 겹치는 줄, artifact가 아닌 목차 줄, 한 줄 안에서 떨어진 두 조각을 검사하고, 손으로 만든 두 쪽 PDF(artifact 머리글·쪽 번호)로 이미 준비한 원본에 Word 없이 빗금만 채우는 경로를 검사합니다. EMF → PNG 검사와 Word로 합성 표본을 내보내 위치를 잇는 검사는 Windows에서만 돌고(Word가 없으면 건너뜀) 다른 OS에서는 건너뜁니다.

원본 쪽은 격리 HTTP Host(리치오 9a803284, Windows, 1440·1920×1080, 밝음·어두움)에서 합성 표본으로 고르기 → 변환 → 목록과 문서가 먼저 보이고 `원본 쪽 준비 중` → 비교 화면으로 바뀜(변환이 끝난 뒤 약 6.5초) → 원본 표 상자를 눌러 문서의 표가 같은 높이로 와서 강조됨 → 확인할 곳 다음 두 번(양쪽이 그 블록으로 감) → 목록으로 돌아가 다시 열기(준비 없이 비교 화면, 약 1.2초)를 확인했습니다.
